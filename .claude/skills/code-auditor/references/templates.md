## Instructions for Executing Agent

This punch list was generated by the Code Auditor. Each item is a
discrete, actionable fix. Items are ordered by priority (critical first).

Work through items sequentially. For each item:

1. Read the full description and linked evidence
2. Implement the fix
3. Verify the fix addresses the finding
4. Mark the item complete

## Punch list categories

| Category                    | Description                                                 | Typical priority |
| --------------------------- | ----------------------------------------------------------- | ---------------- |
| **Acceptance Criteria Gap** | A spec/issue criterion was not met                          | Critical or High |
| **Cornerstone Violation**       | Work violates a doctrine principle, an Accepted ADR, or a development principle | Critical         |
| **Interaction Defect**      | Subsystems work alone but fail at their intersection        | Critical or High |
| **Spec Drift**              | Implementation diverged from the spec without documentation | High             |
| **Missing Artifact**        | Expected file/test/doc doesn't exist                        | High or Medium   |
| **Code Quality**            | Complexity, pattern violations, edge cases                  | Medium           |
| **Test Gap**                | Missing or insufficient test coverage                       | Medium or High   |
| **Documentation Gap**       | README, changelog, or other docs not updated                | Medium or Low    |
| **Improvement**             | Not wrong, but could be better                              | Low              |

## Criterion entry format (Phase 2)

Covered in [`phases.md` § Phase 2](phases.md) as well. Reproduced here for quick reference:

```markdown
### AC-NN: [Criterion Text]

**Source:** [Issue #XX / Spec Phase N / Validation Gate]
**Verdict:** [PASS ✓ / PARTIAL ⚠ / FAIL ✗ / SKIP ○ / UNTESTABLE ?]

**Evidence:**

- [File path and line numbers where this is implemented]
- [Test file that validates this, if any]

**Notes:**

- [What was found, any concerns, quality observations]

**Refutation attempted (required for PASS):**

- [What you looked for that would have proven the criterion NOT met, and why the search came up empty]

**Gaps (if PARTIAL or FAIL):**

- [Specific gap description]
- [What would be needed to fully satisfy this criterion]
```

## Phase 4.6 -- the brief to the GPT seat (`second-opinions/gpt-brief.md`)

```markdown
# Second opinion on a code audit -- [scope], [tier] tier

You are the second reader of a finished code audit. You cannot run
commands or open the repository; everything you may cite is in the packet
below, and every claim you make names the packet's `file:line` or the
command output it rests on. The first reader's verdicts are in the packet;
do not take them as given.

Answer in three parts, in this order:

1. **Your own findings first.** Read the packet's evidence -- the criteria,
   the code and command excerpts, the reads -- and list every defect, gap,
   or unsafe seam you find that is not already one of the first reader's
   findings. One line each: an id (G-01, G-02, ...), a severity (Critical /
   High / Medium / Low), the packet's `file:line`, what fails and when.
2. **Refute the first reader.** For every finding at Medium or above (F-nn
   in § Executive summary and § Risk assessment), and any Low you think
   mis-graded: agree, disagree, re-grade, or narrow -- and in each case
   say what would make the finding false and whether the packet shows it.
3. **What you could not judge.** The claims the packet does not let you
   verify, so the orchestrator knows where its evidence was thin.

Everyday words, no hedging: a finding either survives your reading or it
does not, and you say which.

```

The blind pass's brief (Milestone tier) is the same packet with the
verdict columns and the findings removed, and part 1 alone asked.
