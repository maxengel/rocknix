# Provenance schema

Every Phase 1–5 output file in a council-research run emits a sibling
`.provenance.json` file. The sibling carries two related but distinct
kinds of provenance:

1. **Per-artifact attestation** — agent identity, source-file digests,
   output digest, runtime, timestamp. Verifiable by re-hashing the
   declared sources.
2. **Per-claim provenance** (Phase 5 deliverable only) — the per-claim
   table embedded in the deliverable Markdown itself, NOT in the JSON.
   See [`phase-5-deliverable.md`](phase-5-deliverable.md).

This document specifies (a) the JSON Schema for per-artifact
attestation, (b) the consumer-side re-hash command for verification,
(c) per-phase field-population rules so each phase's emitter knows
exactly what to populate.

## Consumer-side re-hash command

After receiving a phase output and its provenance sibling, re-hash
the declared sources and diff against the recorded hashes. A mismatch
indicates: the source changed between read and verify (rare —
investigate), the executor fabricated the hash (serious — escalate),
or the executor read a different version (investigate which is
canonical).

```bash
# Run from repo root. Replace <phase-N-output>.provenance.json with the actual sibling file.
paste \
  <(jq -r '.source_file_paths[]' <phase-N-output>.provenance.json) \
  <(jq -r '.source_file_hashes[]' <phase-N-output>.provenance.json) \
  | while read -r path claimed_hash; do
      actual_hash=$(sha256sum "$path" 2>/dev/null | awk '{print $1}')
      if [[ -z "$actual_hash" ]]; then
        echo "MISSING: $path (claimed hash $claimed_hash)"
      elif [[ "$actual_hash" != "$claimed_hash" ]]; then
        echo "MISMATCH: $path (claimed $claimed_hash, actual $actual_hash)"
      fi
    done
```

Run silently → all source files unchanged since read time. Any
`MISSING` or `MISMATCH` line → pause + escalate per
[`subagent-orchestration.instructions.md`](../../../../.github/instructions/subagent-orchestration.instructions.md).
Pair with the source-fact probe in [`../SKILL.md`](../SKILL.md) `## Source-fact probe` —
re-hashing verifies the source state matches; source-fact probe
verifies the artifact's claims match the source content.

## Orchestrator-staged source-hash manifest (RC3 of #2991)

When the council-research orchestrator invokes
`scripts/council-invoke.ts` to delegate a phase step to a Facilitator
member, the orchestrator is the only actor that knows which sources
the member is allowed to consume in that step. The facilitator
process is a thin substrate adapter — it does NOT discover sources on
its own. To keep the per-artifact attestation honest in the
delegation case, the orchestrator MUST stage a **source-hash
manifest** on disk and pass its path to the facilitator via
`--source-manifest <path>` together with `--council-research-run-id`
and `--phase`.

The facilitator reads the manifest at start-of-step and copies its
entries verbatim into `source_file_paths[]`, `source_file_hashes[]`,
and (when present) `read_timestamps[]` of the emitted
`.provenance.json`. The facilitator MUST NOT re-hash the sources
itself — the orchestrator's read-time hash is authoritative, because
the orchestrator is the actor that performed the reads on the
member's behalf.

### Manifest shape

```jsonc
{
  "schema_version": "1.1.0",
  "council_research_run_id": "2026-05-27-<topic-slug>",
  "phase": "phase-4",
  "sources": [
    {
      "path": "research/council-research/<run-id>/phase-3-reviews/claude-review-of-gemini.md",
      "sha256": "a1b2c3...64hex...",
      "read_timestamp_utc": "2026-05-27T14:32:10Z",
    },
    {
      "path": "research/council-research/<run-id>/phase-2-synthesis/synthesis.md",
      "sha256": "d4e5f6...64hex...",
      "read_timestamp_utc": "2026-05-27T14:32:11Z",
    },
  ],
}
```

| Field                          | Required | Source                                                                                                                                         |
| ------------------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`               | No       | Defaults to `1.1.0` when omitted. Pinned at manifest write time so a re-run against a newer schema doesn't silently re-interpret entries.      |
| `council_research_run_id`      | No       | Convenience for the facilitator's cross-linking block; redundant with the CLI flag. When both are present the CLI flag wins.                   |
| `phase`                        | No       | Same — convenience for cross-linking; CLI flag wins.                                                                                           |
| `sources[]`                    | **Yes**  | Array of source records. MUST be non-empty when the step has any source inputs. An empty array is only valid for greenfield boilerplate steps. |
| `sources[].path`               | **Yes**  | Repo-relative POSIX path. Forward-slash only.                                                                                                  |
| `sources[].sha256`             | **Yes**  | SHA-256 of the file at the read time the orchestrator performed.                                                                               |
| `sources[].read_timestamp_utc` | No       | ISO-8601 UTC. Emitted into `read_timestamps[]` when present. Encouraged for traceability of long-lived runs.                                   |

### Orchestrator workflow (mandatory before any delegated facilitator call)

1. Determine the source set for the step (per the per-phase rules in this document).
2. For each source, read the file and capture the SHA-256 at that read.
3. Write the manifest JSON to `<runDir>/<phase>/<member>/source-manifest.json` (or any path under the run directory — the exact location is orchestrator-defined).
4. Invoke the facilitator with `--source-manifest <path> --council-research-run-id <id> --phase <phase>`.
5. After the facilitator emits its `.provenance.json` sibling, the digest lint will verify that every `source_file_paths[i]` resolves and re-hashes to `source_file_hashes[i]`. Manifest tampering between staging and verification surfaces as a `source-digest-mismatch` finding.

The facilitator's job in this flow is intentionally narrow: receive
the manifest, render the prompt, call the substrate, write the
artifact, and emit the provenance sibling with the manifest's entries
verbatim. Source discovery and authoritative hashing are the
orchestrator's responsibility.

## Output hashing — hash the file as written to disk (RC4 of #2991)

Every emitter (facilitator, orchestrator, sequestration step, Phase 5
deliverable builder) MUST compute `output_file_sha256` by reading the
artifact file back from disk _after_ the write completes, then
hashing those bytes. The hash MUST NOT be computed from an in-memory
buffer that may differ from what was persisted (trailing-newline
normalization, BOM stripping, line-ending coercion, partial flushes
during a crash). The on-disk artifact is the authoritative
representation, and `output_file_sha256` is the consumer's only
ground-truth binding to it.

Concretely:

```typescript
// CORRECT — read back from disk after write completes
await writeFile(outputPath, artifactBytes);
const outputFileSha256 = sha256Bytes(await readFile(outputPath));

// WRONG — buffer may differ from what landed on disk
const outputFileSha256 = sha256Bytes(artifactBytes);
await writeFile(outputPath, artifactBytes);
```

Rationale:

- **Crash safety.** If the write is partial or the host's filesystem
  coerces line endings, a buffer-hash silently records a binding the
  consumer will fail to reproduce. A disk-read-back binds to reality.
- **Lint repair safety.** The digest lint's `--fix-artifact-paths`
  flag (RC5) refuses to repair when `output_file_sha256` does not
  match the file on disk. A buffer-hash that diverges from disk
  permanently locks out automated repair and forces manual
  intervention.
- **Round-trip honesty.** The promise of the provenance sibling is
  that any later consumer can re-hash the on-disk artifact and
  reproduce the claim. A buffer-hash breaks that promise.

The digest lint enforces this implicitly: when the recorded
`output_file_sha256` does not match the SHA-256 of the on-disk
artifact, the lint emits an `output-digest-mismatch` finding —
regardless of why the divergence happened (write tampering, encoding
coercion, or buffer-vs-disk skew).

## Per-phase field-population rules

Each phase's emitter populates the schema differently. Worked examples
for all 5 phases below.

### Phase 1 — Independent research

Each member emits ONE provenance file: `phase-1-research/<member>/corpus.provenance.json`.

| Field                  | Population rule                                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `phase`                | `"phase-1"`                                                                                                                                                        |
| `artifact_path`        | `phase-1-research/<member>/corpus.md`                                                                                                                              |
| `agent_name`           | The member's `name:` frontmatter (e.g. `"council-member-claude"`)                                                                                                  |
| `invoker_agent_name`   | `"council-research orchestrator (<orchestrator-model>)"`                                                                                                           |
| `source_file_paths[]`  | Every file the member read: the in-repo source pointers, the member's own `.agent.md`. Does NOT include other members' files (they're under `context_excluded[]`). |
| `source_file_hashes[]` | `sha256sum` of each path at read time                                                                                                                              |
| `read_timestamps[]`    | UTC timestamps captured at each `read_file` call                                                                                                                   |
| `context_excluded[]`   | Every directory the member was told NOT to read (sibling member dirs, prior council-research runs, `research/archive/`)                                            |
| `external_sources[]`   | URLs fetched if the member used web search; optional but recommended                                                                                               |
| `output_file_sha256`   | SHA-256 of `corpus.md` after writing                                                                                                                               |

The Researcher Agent emits ONE provenance file:

| `agent_name`           | `"Researcher Agent"`                                                                                                                                                               |

### Phase 4 — Council deliberation

The council skill emits per-step provenance per its own
[`output-conventions.md`](../../council/references/output-conventions.md)
— one sibling per analysis / peer-review / revised-plan / vote. The
council skill's existing schema applies; council-research extends it
by REQUIRING the same `schema_version`, `council_research_run_id`,
and `runtime` / `runtime_version` fields be populated. Other fields
follow the council skill's per-step conventions.

The orchestrator does NOT emit a separate Phase-4-level provenance
file — Phase 4's provenance is the collection of council-skill
per-step siblings, cross-linked via `council_research_run_id`.

| Field                     | Population rule (for council per-step siblings)                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `phase`                   | `"phase-4"` (NEW — extend the council skill's existing schema to require this when it runs INSIDE council-research) |
| `council_research_run_id` | Propagated from council-research Setup                                                                              |
| Other fields              | Per the council skill's existing `output-conventions.md`                                                            |

## Per-class field-population rules — orchestrator-authored and derived artifacts (v1.1.0, RC1 of #2991)

Every council-research run produces artifacts that are **not** freshly
authored by an LLM. The methodology used to be silent about their
provenance, which produced 29 missing-sibling lint findings in the
2026-05-24 researcher-federation-substrate run. This section closes
that gap.

Four classes need explicit rules:

1. **Orchestrator-authored prompts** — `phase-N/_prompts/*.md` — the
   prompt templates the orchestrator hands to each member.
2. **Orchestrator-authored scaffolding** — vote tallies, verification
   logs, READMEs, manifest indices the orchestrator composes
   mechanically from upstream artifacts.
3. **Sequestered/redacted derivations** of Phase-1/2 artifacts —
   `.sequestered-bundle/*` (anonymised corpora, redacted synthesis)
   the orchestrator stages for Phase-3 reviewers.
4. **Reviewer-handle-sanitized derivations** of Phase-3 reviews —
   `.reviews-sanitized/Review-{A..E}.md` the orchestrator stages for
   Phase-4 deliberation.

The unifying principle: **provenance ≠ authorship**. A `.provenance.json`
sibling is the audit trail of how an artifact came into existence,
regardless of whether an LLM wrote it. Orchestrator-authored and
derived artifacts are no less consequential for the deliberation than
LLM-authored ones — they MUST carry sibling provenance.

### Class 1 — Orchestrator-authored static (prompts, scaffolding, summaries)

Use for: `phase-N/_prompts/*.md`, vote tallies (`step4-vote-tally.md`),
verification logs (`model-verification-log.md`), READMEs the
orchestrator composed, manifest indices.

| Field                          | Population rule                                                                                                                                                                                                                                |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`               | `"1.1.0"`                                                                                                                                                                                                                                      |
| `phase`                        | The phase the artifact is part of (`"phase-4"` for `_prompts/step2-claude.md`, `"phase-5"` for a Phase-5 README, etc.)                                                                                                                         |
| `artifact_path`                | Repo-relative path of the .md sibling.                                                                                                                                                                                                         |
| `agent_name`                   | `"council-research orchestrator (<orchestrator-model>)"`                                                                                                                                                                                       |
| `invoker_agent_name`           | The agent that invoked the council-research skill (often the user, sometimes a parent skill).                                                                                                                                                  |
| `runtime`                      | The orchestrator's runtime (e.g. `"vscode-copilot-chat"`).                                                                                                                                                                                     |
| `model`                        | `"n/a-orchestrator-authored"` — signals no LLM generated the body. The body was composed deterministically (template fill, copy, tally).                                                                                                       |
| `derivation_kind`              | `"orchestrator-prompt"` (for `_prompts/*.md`) OR `"orchestrator-scaffolding"` (for vote tallies, verification logs, READMEs) OR `"orchestrator-summary"` (for summaries the orchestrator composed from N upstream artifacts without LLM help). |
| `source_file_paths[]`          | The methodology references the orchestrator consulted (the relevant skill reference docs, the prior phase's outputs that informed the prompt/tally). For pure boilerplate prompts, this MAY be just the skill reference.                       |
| `source_file_hashes[]`         | SHA-256 of each source at compose time. Captured by the orchestrator.                                                                                                                                                                          |
| `read_timestamps[]`            | When the orchestrator read each source.                                                                                                                                                                                                        |
| `output_file_sha256`           | SHA-256 of the .md sibling after writing.                                                                                                                                                                                                      |
| `model_attestation` (optional) | Omit or set `{ self_reported: "n/a-orchestrator-authored", substrate_attested: null, attestation_method: "none", attestation_source: null }`.                                                                                                  |
| `timestamp_utc`                | When the orchestrator finalised the artifact.                                                                                                                                                                                                  |

### Class 2 — Sequestered / redacted derivations

Use for: `phase-3-adversarial/.sequestered-bundle/Corpus-{A..E}/corpus.md`,
`phase-3-adversarial/.sequestered-bundle/synthesis-redacted.md`.

These are **mechanically derived** from a freshly-authored predecessor
(a Phase-1 corpus or the Phase-2 synthesis) by applying a known
transformation (anonymisation, identifier redaction, sibling-label
mapping). The transformation is deterministic and the chain back to
the freshly-authored predecessor MUST be walkable via
`derived_from_artifact_path`.

| Field                        | Population rule                                                                                                                                                |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`             | `"1.1.0"`                                                                                                                                                      |
| `phase`                      | The phase the derivation lives under (`"phase-3"` for `.sequestered-bundle/*`).                                                                                |
| `artifact_path`              | Repo-relative path of the .md sibling.                                                                                                                         |
| `agent_name`                 | `"council-research orchestrator (<orchestrator-model>)"`                                                                                                       |
| `invoker_agent_name`         | The agent that invoked the council-research skill.                                                                                                             |
| `model`                      | `"n/a-orchestrator-authored"` (the redaction is deterministic, not LLM-generated)                                                                              |
| `derivation_kind`            | `"sequestered-redaction"`                                                                                                                                      |
| `derived_from_artifact_path` | **REQUIRED.** Repo-relative path of the predecessor (e.g. `phase-1-research/claude/corpus.md` → `phase-3-adversarial/.sequestered-bundle/Corpus-A/corpus.md`). |
| `source_file_paths[]`        | At minimum, `derived_from_artifact_path` plus the orchestrator's redaction-rule reference. May include the label-mapping table if one was used.                |
| `source_file_hashes[]`       | SHA-256 of each source at redaction time. The predecessor's hash here MUST equal its own `output_file_sha256` (chain-of-custody check).                        |
| `read_timestamps[]`          | When the orchestrator read each source.                                                                                                                        |
| `output_file_sha256`         | SHA-256 of the redacted .md sibling.                                                                                                                           |
| `timestamp_utc`              | When the orchestrator finalised the redaction.                                                                                                                 |

Worked example — `phase-3-adversarial/.sequestered-bundle/Corpus-A/corpus.md`:

```json

  "council_research_run_id": "9a3b1c20-7f4e-4d2b-b5e6-1a8d2c3f4a5b",
  "phase": "phase-3",
  "artifact_path": "research/council-research/2026-05-24-researcher-federation-substrate/phase-3-adversarial/.sequestered-bundle/Corpus-A/corpus.md",
  "output_file_sha256": "<sha256 of redacted corpus.md>",
  "agent_name": "council-research orchestrator (Claude Opus 4.8 (copilot))",
  "invoker_agent_name": "user (Local Chat)",
  "runtime": "vscode-copilot-chat",
  "model": "n/a-orchestrator-authored",
  "derivation_kind": "sequestered-redaction",
  "derived_from_artifact_path": "research/council-research/2026-05-24-researcher-federation-substrate/phase-1-research/<member>/corpus.md",
  "source_file_paths": [
    "research/council-research/2026-05-24-researcher-federation-substrate/phase-1-research/<member>/corpus.md",

  ],
```

> **Note on `<member>` placeholder:** the un-anonymised
> `derived_from_artifact_path` value links the sequestered copy back
> to its origin. This linkage is acceptable inside the .provenance.json
> because the audit trail is consumed AFTER deliberation, not during.
> If your run's threat model requires anonymity to survive past
> deliberation, you may instead store the un-anonymised path in an
> orchestrator-private map and put `"sequestered-anonymous"` here
> (file an Outcome-C deferral note per `found-failure-discipline`).
> For the 2026-05-24 backfill, sequestration was lifted at Phase 4, so
> the direct linkage is correct.

### Class 3 — Reviewer-handle-sanitized derivations

Use for: `phase-4-deliberation/.reviews-sanitized/Review-{A..E}.md`.

Same shape as Class 2 with `derivation_kind: "reviewer-handle-sanitization"`
and `derived_from_artifact_path` pointing at the corresponding

(`Review-A` ↔ `<member>`) is the same map used for Phase-3

### Class 4 — Bundled README / index artifacts

Use for: top-level `README.md`, `phase-N/README.md` indices.

Treat as Class 1 (`derivation_kind: "orchestrator-scaffolding"`). The
source_file_paths[] are the artifacts the README indexes.

### Retroactive annotation — preserving historical runs

Runs that pre-date the v1.1.0 sibling-mandatory enforcement may be
valuable as research or training corpora even when their provenance is
imperfect. Treat those runs as historical artifacts: preserve their
substantive outputs, label their trust posture, and do **not** rewrite
history to make lint findings disappear.

Allowed retroactive work is limited to annotation and path-honesty
repair:

| Situation                                                        | Correct action                                                                                                                                                                                                 |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Metadata points at the wrong artifact                            | Correct the pointer and add `backfill_note` or a run-level closeout note explaining the repair. Preserve historical digest values unless the original emission hash is known.                                  |
| Historical digest drift is present                               | Leave the drift visible. Document whether the research result remains trusted and whether the drift affects downstream use.                                                                                    |
| Original read timestamps or source hashes are absent             | Do not invent them. Add a note that the original values cannot be reconstructed.                                                                                                                               |
| A run is kept for research/training value                        | Add a README or closeout artifact that labels canonical outputs, superseded material, and known provenance limits.                                                                                             |
| A superseded phase attempt in an otherwise current run has drift | Preserve it as non-canonical evidence. The run README must declare the accepted canonical phase chain, list the superseded attempt, and report full-root findings separately from canonical-chain strict lint. |

For future runs, use the Class 1–4 rules above at artifact creation
time. Do not apply those rules after the fact as if current-state
hashes were original read-time evidence.

### Canonical-chain closeout with preserved superseded drift

A versioned replay or corrected phase attempt can supersede an earlier phase
directory without deleting the earlier evidence. In that case, downstream
consumers judge the run through the accepted canonical chain, not by pretending
the superseded material is clean.

Closeout requirements:

1. Declare the accepted canonical chain in the top-level run README.
2. Ensure Phase 4 and Phase 5 provenance/source manifests cite only accepted
   canonical attempts.
3. Run strict lint summaries over the accepted canonical-chain directories.
4. Run or record the full-root summary separately when preserved superseded
   material remains under the run root.
5. If full-root lint still reports only documented superseded findings, report
   that caveat exactly. Do not rewrite old read-time hashes or timestamps to
   force a full-root pass.

This is different from a `.digest-drift-allowlist.json`: canonical-chain
closeout preserves and names a non-canonical artifact while keeping the accepted
chain strict. A digest-drift allowlist changes the trust posture of the whole
run root.

### Lint behavior with v1.1.0

The existing lints accept v1.1.0 siblings unchanged:

- `lint-council-research-provenance.ts` checks sibling presence + JSON
  validity only. The new fields are additive.
- `lint-council-research-digests.ts` validates `artifact_path`,
  `output_file_sha256`, `source_file_paths`/`source_file_hashes` —
  all of which are populated honestly for v1.1.0 siblings (the
  orchestrator hashes the .md and the sources it actually consulted).

A future lint extension (tracked under RC1 in #2991 if needed) MAY
add a `derived_from_artifact_path` resolver that walks the chain back
to a freshly-authored ancestor and verifies the predecessor's claimed
`output_file_sha256` equals the hash this derivation recorded for it.
Not required for v1.1.0 schema acceptance.

### Per-run preserved-corpus allowlist (`.digest-drift-allowlist.json`)

A run that pre-dates a load-bearing discipline (read-time source
hashing, orchestrator-staged output hashing, the composite Facilitator
schema, the v1.1.0 `artifact_path`/`output_file_sha256` contract) may
be preserved as evidence rather than rewritten. The historical drift
is then surfaced as informational findings via a per-run-root
`.digest-drift-allowlist.json` file. Shape:

```jsonc
{
  "schema_version": "1.0.0",
  "purpose": "preserved-historical-corpus-digest-drift-allowlist",
  "council_research_run_id": "<run uuid>",
  "decision_artifact": "research/council-research/<run-slug>/retroactive-provenance-closeout.md",
  "reason": "<why this run is preserved as-is, not rewritten>",
  "allow_all_digest_findings_for_run": true,
  "allowed_kinds": [
    "source-digest-mismatch",
    "schema-mismatch",
    "output-digest-mismatch",
    "artifact-path-mismatch",
  ],
}
```

Rules:

- The file is scoped to a single run-root and **must not** be copied
  to new runs. Each run is allowlisted on its own merits with a
  pointer to a closeout artifact that explains why.
- `allow_all_digest_findings_for_run` MUST be `true` for the
  `allowed_kinds` list to take effect — partial allowlists (allowlist
  one path, block another within the same run) are not supported by
  design. Allowlisting is a per-run trust posture, not a path-level
  exception mechanism.
- A `decision_artifact` MUST exist and MUST be the human-readable
  rationale for preserving this run.
- New runs face the full strict gate. Adding a new entry to the
  allowlist for a fresh run is a smell — fix the run instead.
- For a current run with a clean canonical chain and drift confined to a
  preserved superseded attempt, prefer canonical-chain closeout plus explicit
  README caveat over a broad run-root allowlist. The allowlist is not
  path-scoped and must not become a way to hide future findings in accepted
  canonical artifacts.

Lint behaviour: `lint-council-research-digests.ts --strict` annotates
each finding with `allowed: true|false` based on the matching
run-root allowlist, and exits non-zero **only** when at least one
finding is `allowed: false`. The provenance lint does not implement
allowlists — provenance siblings are either present or they are not,
and absence is always blocking.

## Lint summary gate — pre-commit and per-phase (RC6 of #2991)

Two surfaces share one script:

| Surface                         | Invocation                                                                                               | Exit-code semantics                                                                                 |
| ------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **Pre-commit hook**             | `npx tsx scripts/summarize-council-research-lints.ts --strict research/council-research/`                | Exits 1 if any non-allowlisted finding exists anywhere under the council-research tree.             |
| **Per-phase orchestrator gate** | `npx tsx scripts/summarize-council-research-lints.ts --strict <runDir>/phase-N/` after every phase write | Exits 1 if the just-written phase introduced a new blocking finding. Orchestrator pauses on exit 1. |

The summary script:

1. Spawns the provenance lint and the digest lint in `--json` mode
   against the requested target path.
2. Groups findings by lint, finding kind, and run area (phase folder
   under the run-root).
3. Honours per-lint `blocking_count` (digest lint sets it from the
   allowlist; provenance lint omits it, so all provenance findings
   are blocking).
4. Exits 1 in `--strict` mode if and only if total blocking > 0.

Tiered-capture mapping
(`failure-is-knowledge` (estate-local; scaffold: development-principles § Quality — treat every discovered failure as explicit work)):
the per-phase gate catches drift at **T1** (one phase, one drift) so
the next phase boundary surfaces it; absent that gate, the same drift
re-enters at **T3** as 200+ end-of-run findings whose root causes are
indistinguishable from each other. The pre-commit hook is a backstop
in case the orchestrator gate is skipped — VCS refuses the commit
rather than absorbing the drift silently.

## Read-time digest capture — the load-bearing discipline

The single most consequential rule in this schema: **`source_file_hashes[]`
must be captured AT READ TIME, not at end-of-phase.** Reasons:

1. **Anti-backfill:** End-of-phase hash capture could mean the agent
   never actually read the file — it could just `sha256sum` the file
   at the end and report a plausible hash. Read-time capture pairs
   the hash with the read event.
2. **Source-change detection:** If a source file changes mid-phase
   (rare in practice but possible — concurrent editing, automated
   process), read-time digests will diverge from end-of-phase digests,
   surfacing the change rather than papering it over.
3. **Trust model:** Read-time digest is what the executing agent's
   reasoning was actually based on. End-of-phase digest is what the
   file LOOKED LIKE at the end. The first is what we need to verify;
   the second is meaningless.

Operational rule for executing agents: each time you call `read_file`,
**immediately** append `{path, sha256, timestamp_utc}` to your phase's
`.provenance.json` working file. Treat this as part of the read
operation, not as bookkeeping you'll catch up on later. Skipping the
append is equivalent to silent failure (per
`silent-failure-discipline` (estate-local; scaffold: incident-response + development-principles fail-loud rules))
and corrupts the verification primitive.
