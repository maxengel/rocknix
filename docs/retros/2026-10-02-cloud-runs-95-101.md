# Mini-retro: cloud runs 95 to 101

**Written:** 2026-10-02. **Scope:** #354, #353, #363, #364, #365, #366;
readiness review #375. This is the requested step back (D-WORKFLOW-134),
not a declaration that the cloud epic is complete. Baseline: run 101
`b2378d9c33`, ES `e108699ea`; earlier RECORDs and raw logs are indexed in
`docs/audits/2026_10_02-milestone-375-rasteratops-0-0-1/`.

## What worked well

- Keeping images, source IDs, raw logs and frames lets this review distinguish
  the image from later test changes. Run 101 was retained despite red gates.
- Copy/check/remove and the pair test preserve a useful invariant: a second
  device can follow an emptied old root or merge saves written there later.
  The corrected in-tree pair tool has now run against RC2 and run 101:
  **42 PASS, 0 FAIL**, `qa-b2378d9c33-pair-migration-from-69e6039f8f-20261002-0606`.
- Frame comparison caught real presentation changes (run 97's settings inset),
  while the dedicated proof caught behavior a green main suite missed
  (run 100's backup recreating `/GAMES`). Both kinds of proof are needed.

## What was harder than expected

- The folder question was answered by seven actors. Moving follow out of sync
  fixed its cost, then the backup guard reintroduced a smaller network check.
  Run 100's 16 ms difference became run 101's 59 ms, above the 30 ms criterion.
- Fixtures contained their own old defaults. Run 96's screens and run 101's
  round-trip failed for that reason. The stale-name guard itself missed bare
  `/GAMES`, so a green guard did not imply a current fixture (#366).
- The session proof inherited state across cases: D remembered C's selection;
  C/F/G mostly collected frames; an earlier runner could return success despite
  failed assertions. A successful rerun of D alone did not repair the chain.
- Worker lifetime and visible-card lifetime differ. The run-101 E frame shows
  SKIPPED over CHECKING YOUR CLOUD; ES clears `mInstance` before its card's
  linger ends. Waiting for the worker is insufficient for visual ordering.

## Discoveries that affect remaining issues

- `docs/rasteratops/cloud-folder-state-table.md` now distinguishes absent,
  empty, populated and unreadable folders. Startup can write into an existing
  empty legacy folder before the later scan chooses the real source. Those
  whole-boot cases remain explicit verification work, not claimed failures.
- Missing old parent and missing old child produce different restore answers,
  even when a later step can follow the fleet. This is the intersection that
  must be tested before adjusting boot order; the prior lock conflict remains
  a valid reason for D-CLOUD-171.
- Small probes of the production predicates find two additional seams for
  #375's audit: an S3 parent-listing failure becomes an absence offer, and
  changing OS_NAME hides a same-device ROCKNIX archive from the new scan.
  These need regression cases and image verification in #377 (bucket failure)
  and #376 (archive compatibility).
- Bot identity completion does not deliver OS identity. Run 101 still has a
  ROCKNIX name, updater, splash and archive format. The final combined image
  must prove their compatibility under #337/#344.
