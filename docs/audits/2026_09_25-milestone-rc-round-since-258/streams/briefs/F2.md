## PL-002: The shared rotation generators sit outside their consumers' build stamps
- **Severity:** High
- **Category:** Correctness
- **Source Finding:** F-EM-01 (gpt)
- **Owner area:** packages emulators (rotation tables)
- **Where:** the rotation generators and the `-lr` recipes that consume them (bucket 9)
- **What:** A change to a generator does not invalidate the packages that embed its table, so a wrong table ships silently on a warm root. Fix: the generator files live under (or are hashed into) each consumer's `PKG_DIR`, or the recipe's `PKG_VERSION`/stamp input names them.
- **Acceptance:** editing a generator and running `./scripts/build <core>` rebuilds the core (the `build_target` stamp moves)
<details><summary>The audit's verdict(s) this item rests on</summary>
### F-EM-01 (gpt, 9-emulators) -- the rotation generators are outside their consumers' stamps
**Seat's claim:** `rotation-table-fba.py` / `rotation-table-mame.py` live beside the package directories, not in them, so a change to a generator does not invalidate the consumers' build stamps and an incremental build ships stale tables.
**Checked:** `fbneo-lr`, `fbalpha2012-lr`, `mame2010-lr` (and the other MAME/FBA cores) run `python3 ${PKG_DIR}/../rotation-table-*.py` in their install step; `config/functions` `calculate_stamp` hashes `$PKG_DIR`, the project's `patches/$PKG_NAME` and `packages/$PKG_NAME` -- never `$PKG_DIR/..`. The same class as `device-builds.md`'s note on overrides that source a generic recipe. Upstream's CI is always clean and would not see it; a warm build root does.
**Verdict:** survived -- **High** stands (a wrong table ships silently). Punch item: the generators become a package of their own (`rotation-tables:host`, or under `projects/ROCKNIX/packages/emulators/libretro/rotation-tables/`) that each consumer names in `PKG_DEPENDS_TARGET`, so their directory is hashed; or each consumer hashes the generator into its stamp.
</details>

- **Category:** Correctness

- **Acceptance:** a `RARCH_LOG` line on the guest names the table applied; `frame-diff` shows the widget text at a sharp size
<details><summary>The audit's verdict(s) this item rests on</summary>
### F-RW-01 (gpt, 6-retroarch-widgets) -- patch 0017 carries the 14 px line as stale context

**Verdict:** survived, **Medium**: regenerate 0017 against 0016's output before the PR series (a reviewer applying the stack strictly gets a rejected hunk).
### F-RW-01 (claude, 6-retroarch-widgets) -- patch 0017's sharp-size tables never apply on the shipped font
**Checked:** `0017-widgets-sharp-font-sizes.patch:122-123`: the branch taken when `video_font_path` is set calls `gfx_widgets_font_init(... font_path, BASE_FONT_SIZE, 9.0f, NULL, 0)`, and `gfx_widgets_sharp_size` returns its input when the table is `NULL`; the tables are passed only for the ozone faces (`:114-115`). **Verdict:** survived at **Medium** (Correctness / Upstream fit; the GPT seat did not raise it): either pass a table measured for the shipped face on the user-path branch, or drop 0017 from the series and reword D-UI-088 -- a patch that claims what it does not do is a reviewer's first question upstream.
</details>
