## 3. Findings

### G2-C-01: PL-016's flush is timed to the probe's `open`, not to a field holding focus on the handheld
- **Severity:** Medium
- **Category:** Correctness / a test whose device model cannot see the failure
- **Where:** `cloud_oauth` REMOTE_PAGE `poll()`, `@@ -901,13 +1138,22 @@`; `cloud-signin-window.c` `focus_first`, `@@ -615,11 +676,17 @@`; harness C4 `page().device()`.
- **What:** On the first probe that says `open`, the page sends the whole box (`if (opened) { sent = ""; deliver(box.value); }`) and marks it delivered. On the handheld, the window has just been spawned, the provider's page is still loading, and `focus_first` polls for up to ten seconds before any field holds the caret. uinput keystrokes arriving before that land on a page with no focused field and are dropped; `sent` now equals `box.value`, so nothing resends them. The loss window PL-016 describes has moved, not closed.
- **Failure scenario:** Player scans the QR, types `me@example.com` into the phone box, chooses CONTINUE on the handheld. The phone's 2-second poll returns `open` within 0–2 s of the window process starting; Dropbox's page finishes loading 3–5 s later; `focus_first` places the caret; the field is empty; the phone shows `me@example.com` as sent. The next keystroke adds only itself — the exact symptom the item was filed for.
- **Evidence:** The C4 model's `device()` accepts every `type=` post unconditionally, so `typedBeforeOpen` cannot distinguish "sent while a field was focused" from "sent into a page with no focus". What `open` is computed from (the GET handler) is outside the diff; if it means "the window process is running" or "the page file exists", both precede a focused field. Nothing in the diff retries or holds back delivery until the handheld reports a focused text field (the window already has that probe — `on_probe`'s `text:` answer — but it is not fed back to the serve). The acceptance's guest run is the artifact that would settle it; the report lists it as not run.
