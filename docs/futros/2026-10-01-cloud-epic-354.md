## 1. What do we know and what are we assuming?

**The plan.** The default cloud folder becomes `/Rasteratops/{Saves,Backups,Content}`, as part of the brand transition (D-CLOUD-158/159). A device still on a folder this project once shipped as its default is offered the move once, MOVE first, by copy, verify, delete (D-CLOUD-160); a carried upstream `/GAMES` counts as no folder and the device is offered the creation of `/Rasteratops` with its sync folders (D-CLOUD-161); other devices follow when they find the new folder. The restore flow scans first on a page of its own and offers only what the cloud holds for this device (D-CLOUD-156, 162); the content listing shows only ours and finds the folder under the cloud root before asking (#352); the phone page's Close control moves and confirms, the finishing page is styled, and every image declares a handset chassis so the sign-in window sends WebKit's mobile identity (D-CLOUD-163, D-NET-016). Thirteen strings are approved as the baseline (D-CLOUD-164).

**Assumptions the plan relies on that are not in its text:**

- The maintainer's three devices are the only fielded ones, all on one Dropbox, and that Dropbox holds `/ROCKNIX/{Saves,Backups,Content,Saves-replaced}` and no `/GAMES` (read from the Nova, 2026-10-01). The move is therefore run once, by one device, and the other two follow.
- `rclone check` on Dropbox compares by hash; the move's verify step is only as strong as the backend's comparison (`CHECK_OPTS=(--download)` where no hash exists, `cloud_migrate_layout:~575`). The QA WebDAV compares by size alone (memory: one-writer-per-QA-cloud-folder), so a VM proof of the verify is weaker than the device's.
- The `.layout` marker is data and not a lock: two devices moving at once are kept apart by copy-then-verify-then-delete order, not by the marker.
- The interface reads `cloud_migrate_layout --state` once per page open, and a listing of the saves folder costs one `rclone lsf -R` -- acceptable on a page, never on the launch path.
- The `--follow` hook in both sync scripts runs only on a device whose saves folder is a superseded default and not kept, behind a default-route test and a twenty-second cap; on every other device it is a string test (time to play, D-CLOUD-098).
- The suite `tools/last-good-scripts-test` and `tools/cloud-round-trip` encode the old default in roughly 230 expectations; moving the default means moving those expectations, section by section, never blanket.
- The ES changes (the scan page, the dialogs, the chooser) live in the other repository and are built only by an image build; `tools/es-syntax-check` is the compiler before the pin moves.

**Confidence:** mixed. The script half is understood and now has a sandbox suite (fifteen checks, twelve of which fail against the old tool). The interface half is unbuilt and its first frames do not exist yet; the device move is a one-shot on a person's cloud.

## 3. What patterns from prior work apply that we haven't named?

- **The `/GAMES` to `/ROCKNIX` move is this exact shape, done once** (`cloud_migrate_layout` since 2026-09, PL-025/026, the F-CS-07 late-save case at `tools/last-good-scripts-test:8850`): copy, verify, delete, refuse a merge, resume a cut copy. The new target is a constant; the new source is a list. Reuse, do not rewrite.
- **A renamed key resets everyone's preference** (`upgrade-and-install.md`; `cloud_sync_helper:370-400`): the helper carries values across; it is why the Nova kept `/GAMES`. The same mechanism is the reason the move must be *offered*, not assumed from a default.
- **A name is not a behaviour** (`engineering-practices.md`): the scan's unfiltered legacy rows (#352) hid behind a comment that promised a filter. Each new verb here has a sandbox check that fails against the old code (fifteen written, twelve seen to fail).
- **Dim, don't hide** (`es-ui-style-guide.md`) decided D-CLOUD-162 on the first ask.
- **The first PASS is the one to distrust** (blindspot 39, D-QA-022): the sandbox suite passed fourteen of fourteen first time; the negative run was made before trusting it.
- **Build small items with the proposed words** (memory, 2026-09-26): the thirteen strings were approved as a batch before a build, so no item waits on wording.

## 4. What could we be missing?

**Agent-execution simulation.** A fresh agent with only #353's body builds the move page and runs the move on guest a of a `vm-pair` where guest b is on the old build (RC2's image). Decision points where it trips:

- It runs `--apply` from the page while guest b's startup sync is writing into `/ROCKNIX/Saves` (the saves sync holds `cloud_sync.lock` on the device, not in the cloud). The copy sees a save appear after the verify: the F-CS-07 case covers a *late* file in the old folder (left in place, not lost), so nothing is lost, but the two devices now disagree until b follows. The simulation says: the move page's words must tell the player to leave the other devices alone for the minutes it runs, and the P3 order must stage all three before any move.
- It reads `STATE=superseded-empty` on the Nova (whose `/GAMES` is absent) and offers CREATE IT, which seeds `/Rasteratops` -- while the Nova's real saves sit in `/ROCKNIX/Saves`, which `--state` never looked at because the Nova's conf names `/GAMES`. **The Nova is both superseded-empty (by its conf) and a `/ROCKNIX` device (by its cloud).** The state verb must look for *every* superseded default's folder in the cloud, not only the configured one, and prefer the move over the creation when one holds files. This is a gap in the script half as written tonight; it goes to #353 as a criterion and to the verb before the interface reads it.
- It ticks the chassis checkbox from the user-agent string alone; Dropbox's page may still serve the desktop layout for other reasons (viewport width, a quirk entry). The checkbox already names the before-and-after frames; keep them the evidence.
- Two weeks on, an agent bumps the ES pin for the scan page and forgets `tools/es-menu-map-check`; the map check fails in `vm-qa`'s `menumap` suite -- the guard exists (D-UI-039), nothing to add.

**Pre-mortem.** A month on, the maintainer's RG SP has saves in `/ROCKNIX/Saves` and the other two devices in `/Rasteratops/Saves`, and a game's progress forks across them. The review says: the move ran on the Nova while the RG SP was asleep on RC2, the RG SP woke, synced to the old folder for a week, and its later follow re-pointed it without moving the week's saves, because the old folder had been deleted. What we should have seen: the follow verb must not re-point a device whose old folder still holds files newer than the new folder's; it must offer the move (or a merge) instead. Second cause in the same review: the move deleted `/ROCKNIX/Saves-replaced/`, the set-aside folder of conflict losers, which nobody listed as "ours". Check: does `relocate` take the set-aside folder along? Today's `SAVES_EXCLUDES` excludes `/backup/**` and `/Backups/**` only; `Saves-replaced` sits beside `Saves`, not inside it, so the move leaves it in `/ROCKNIX` -- orphaned under the old name, never deleted, never read. Name it: #353 moves `Saves-replaced` beside the saves or says in the notes that the old set-aside stays where it was.

**Blindspot check.** 38 (a run that touched the maintainer's own cloud): every move runs on `vm-pair` first and on a device only on a yes asked by name. 51 (a stale checkbox): #349's superseded criteria were rewritten in the same action as the answer. 65 (a shim passing where the real thing fails): the sandbox shim answers `rcat` by writing a file; the real marker write is proven only in the round trip on the WebDAV. 69 (a page test kinder than a browser): the phone page's two-step Close is DOM code; it goes through the #330 load test and a real tap on guest d's WebKit. New candidate entry: *a state read from the configured folder alone, on a device whose cloud holds a different one of our folders* (the Nova case above) -- the same shape as blindspot 22's "a probe that cannot report absence", turned around: a probe that reports one absence and misses a presence next door. Entered if it recurs; named here.

**Replaced-mechanism archetype.** The startup-sync offer (`>>> offer create-saves-folder` presented by `GuiCloudTransfer`) is replaced by the setup step and the scan page. What it guarded: a fresh device whose cloud has no folder got asked at the first boot with the cloud reachable. The new homes: the sign-in flow's end (the player is there), the scan page (the player opened it), and the card's action line pointing at MANAGE CLOUD STORAGE (the player did neither). A device that signed in, declined, and never opens the pages keeps a card with an action line every boot -- which is the design (D-CLOUD-153's timing rule), and the notes say so.
