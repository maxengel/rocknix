Title: rocknix: the last good system.cfg, and backups without a sign-in

A system.cfg cut short by a power loss used to reset a device to defaults, because the file was backed up at every clean shutdown with whatever it held, so the truncated copy replaced its own good one. chksysconfig now writes the backup only from a file that has just been checked, and the verify at boot takes the live file, then the record, then the defaults, and says which it took. No shell writer completes a cut file any more.

backuptool writes tar.gz archives whole and renamed, holds back every Wi-Fi, account and cloud credential, refuses an archive in which a sign-in is still found, and keeps a way back from a restore; an interrupted restore is undone at the next boot. Before this, on-device backup and restore reported success while writing short archives and aborting on the first symlink. It also carries the shared settings functions, the boot autostart, run, factoryreset, the updater (a status returned, a download kept as .part until its checksum matches), setrootpass refusing an empty password, automount, the post-update hooks, and the shipped system.cfg, which now holds the keys later changes read; a device without those features ignores them.

I tested it with a harness that runs every shell path under the image's own busybox with the image's own files as fixtures (1,257 cases pass), an upgrade rehearsal that boots the previous image in a VM, seeds a player's state, updates in place and checks every piece survived (20 of 20), and a truncated system.cfg I constructed, which the record restored. On my RG35XX SP the case that started this no longer happens. Which files a backup holds is still the backup configuration's business, read as text and never sourced; the cloud tiers are the cloud changes'. No kernel, bootloader or device tree changes. It depends on the evidence change before it, whose recipe installs chksysconfig's unit.
