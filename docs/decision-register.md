# Decision register

The lookup table for decisions that shape the work but live nowhere findable —
maintainer calls, resolved forks, invalidated assumptions. Without this they sit
in issue comments and chat, and the next session re-derives, contradicts, or
quietly re-decides them.

**Append-only.** A reversal is a new row citing the old ID; never edit or delete
a decided row. Cite rows by ID (`D-…`) rather than re-arguing the choice.

See `.claude/rules/decision-register.md` for when to write and read rows.
This is the index of decisions; `docs/work-logs/` is the narrative,
`docs/blindspot-register.md` the catalogue of weaknesses.

| D-CLOUD-009 | 2026-08-29 | **The per-device cloud identity is seeded from the permanent hardware address, hashed, and stored in `/storage/.config`.** Supersedes the machine-id-only derivation in the first cut of #49. `ethtool -P` reports the address burned into the adapter, so MAC randomisation is irrelevant; hashing keeps a network identifier out of the cloud path; storing it means a wifi-module swap does not strand the backups and the file can be edited to adopt another device's folder. Chosen because a player's "my device" is the handheld, not the installation — so a reflash must find its own backups. | `cloud_device_id`, supersedes part of `b132442778` |

| D-CLOUD-010 | 2026-08-29 | **OAuth goes through rclone's own `authorize` flow, wrapped by a LAN page — one path for every backend, no provider-specific code.** Settles D-CLOUD-007: no device flow, no hosted callback, no registered client. rclone's `authorize` already runs the exchange; what it lacked was somewhere for a browser to be. The listener binds the LAN only while a sign-in is running, times out on its own, and is gated by a PIN shown on the handheld. Covers 19 backends rather than the 3 a per-provider design would have. | `f63c07c21c`, `cloud_oauth` |
| D-CLOUD-011 | 2026-08-29 | **The typed fallback asks for the PIN rather than carrying it in the address.** A bare address used to answer 403, so typing it in was a dead end unless you typed `?pin=7677` too. Ten wrong answers end the attempt; the QR still carries the PIN so scanning skips the prompt. | `deee4bbed5` |
| D-UI-003 | 2026-08-29 | **Steps that are carried out on the phone live on the phone page, not on the handheld.** The sign-in page cannot scroll, so its space is finite; the phone page has room and is where the redirect-that-fails actually happens. The handheld says only where to go. | `5d626a13e` |
| D-CLOUD-012 | 2026-08-29 | **There is no success page at the OAuth redirect, and there cannot be one.** The provider redirects the *phone* to `http://localhost:53682/`, which is the phone's own loopback; rclone's listener is on the handheld. The redirect URI is registered against rclone's provider app and cannot be pointed at the handheld's LAN address. Serving that page would mean registering our own OAuth client with a hosted callback, which D-CLOUD-001 rules out. Mitigated instead: the failure is described before the click, the paste box is the first thing on the page, and there is a real success page after the paste. | #51, `9612b34d24` |
| D-CLOUD-013 | 2026-08-29 | **The sign-in server outlives any one attempt, and the PIN belongs to the server.** rclone's authorize server answers exactly one redirect and then exits, and provider codes expire in about two minutes — so the ordinary failure ended the attempt and sent the player back to the handheld. A dead attempt is now replaced in place from the phone page. The PIN cannot be re-issued (the handheld is showing it, and a QR built from it), so it moved to the server. | `9612b34d24` |
| D-UI-004 | 2026-08-29 | **The paste box sits above the sign-in button, and the four-digit number is a PIN, never a "code".** Both from a real Dropbox test: the tester approved access, could not see where the address went, and by the time they found it the code had expired. Two things called "code" on one flow is what made it ambiguous. | maintainer, 2026-08-29; `f0af991f9` |
| D-UI-005 | 2026-08-29 | **One cloud entry, not two.** `SET UP CLOUD REMOTE` (the SSH wizard) and `CONNECT CLOUD STORAGE` (native) named the same job; the wizard is now `USE A COMPUTER INSTEAD` one level down, kept because rclone's own config is still the only way to build a crypt/union remote or reconnect a lapsed sign-in. The post-restore advice that named the old entry was updated in the same change. | maintainer, 2026-08-29; `Cloud: one way in` |
| D-UI-006 | 2026-08-29 | **The PIN lives in the address (`http://device:8080/7677`), not on a line of its own.** Only somebody typing the address rather than scanning the QR ever needs it, so displaying it separately was an extra number to read on a page that also asks for something it calls a code. `?pin=` is still accepted, for the prompt's own form and for an older QR. Supersedes the two-line layout in D-UI-004. | maintainer, 2026-08-29; `36b0d51861` |
| D-UI-007 | 2026-08-29 | **A placeholder must never look like a value.** `placeholder="http://localhost:53682/?code=..."` read as a filled-in form; the tester pressed the button on it and the sign-in stopped there. Placeholders on this flow say what to do ("Paste here"), never what the value looks like. | `36b0d51861` |
| D-WORKFLOW-002 | 2026-08-29 | **Adopt from the scaffold estate only where a local failure earned it.** Two of its 41 instruction cards were taken; `git-safety` was rejected because its headline advice (stash before destructive ops) is the one thing this environment forbids, the stash stack being shared across worktrees. | `a371bb77f8` |
| D-UI-008 | 2026-08-31 | **The on-screen keyboard raises itself when the caret lands in a text field, once per field, and the WebView keeps GTK focus throughout.** Auto-raise because a touchscreen handheld focuses a field by being tapped and one without does it by pressing A — neither is a moment to have to know that X exists. Once per field because re-raising a keyboard the player just dismissed, every half second, is worse than never raising it. Focus stays on the page and the d-pad is intercepted before the page sees it: keys that take focus stop the d-pad walking them after the first press, and a WebView that loses focus blurs the field, so the character goes nowhere. | maintainer, 2026-08-31; `cloud-signin-window.c` |
| D-UI-009 | 2026-08-31 | **L1/R1 scroll by running `window.scrollBy` in the page, not by sending Page_Up/Page_Down.** Those keys do nothing while a text field has the caret — which is most of a sign-in form, and exactly the moment the button below the fold is what cannot be reached. | maintainer, 2026-08-31; `cloud_oauth`, `cloud-signin-window.c` |
| D-UI-010 | 2026-08-31 | **One `RECOMMENDED` provider list and one `COMPLETE LIST`, not a split by sign-in type.** Splitting the shortlist into "sign in with your phone" and "sign in with an address and key" grouped providers by our mechanism rather than by anything the player is choosing between, and read as a hierarchy it was not — the second group was a handful of picks, not the rest of the catalogue. The tier now decides what happens *after* a provider is chosen. Restores the pre-`f0af991f9` wording. | maintainer, 2026-08-31; `082edc223` |
| D-UI-011 | 2026-08-31 | **The route is chosen up front — `ON THIS DEVICE` or `WITH MY PHONE` — and the phone is described as a keyboard, never as where the sign-in happens.** The sign-in opened onto the QR screen whichever way the player meant to work, so signing in on the handheld met a page about a phone and stopped there. The provider's page is on the handheld in both routes; the phone is one of two keyboards. Supersedes D-UI-003, whose premise was that the phone carried the sign-in. | maintainer, 2026-08-31; `082edc223`, `ea750c82d` |
| D-UI-012 | 2026-08-31 | **Button-bar spacing is `BUTTON_GRID_HORIZ_PADDING` = 0.022 of screen width, defined once, and button labels are one word.** These are separate fixes: `makeButtonGrid` centres each button in a column of `buttonWidth + PADDING`, so the gap equals the padding regardless of label length — terser labels shrink the buttons but never separate them. The old 0.0052 was 3px on a 640px panel, putting a destructive choice a thumb's width from a safe one. | maintainer, 2026-08-31; `es-native-ui.md` |
| D-UI-013 | 2026-08-31 | **The exit combination is Mode+Start where the pad has a Mode button, Select+Start where it does not, and the on-screen label is read from the hardware rather than written in the source.** Maintainer confirmed Mode+Start is what their fingers reach for on the RG35XX SP, which is also what ES maps its own hotkey to there. Hard-coding it would instruct RG351M and RG353M players to press a button they do not have. `find_gamepad()` already enumerated the pad's key capabilities; `exit_hint()` reports from them, reaching the window via `--exit-hint` and the ES page via `EXIT_HINT=` from `info`. Both combinations remain accepted everywhere. | maintainer, 2026-08-31; `c5f97fa31` |
| D-UI-014 | 2026-08-31 | **Both exit combinations are named on screen, the device's preferred one first** — `MODE OR SELECT + START` where a Mode button exists, `SELECT + START` where it does not. Refines D-UI-013, which named only the detected one: Select+Start already worked and is the convention players arrive with from other handhelds, so naming only Mode+Start told somebody pressing a working combination that it was not the way out. Mode is also not always labelled "Mode" on the shell, where Select and Start almost always are. | maintainer, 2026-08-31 |
| D-CLOUD-014 | 2026-09-01 | **A backup never deletes by default: `BACKUPMETHOD` is `copy`, and a chosen `sync` archives into a dated sibling instead of destroying.** One cloud folder is shared by every handheld, so a mirror makes it match whichever device ran last — it deleted 70 files, another handheld's whole save library, from the shipped upstream default (`9f1fab30f6`). `--backup-dir` must be a sibling of the destination; rclone rejects an overlapping one, verified against the real remote. | `cloud_backup`, this session |
| D-CLOUD-015 | 2026-09-01 | **A changed default is rewritten into existing configs when the old value is destructive.** `cloud_sync_helper` only appends keys it cannot find, so changing a default never reaches a configured device. `sync` → `copy` is rewritten on update with the previous file kept as `cloud_sync.conf.pre-copy-default`, following the `--verbose` strip precedent. Not offered, because somebody who does not want a mirror cannot learn they have one until their saves are gone. | `cloud_sync_helper` |
| D-CLOUD-016 | 2026-09-01 | **The cloud layout migration is offered, never automatic, and moves only the two folders we wrote.** `/GAMES` → `/ROCKNIX/Saves` + `/ROCKNIX/Backups`, server-side, refusing when the destination exists (a move into an existing directory goes file by file and could merge two devices' libraries). Config updated last. Where a player's saves live is theirs to decide — the carve-out in `upgrade-and-install.md` for a choice that is really the owner's. | `cloud_migrate_layout`, maintainer 2026-09-01 |
| D-CLOUD-017 | 2026-09-01 | **Savestates are namespaced by core, with the core build recorded in a per-device manifest rather than in the directory name.** Resolves #10's open question ("arch, chipset, or device?") — none of them. Structure churns permanently; a version in a manifest is data that can be compared and explained at reconciliation. Save files stay one shared pool. Pre-existing states are `unknown`, and consumers must handle that. | maintainer, [#10 comment](https://github.com/maxengel/rocknix/issues/10) |
| D-CLOUD-018 | 2026-09-02 | **The cloud content layout is `ROMs/` and `BIOS/`, not a mirror of `/storage/roms`.** The person filling it in is looking at a file manager on a computer, where `bios` sitting beside `snes` is an accident of how a handheld stores things. Seeding the 126 system folders was tried and rejected in testing — the maintainer looked at the result and still could not tell where ROMs went. Restore reads three shapes (ROMs/BIOS, the flat layout, the pre-`CONTENTPATH` root); backup writes only the first, so libraries migrate themselves. | maintainer, 2026-09-02; `d77d4ea44d` |
| D-CLOUD-019 | 2026-09-02 | **Content sync membership is an allowlist: a system EmulationStation declares, and not something another tier already owns.** It was a denylist — everything under `/storage/roms` bar four names — so `bezels`, `themes`, `music` and a stray `scummvm` folder were uploaded as game systems. Both halves of the rule are load-bearing: ES declares `screenshots` and `savestates` as systems, so the allowlist alone had content sync duplicating what the saves tier already keeps. Matched on `<path>`, not `<name>` — they differ for a dozen systems. | maintainer, 2026-09-02; `d77d4ea44d` |
| D-CLOUD-020 | 2026-09-02 | **Three tiers, by size and cadence: saves (frequent, small, automatic), content (large, static, explicit), system backup (occasional, zipped).** Anything in no tier is a gap to name, not an accident to leave — `/storage/roms/bezels`, `music` and `themes` are currently in none. They do not belong in the zip: it is rewritten and re-uploaded whole each time, which is why it suits small config and not large static assets. | maintainer, 2026-09-02 |
| D-CLOUD-021 | 2026-09-02 | **A backup-format change need not preserve compatibility with `.zip` archives.** Maintainer's call: cloud backup and restore were broken until this work fixed them, so there is no population of working archives to protect. Unblocks #58 (tar over zip, for symlink and permission fidelity — busybox `unzip` aborts a whole restore on a symlink, which has cost a restore here already). | maintainer, 2026-09-02; #58 |
