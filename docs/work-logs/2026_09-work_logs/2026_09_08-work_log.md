# 2026-09-08 work log

## 04:35 UTC — The RetroArch crash is a wrapper bug; patched here, reported and fixed upstream

Crash 3 on #79 came with a core dump: RetroArch 1.22.2's threaded video
wrapper has a single-slot command mailbox whose reply wait matches on the
command *type*, so the achievement badge upload (main thread) and the
automatic screenshot task (task thread) posting `CMD_CUSTOM_COMMAND` at the
same instant hand the video thread a `gl3_texture_cmd_t` on a returned stack
frame (`video_texture_load_wrap_gl3_mipmap`, `ldr x0,[x0]`).

- ROCKNIX: `0011-video-thread-wrapper-serialise-posters.patch` on
  `next` (`1c4fa3b308`) — a user-side lock held from send to reply. Linux
  has no same-thread re-entry into the wait, so a plain `slock_t` is enough.
- Upstream: libretro/RetroArch#19517 (report) and #19518 (fix on master,
  from `maxengel/RetroArch`). Master's rework still keeps one command
  outstanding and only asserts it in DEBUG. The master fix is a poster slot
  (`cond_user`, owner, depth) that is re-entrant on its owner and pumps
  the cocoa trampoline while waiting, because on Apple the reply wait can
  re-enter the wrapper on the waiting thread. Compile-tested release, DEBUG
  and `-std=c89`; a runtime result waits for the H700 build.
- Lesson: an upstream fix has to survive platforms the fork never builds.
  The first draft was the ROCKNIX lock verbatim; reading the `cond_reply`
  comment on master showed it would deadlock a macOS main thread.

## 05:25 UTC — #83 was a boot race, not a missing card; the guard now waits and re-checks

The maintainer asked how two cards that were never removed produced two
trees. The RG SP journal answered: udev starts `rocknix-automount` when the
card is detected (the unit is disabled, not in the boot transaction, so the
compositor's `After=` on it is inert); the script unmounts `/storage/roms`
at 23:48:57 and binds the card back at 23:48:58; the interface started at
23:48:57 and its boot restore at 23:48:58. A restore that got in first, or
that the bind landed under, wrote to the internal card.

- `cloud_saves_root check --wait 15` / `record IDENTITY` (`9618b63d7c`,
  D-CLOUD-055): the race is a delay, a mid-run flip is a failed run.
- VM lesson: a flip is simulated with a tmpfs *copy* bound over the tree,
  and the bind only lands mid-copy if rclone is throttled
  (`RCLONE_BWLIMIT`); two unthrottled attempts finished before the bind and
  looked like a passing post-check that had never run (blindspot 31's
  shape — the harness agreeing with itself).
- The ordering defect itself is ROCKNIX's; filed separately for its own
  review rather than riding this build.

## 06:10 UTC — #84: the cause was a card-enumeration race, not unit ordering

Corrected my own #84 diagnosis. Monotonic-time boot logs show
rocknix-automount finished ~10 s before EmulationStation on both
handhelds; the wall-clock journal that suggested the reverse was jumping
because the RTC set failed and NTP corrected the clock mid-boot. Lesson:
read boot ordering in monotonic time, never wall time, on a device whose
clock is set by NTP during boot (blindspot-shaped: a timestamp that jumps
under the events you are ordering).

Real cause: `automount`'s `find_games` scans for the external card once
and binds internal over /storage/roms if it has not enumerated yet. Fix
`accaadc3c0`: retry up to 15 s when the device expects an external card
(`system.merged.device=external` or pinned `system.gamesdevice`);
one-card boot unchanged. D-CLOUD-056. Tested on the VM against the real
function body with mocked blkid/dev-node — six scenarios. The udev re-run
already guards against tearing down a correctly mounted card
(`RESULT==""`), so no change there.

Must verify on the RG SP when it is back: `system.merged.device` is
`external` (or a games device pinned) so the wait engages there.
