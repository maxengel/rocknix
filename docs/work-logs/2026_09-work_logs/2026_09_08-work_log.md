## 04:35 UTC — The RetroArch crash is a wrapper bug; patched here, reported and fixed upstream

Crash 3 on #79 came with a core dump: RetroArch 1.22.2's threaded video
wrapper has a single-slot command mailbox whose reply wait matches on the
command *type*, so the achievement badge upload (main thread) and the
automatic screenshot task (task thread) posting `CMD_CUSTOM_COMMAND` at the
same instant hand the video thread a `gl3_texture_cmd_t` on a returned stack
frame (`video_texture_load_wrap_gl3_mipmap`, `ldr x0,[x0]`).

- ROCKNIX: `0011-video-thread-wrapper-serialise-posters.patch` on
  `next` (`1c4fa3b308`) — a user-side lock held from send to reply. Linux
  has no same-thread re-entry into the wait, so a plain `slock_t` is enough.
- Upstream: libretro/RetroArch#19517 (report) and #19518 (fix on master,
  from `maxengel/RetroArch`). Master's rework still keeps one command
  outstanding and only asserts it in DEBUG. The master fix is a poster slot
  (`cond_user`, owner, depth) that is re-entrant on its owner and pumps
  the cocoa trampoline while waiting, because on Apple the reply wait can
  re-enter the wrapper on the waiting thread. Compile-tested release, DEBUG
  and `-std=c89`; a runtime result waits for the H700 build.
- Lesson: an upstream fix has to survive platforms the fork never builds.
  The first draft was the ROCKNIX lock verbatim; reading the `cond_reply`
  comment on master showed it would deadlock a macOS main thread.

## 05:25 UTC — #83 was a boot race, not a missing card; the guard now waits and re-checks

The maintainer asked how two cards that were never removed produced two
trees. The RG SP journal answered: udev starts `rocknix-automount` when the
card is detected (the unit is disabled, not in the boot transaction, so the
compositor's `After=` on it is inert); the script unmounts `/storage/roms`
at 23:48:57 and binds the card back at 23:48:58; the interface started at
23:48:57 and its boot restore at 23:48:58. A restore that got in first, or
that the bind landed under, wrote to the internal card.

- `cloud_saves_root check --wait 15` / `record IDENTITY` (`9618b63d7c`,
  D-CLOUD-055): the race is a delay, a mid-run flip is a failed run.
- VM lesson: a flip is simulated with a tmpfs *copy* bound over the tree,
  and the bind only lands mid-copy if rclone is throttled
  (`RCLONE_BWLIMIT`); two unthrottled attempts finished before the bind and
  looked like a passing post-check that had never run (blindspot 31's
  shape — the harness agreeing with itself).
- The ordering defect itself is ROCKNIX's; filed separately for its own
  review rather than riding this build.

## 06:10 UTC — #84: the cause was a card-enumeration race, not unit ordering

Corrected my own #84 diagnosis. Monotonic-time boot logs show
rocknix-automount finished ~10 s before EmulationStation on both
handhelds; the wall-clock journal that suggested the reverse was jumping
because the RTC set failed and NTP corrected the clock mid-boot. Lesson:
read boot ordering in monotonic time, never wall time, on a device whose
clock is set by NTP during boot (blindspot-shaped: a timestamp that jumps
under the events you are ordering).

Real cause: `automount`'s `find_games` scans for the external card once
and binds internal over /storage/roms if it has not enumerated yet. Fix
`accaadc3c0`: retry up to 15 s when the device expects an external card
(`system.merged.device=external` or pinned `system.gamesdevice`);
one-card boot unchanged. D-CLOUD-056. Tested on the VM against the real
function body with mocked blkid/dev-node — six scenarios. The udev re-run
already guards against tearing down a correctly mounted card
(`RESULT==""`), so no change there.

Must verify on the RG SP when it is back: `system.merged.device` is
`external` (or a games device pinned) so the wait engages there.

## 15:40 UTC — #84 boot cost: wait only when a card is actually present

Maintainer asked whether the 15 s retry adds 15 s to boot. It does not —
a present card mounts on the first pass. Refined so the wait engages only
when a candidate external block node exists but its filesystem is not
readable yet (`external_node_present()` over /sys/block); a removed card
falls to internal after a 2 s grace, ceiling 10 s. `b82d19ab94`,

found bug A — run it anyway.

## 19:15 UTC — #21 fix pass: the merge, the race, and a gate that could not fail

Review of the capture slice found 22 things, five serious; all applied except
the two optional halves named below. What the serious ones were:

- **A PUT at a MOVE source was deleted with the source.** `cp -p state1
  state2` then new bytes at state1 is a move and a put in one pass; the merge
  computed `$dead = move.from − move.to` and deleted it after the reduce, so
  state1's new version vanished — and stayed unrecorded (no entry, mtime
  below the next `--started`). `$dead` now also subtracts put/meta paths;
  CAP7 carries the case.
- **Backgrounding the boot `--full` (D-CLOUD-064) made it a concurrent writer
  with the first game's exit capture**, and a discarded exit is not
  self-healing for a first version. The loser now re-runs itself once
  (`CLOUD_CAPTURE_RETRY=1 exec "$0" "${ORIG_ARGS[@]}"`; exec runs no EXIT
  trap, so `cleanup` is called by hand) for exit/rescan/retire; `--full`
  never retries. CAP11 stages the race with a `cloud_device_id` shim that
  rewrites the manifest on the `--label` call — the one sibling call between
  load and rename — and proves both the retry and the non-retry.
- **ES spawned capture for systems with no `<emulators>`** (tools, st-v):
  `--emulator ''` was a usage error, a capture-failures row per run. ES skips
  the spawn on an empty `launchedEmulator`; the producer treats it as nothing
  to record (rc 0); CAP9 asserts it.
- **The boot game (`launchStartupGame`) was a second exit path with no
  capture.** It now captures from the stored command's `-P`/`--emulator=`/
  `--core=` tokens; `launchArgument` moved to `es-app/src/LaunchCommand.h`
  (header-only, 9-assertion host test) and is shared with FileData.cpp.
- **CAP10(d) could not fail**: it compared line numbers, and the sync block's
  own toggle test sits above anything appended after its `fi`. It now
  resolves the enclosing `if` (depth-counted over `fi`, `else`/`elif` at
  depth 0 is a fail) and requires both toggles, `setsid|nohup`, `nice`, and a
  single trailing `&`. Proven against five constructed violations on the host
  before trusting the PASS.

## 20:05 UTC — #86: the shared device id was a constant seed; healed once, old folders kept readable

Both handhelds printed the hash `ee5013fc56` (RG SP `Anbernic-RG-SP-ee5013fc56`,
RG35XX SP `ROCKNIX-ee5013fc56`). The issue's investigation had the cause: on
every kernel with `CONFIG_IPV6_SIT=y` (H700, RK3566, RK3576) the sorted
interface list is `lo sit0 wlan0`, `sit0` was not on `usable_interfaces`'s
denylist, `ethtool -P sit0` → "Permanent address: not set" → the script's own
`sed`/`tr` → `notset`, and `permanent_address`'s three-value denylist accepted
it. `DEVICE` is never exported on a device, so the hash was
md5(`notset|unknown`)[0:10] on every one of them. The VM (sit a module, `eth0`
sorting first) never hit it.

Done on `feature/device-id-seed` (uncommitted, from `next` 208c6f9273):

- **`cloud_device_id`**: an interface counts only with `/sys/class/net/<n>/type`
  = 1 and a `device` link (the names `sit* ip6tnl* gre* wg* dummy* bond* ifb*`
  join the case for the reader, but do not decide); a seed only if it matches
  `^([0-9a-f]{2}:){5}[0-9a-f]{2}$` case-insensitively and is not all-zero or
  broadcast. **Hash recipe unchanged** (`hash_of`), `poisoned_hash` computes
  the constant from `notset`, and the comment that claimed the family joins
  the hash is corrected. A stored id ending in the constant is healed once,
  when a validated address is present: old id appended to
  `cloud_sync-device-id.previous` (no duplicates), `<label>-<hash>` written,
  `old -> new` to `logger -t cloud_device_id` and `/var/log/cloud_sync.log`.
  No address → returned unchanged; any other stored id → untouched. New
  `--previous`: `.previous` lines, `<label>-ee5013fc56`, `<hostname>-ee5013fc56`,
  deduplicated in that order.
- **`cloud_restore`**: own → `--legacy` → each `--previous` → root, logging
  which folder and why (WARN on a `--previous` folder — a same-model or
  same-hostname device may share it); `folder_has_archives` helper; a helper
  from before `--previous` existed answers with the current id, which the
  chain skips.
- **`cloud_backup`**: comments only — it already writes and trims only
  `device_dest`, and now says the old folder is never reached.
- **Harness**: `SOLO_FIXTURES` registry (one device + the QA endpoint,
  `--only A15`, no `--second-port`), `run_solo`, `--list` section. A15 sources
  the staged script minus its dispatch line in a driver of its own and
  overrides `usable_interfaces` there — no hook in the product. A11 untouched.
- **Docs**: changelog *The device id is seeded from a hardware address or
  nothing*, two earlier sentences amended; D-CLOUD-068; schema §7 example
  annotated and the `device.id` row; the `cloud_backup` device.json comment.
