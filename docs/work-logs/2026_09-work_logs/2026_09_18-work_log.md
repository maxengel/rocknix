## 04:10 UTC — Cached images are proved at write and swept in the background (#213 options 1+2); #214/#215 filed

Shipped #213's first two recommendations and merged them to `next` (`2e1df9d4dc`, `0d74ce702b`,
merge `ee851fbc50`); registered as D-RA-024.

**What changed.** Patch `013` makes `download_static_image` read the whole body, compare it with
`Content-Length`, and require the PNG magic plus a trailing `IEND` before the rename — so an
incomplete fetch leaves nothing behind and the next pass re-takes it. `raofflineproxy-cache-images
--verify` applies the same checks to what is already on disk, deletes what fails, and lets the
fetch phase that follows re-fetch it; `raofflineproxy-ctl` runs it on the **top-up** tail only
(the scan tail keeps the existence pass), and `images [--verify]` runs it by hand.

**Two defects in my own work, both found while proving it.**

1. *One shape for a path.* Stored bodies keep **media-host** URLs — the rewrite to the proxy
   happens on serve, not on store — and `extract_image_path` returns the path **with its leading
   slash**. So the fetch was building `https://media.retroachievements.org//Badge/….png` and the
   resume cursor was compared against a differently shaped string; a hand-written cursor made a
   run report `verified 0 of 9648 image(s) from 9648`. It worked only because the server tolerated
   the double slash and `download_static_image` lstrips for the target. Normalised to the
   extractor's shape everywhere.
2. *`--seconds` was read twice*, once for the sweep's deadline and once for the fetch's, so a pass
   handed the 300 s a top-up had left could spend 600. One budget now, the sweep capped at half.
   An unfinished sweep also exited 0 when nothing happened to be missing — reading as "nothing to
   do" with 2,319 files unexamined. It now names the count and where it resumes, and exits 1.

**Proofs** (guest d, 9,648 cached images, 202 games carrying images): three deliberately truncated
badges found, removed, re-fetched, second run `0 damaged` / `NOTHING_MISSING`; with the page cache
dropped so the sweep outlasts a 1 s ceiling, `verified 7329 of 9648 … 2319 image(s) left to verify;
the next pass resumes at /Badge/593335.png`, rc=1, and the next run came round at rc=0; offline
(RA hosts pointed at loopback) `images --verify` → `why NO_NETWORK`, rc=69. A warm full sweep of
those 9,648 files costs **458 ms**.

**Numbers worth keeping** for the cold-start question: **46.1 images per game** on average (median
35, min 1, max 505 — badge counts scale with a game's achievement count), **5,591 bytes** mean per
image, **6.56 images/s** with the pass's four workers, and **~6.1 s per game** for the sets phase.
The ceilings are `TOPUP_INTERVAL=1800`, `TOPUP_TIMEOUT=900`, `IMAGE_PASS_SECONDS=300`.

**Filed.** #214 (per-game manifest — #213's option 3, the maintainer asked for it to be tracked)

## 08:30 UTC — Correcting the cold-start numbers: the two hours are pacing, not bandwidth (#217)

The maintainer pushed back on the first-time-enable estimate. Re-measured, and two of the inputs
above are wrong.

- **The image rate was understated.** `6.56 images/s` had the store read folded into the clock.
  The real pass does **14.9/s** (907 images in 61 s against a cold store), so the image half of a
  494-game library is **34 min**, not 78.
- **Almost all of that is handshakes.** `download_static_image` calls `urllib.request.urlopen` per
  image, so each 5.6 KB badge pays a fresh TCP+TLS setup: **161 ms median fresh against 28 ms on a
  reused connection** (5.8x), and **83.6/s at 8 workers / 103/s at 24** with keep-alive per worker
  against 14.9/s today. Connection reuse at today's four workers puts the image phase at ~6 min.
- **The sets phase is throttle-bound, and the device figure includes hashing.** The client's
  `RA_MIN_REQUEST_INTERVAL_SECONDS = 0.3`, `SCAN_BATCH_SIZE = 50`, `SCAN_BATCH_COOLDOWN_SECONDS = 30`
  give a ~12 min floor for 494 games. Guest d's 04:00 periodic refresh did **25 games in 19.7 s =
  0.79 s/game** hash-free, against **6.1 s/game** on the RG SP's scan — so roughly 3-4 s per game
  there is ROM hashing, which `topup --after-index` already avoids.
- **The "two hours" is the cadence.** `IMAGE_PASS_SECONDS = 300` × `TOPUP_INTERVAL = 1800` means 34
  minutes of work takes seven passes over three and a half hours online. That pacing is right for
  keeping a warm cache warm and wrong for the one time somebody has just switched the feature on.

Filed #217 with the table and the strategy: reuse the connection, fill in the foreground once, use
the index rather than re-hashing, and leave the RetroAchievements API throttle alone — it is a
volunteer service and the courtesy is deliberate. That lands a first-time enable at ~20-25 min for
a 500-game library, nearly all of it the API throttle.

Lesson worth keeping: I quoted a rate measured through a wrapper rather than the code path, and
built an estimate on it. Measure the thing that will run.
