## 00:20 UTC — #196 confirmed on the device; the save-state hotkey's slot is #209 (read from the code, not yet fixed)

- Maintainer, on build 15 on the RG SP: *"The save state manager quit and auto-save did work as intended."* #196's device box ticked with those words. Their second half -- *"when I launched from a numbered slot and then tried to save with the RetroArch shortcut ... it didn't save it into the proper slot"* -- is #209.
- The chain, read end to end (no device: the RG SP stopped answering after the 20:32 reboot, so `/tmp/.retroarch.cfg` and `global.incrementalsavestates` from that launch are still owed): the interface passes `-state_slot N` and `-state_file` (`SaveState.cpp:97-157`, the launched slot since D-UI-057); `setsettings.sh:902` writes `state_slot = N` and `set_autosave` emits `-e N`; RetroArch's `command_event_set_savestate_auto_index` (`command.c:1912`, from `runloop.c:4349`) moves the slot to the highest existing one when `savestate_auto_index` is true, and the entry-slot block right after (`runloop.c:4391`, `4913`) puts it back to N -- so the launch is on the launched slot; then `CMD_EVENT_SAVE_STATE` increments *before* writing (`retroarch.c:3684`, `command.c:1894`), so the hotkey's save lands in N+1, wrapping to 0 past `savestate_max_keep`.
- So their guess was right for INCREMENT PER SAVE (the mode promises exactly that), and two real defects sit behind it: `set_savestates` maps only `0|false|none` to `savestate_auto_index=false`, while the interface writes `""` and `"2"` -- **DO NOT INCREMENT is silently ignored** (`setsettings.sh:859-871`, ROCKNIX's own since `9f1fab30f6`); and a legacy `global.incrementalsavestates=0` on an upgraded device shows INCREMENT PER SAVE in the menu while ES and the script behave as off, so the row lies (their "edge case from my own upgrade cycle" is a real state, though which one their device is in is unread).
- Also unseeded: `maxincrementalsaves` -> `savestate_max_keep` is written empty when unset, and a small value makes the increment wrap to slot 0 and prune the oldest, so "never overwrite old save states" is not literally true at the wrap.
- **Nothing changed in the product.** #209 carries the direction (one `case` line for the mapping, a decision on the legacy `0`, the max-keep seed) and five acceptance criteria, including the VM proof of both modes side by side. The maintainer asked to look in the code, so it stops here until they say to land it.
