## 03:40 UTC -- the maintainer's questions found a simpler architecture

Working the nine decisions one at a time, the maintainer stopped on "the
stage" and asked how a copy taken at exit could be safe if the emulator
might still be writing -- and caught a sentence of mine that was wrong as
worded. The precise answer (the emulator that exited is gone; the copy
guards against the *next* emulator during a long upload) led to the
better question: why allow a launch during the upload at all? Cancelling
a sync the player can see is counterintuitive. So: the launch waits, the
sync bounds itself to a few seconds and fails with a connectivity outcome
past that, never minutes, time-based bounds (D-CLOUD-109). With nothing
writing during the upload, the frozen copy of the new save has no job;
the stage is the last-agreed cache and nothing more (D-CLOUD-110).
Decisions 1-4 before it: D-CLOUD-105 (fleet setting; OFF keeps a
transaction copy -- the council's reading rejected), 106 (prune order,
the 90-day cap dropped), 107 (copy never move), 108 (the one fallback
fetch).

## 06:35 UTC — The QA cloud matrix: five backends, three defects WebDAV could not show (#133)

`tools/cloud-test-backend` grew `--backend webdav|s3|sftp|smb|ftp`
(`CLOUD_QA_BACKEND` still means the same thing), each on its own port so
several can be up at once: WebDAV 9010 unchanged, MinIO 9012, an
unprivileged `sshd` 9013, Samba in a container 9014, `pyftpdlib` in a venv
9015; 9011 stays the dead port. Nothing was installed on the host — the two
containers are images already pulled, the sshd is the system binary run as an
ordinary user with its own config, and pyftpdlib lives in a venv under the QA
cache that `up` creates if it is missing. `up`, `down`, `status`,
`rclone-conf`, `reset`, `ls`, `cat`, `put`, `seed-content` and `seed-device`
all work through the same abstraction, and the WebDAV path is byte-identical
to before apart from `rclone obscure`'s nonce (D-QA-018).

Two things the tooling had been getting from a name rather than from the
endpoint, both of which broke as soon as there were five (D-QA-019):

- **The shape of a remote path.** Three shapes among five: the folder *is*
  the path (WebDAV, FTP); the first component is a bucket or a share (S3,
  SMB); or every path is absolute (SFTP, because an sshd running as an
  ordinary user cannot chroot). `endpoint-prefix` states it. The harness had
  `if backend == "s3"` and a hard-coded `/QA-Custom`, which is a legal folder
  on Dropbox and an illegal bucket name on S3 — six checks failed for a
  reason that had nothing to do with the code under test.
- **Whether a remote carries a hash.** A14 asserted "non-null unless WebDAV";
  three of the five have no hash. `caps` reports hash/modtime/commit.

And the refused-cloud fixture had been made by sed-ing `url` or `endpoint`
onto a closed port — the address fields of two backends out of five. On SFTP,
SMB and FTP the sed matched nothing, the scan ran against a *working* cloud,
and the check that a refused cloud does not read as an empty one passed on a
cloud that was never refused. `dead-conf` now writes the refusing stanza from
the backend that knows which field carries its address.
