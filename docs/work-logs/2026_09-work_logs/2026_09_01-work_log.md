# 2026-09-01 work log

## 01:40 UTC — Pointer feel, and a keyboard that was disabled when it mattered

### "Nothing ever shows up in the box when I type"

Mine. The page set `box.disabled` from the status poll, so until the handheld
reported the sign-in page open the box could not be typed into at all — which
is exactly the window this flow asks people to use, because the QR sits on
the screen the sign-in page then replaces and can only be scanned first.
Re-asserting `disabled` every two seconds would also have dismissed a phone
keyboard mid-word.

It probably explains the paste report too: a disabled box has nowhere for a
paste to land either, so the device-side keymap was never at fault — every
character of `Tr0ub4dor&3!xZ_q%^*()` maps and sends, tested directly.

The fix needed **two strings, not one**: what is shown, and what has actually
reached the handheld. Conflating them made the send button compute an empty
difference and transmit nothing — the same symptom as the bug it was there to
fix. Caught by walking the states before building, not after.

### Pointer drift and the "magnetic" feel: one class of fault, two places

- libinput's default acceleration profile adapts to speed, so the same drag
  covers a different distance depending how fast it was. Right for a hand on
  a desk, wrong for a finger on a phone driving a screen it is not touching.
  Now `accel_profile flat`, `pointer_accel 0`, targeted by device identifier;
  sway confirms `accel_profile: flat, accel_speed: 0.0`.
- The page discarded the fraction left after rounding each delta. At sixty
  events a second that loses a little of every movement, and over a drag the
  pointer slides away from where the finger went. The remainder is carried
  now, and the 2.2x multiplier is gone — 1:1 with the finger.

### What made this round verifiable

The phone is the one surface this session cannot reach. Three rounds of phone
fixes went out unverified before it occurred to me that the page's JavaScript
can be lifted out and exercised in node against a stub DOM. `node --check`
first, because one syntax error kills every handler on the page including the
poll; then a harness driving the real handlers.

It proved all five behaviours the phone was supposed to have, including the
two I had just got wrong. Kept in `.qa-scratch/harness.js`; worth promoting to
a real tool if the phone page grows.

## 02:15 UTC — The sign-in never actually completed

A real attempt reached the end and was told it had not, then had to start
over. Not a UI fault: `_write_config` — which creates the rclone remote and
sets `status=signed-in` — was only ever called from `submit()`, the paste
path. With the page on the handheld, rclone's own server takes the redirect,
so nothing is pasted back, `submit()` never runs, and the token sat collected
in a daemon thread with no remote made.

So the on-device flow — the entire point of this work — could not finish a
sign-in, and every "success" for weeks was a success at reaching the
provider's page and nothing beyond it. The paste path worked, which is why it
was never noticed: that is the one that was tested.

The collector finishes the job now, and both callers are guarded against
creating the remote twice. Verified by feeding a Session rclone's real token
output through a stubbed process: token captured, `_write_config` called,
callback fired, and the second call short-circuits.

Finishing also closes the window, so the player is returned instead of being
left on rclone's own "All done. Please go back to rclone" — a sentence about
a program they have never heard of, on a screen whose only exit is a button
combination. B did nothing there because there was nothing to go back to.

### Pointer drift, again, and the actual cause

The previous round fixed acceleration and sub-pixel loss and it still drifted,
because the real cause was elsewhere: movement went through the same strict
promise queue as keystrokes. A finger produces about sixty events a second
and each request takes longer than that, so a backlog built and kept draining
after the finger stopped. Coalesced now — one request in flight, everything
else summed — while keystrokes keep the ordered queue, since for them order
is the point.

Measured in node: 60 touchmove events become 2 requests, never more than one
in flight, delivering exactly the 180x120 the finger travelled.

Lesson worth keeping: two rounds were spent on plausible causes of drift
(acceleration, rounding) that were both real and both insufficient. The third
was found by asking what happens to the *requests*, not to the numbers in
them.

Harnesses kept in `.qa-scratch/` — `harness.js` for the typing logic,
`pointer-test.js` for movement.

## 16:50 UTC — A backup deleted another device's saves

First successful end-to-end Dropbox sign-in, and then the backup that
followed deleted 70 files: another handheld's entire save library, from the
shipped default.

`rclone sync --delete-excluded /storage/roms/ -> dropbox:/GAMES/`. One cloud
folder is shared by every device — that is what makes it a library rather
than four backups — and `BACKUPMETHOD="sync"` makes it match whichever device
ran last. Upstream's default (`9f1fab30f6`), and it contradicts our own rule
that progress is preserved above all.

Recovered from Dropbox's 30-day trash by the maintainer; verified afterwards
as 70 deleted, 70 restored, lists identical, nothing missing or extra.

### What was wrong, in layers

1. **The default deleted.** Now `copy`.
2. **Changing the default reaches nobody.** `cloud_sync_helper` appends keys
   it cannot find and never rewrites one already written, so every configured
   device stays on `sync` for ever. It now rewrites it, keeping the old file.
   This is the "fixing forward is not enough" rule, and I nearly shipped the
   default change alone and called it done.
3. **A mirror is still available**, so it archives into a dated sibling rather
   than destroying. Sibling because rclone rejects an overlapping
   `--backup-dir` — found by running it, not by reading the docs.
4. **The layout was wrong too.** `/GAMES` with backups nested *inside* the
   saves folder, which is the path a mirror deletes from. The current default
   has been `/ROCKNIX/Saves` + `/ROCKNIX/Backups` since `b35c5832b1`; the same
   append-only helper meant no existing device ever moved.

### The migration

Offered, never automatic. Server-side, moves only the two folders we wrote,
refuses if the destination exists, config updated last.

Two bugs surfaced in the dry run against the real remote, neither visible by
reading the code: it wanted to move the backups into the middle of the saves,
and the fix for that recursed into the very subfolder it was testing and drew
the same conclusion. Then run for real: 70 saves and 1 backup moved, lists
identical, `/GAMES` empty.

A side effect worth noting: the restored saves were in `/GAMES/saves` while
`SYNCPATH` was `/GAMES`, so `cloud_restore` was looking at a root with nothing
in it. The migration made them visible again.
