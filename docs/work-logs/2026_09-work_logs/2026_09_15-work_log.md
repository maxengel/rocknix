## 00:40 UTC — #190: RETROACHIEVEMENTS hangs on PLEASE WAIT with Wi-Fi off (RG SP, RC-7); RC-9's first half

The maintainer, mid-test on the RG SP with Wi-Fi off: *"trying to launch Retro Achievements from the
main menu just gets stuck on 'Please Wait' while I'm offline."* -- *"It also isn't timing out."* Two
causes fit and the device's log will name it: the interface decided "online" from the proxy's state
file (rewritten only when the proxy's next probe fails, after the link drops) and asked the web with
no total timeout; and the device path over 247 saved games is 494 requests to a proxy that, while it
still believes it is online, tries upstream first with a 15 s timeout each -- hours on a dead link.
PL-09's VM proof had waited for the state file to say offline before opening the page (blindspot 44
again: the fixture's timing, not the person's).

RC-9 `122fdfd828` (ES `fix/offline-summary-hang` `6e0e89f3f`): `proxyOffline()` is true when no wired or
wireless interface has an address (the network watcher's own question; a VPN tunnel does not count),
and the three page requests are bounded at 15 s. On the VM both scenarios answer in 1.7 s -- but the
VM cannot show the hang: name resolution on its dead link fails at once, and QEMU's `set_link off`
leaves eth0's address in place (so the new check was not what answered; the instant DNS failure was).
The robust fix follows for RC-10: the interface asks the proxy for the store only (a header the fork's
proxy honours before it considers upstream), and a one-call `raofflineproxy-ctl summary` over sqlite
replaces the 494 requests. H700 RC-9 built and filed (`h700-all-20260914-122fdfd828`), not staged.
Lesson for the proof scripts: a "second change" timer measures nothing when the answer is in the first
screenshot; measure the frame that then holds still.
