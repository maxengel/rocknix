- **bwrap cannot make a mountpoint under a read-only bind.** `--ro-bind /usr

## 02:00 UTC -- #50: the shipped device name becomes the unit's own

`network-base-setup` (`d857ba04c9`, D-NET-002): a `system.hostname` equal to
the build family (or empty) is the shipped default, and at boot it becomes
`<FAMILY>-<four hex of cloud_device_id>` once, written back; any other name
is the player's and is left alone (D-NET-001). That rule *is* the upgrade
path -- an upgraded device still called H700 gets its own name at the first
boot of the image, a renamed one keeps its name. Run by hand on the three
guests: `GENERIC_X64` -> `GENERIC-X64-491f`, `-15ca`, `-0964`; a second run
unchanged; "Max Deck" untouched; empty -> suffixed. `last-good-scripts-test`

`avahi-daemon.service` has been commented out since the fork's first
commit with no reason on record, and nothing user-facing promises `.local`.

Two things met on the way:

- **`hostnamectl --transient` is refused on the image** ("static hostname is
  already set") because `/etc/hostname` is a symlink to
  `/proc/sys/kernel/hostname`, so systemd-hostnamed reads the *current*
  kernel name as the static one, caches it, and puts it back over whatever
  the script just wrote. At boot the echo lands first and hostnamed starts
  after it, so the boot path works by construction; a re-run without a
  reboot does not apply a changed name (seen on guest c). Not changed
  tonight; noted for the day it matters.
- **In a sandbox, put the shims on PATH after the profile**: `001-functions`
  prepends `/usr/bin`, so a shim directory exported before it loses to the
  host's real `logger`. Case m's "the log says so" check passed over an
  empty log until the order was fixed.

Not yet in an image: `878ec8863b` (built 00:42, the runner on it now)
predates this commit. The next x64 and H700 builds carry it; `vm-qa`'s
pair-identity suite gains "the two guests' hostnames differ and equal the
cleaned setting" once the runner has finished with the file.

## 02:40 UTC -- the device sometimes boots as ROCKNIX, and why (#50, second defect)

The pair-identity suite's new check (kernel hostname equals the cleaned
setting) failed on guest b of `878ec8863b`: hostname `ROCKNIX`, setting
`GENERIC_X64`. The boot journal in monotonic time:

| t | who | what |
| ---: | --- | --- |
| 1.87 s | systemd-resolved | using system hostname 'ROCKNIX' |
| 2.25 s | NetworkManager, via D-Bus | activates systemd-hostnamed |
| 3.21 s | network-base-setup | writes GENERIC-X64 to the kernel |
| 3.21 s | hostnamectl --transient | "static hostname is already set, so the specified transient hostname will not be used" |
| 3.21 s | systemd-hostnamed | "Hostname set to <ROCKNIX> (static)" |

`/etc/hostname` is a symlink to `/proc/sys/kernel/hostname`, so hostnamed
takes whatever the kernel is called when *it* starts as the static name,
and re-applies that cached name when it answers a hostname1 call. Our own
`hostnamectl --transient` was that call. Whether the device boots with the
right name depends on whether NetworkManager's D-Bus activation of hostnamed
lands before or after network-base.service; guest a won the race, guest b
lost it, and a handheld does the same. Reproduced by hand on guest b: with
hostnamed holding ROCKNIX, echo then `hostnamectl --transient` ends as
ROCKNIX; with hostnamed stopped, the echo sticks and hostnamed reads it as
static on restart.

`af9295025a`: `network-base.service` orders itself
`Before=systemd-hostnamed.service NetworkManager.service`, and the script no
longer calls hostnamectl -- the write is the whole job. `vm-qa` declares
`SSHO` (blindspot 40) and its pair-identity suite requires two names, each
equal to its setting; case m checks the ordering and the absence of the
call. The proof at boot needs an image that carries it; `878ec8863b` does
not, and the suite fails on it as it should. Related, not changed:
`avahi-set-host-name` logs "Daemon not running" on every boot, because the
responder is off (D-NET-003).
