## 02:40 UTC -- the device sometimes boots as ROCKNIX, and why (#50, second defect)

The pair-identity suite's new check (kernel hostname equals the cleaned
setting) failed on guest b of `878ec8863b`: hostname `ROCKNIX`, setting
`GENERIC_X64`. The boot journal in monotonic time:

| t | who | what |
| ---: | --- | --- |
| 1.87 s | systemd-resolved | using system hostname 'ROCKNIX' |
| 2.25 s | NetworkManager, via D-Bus | activates systemd-hostnamed |
| 3.21 s | network-base-setup | writes GENERIC-X64 to the kernel |
| 3.21 s | hostnamectl --transient | "static hostname is already set, so the specified transient hostname will not be used" |
| 3.21 s | systemd-hostnamed | "Hostname set to <ROCKNIX> (static)" |

`/etc/hostname` is a symlink to `/proc/sys/kernel/hostname`, so hostnamed
takes whatever the kernel is called when *it* starts as the static name,
and re-applies that cached name when it answers a hostname1 call. Our own
`hostnamectl --transient` was that call. Whether the device boots with the
right name depends on whether NetworkManager's D-Bus activation of hostnamed
lands before or after network-base.service; guest a won the race, guest b
lost it, and a handheld does the same. Reproduced by hand on guest b: with
hostnamed holding ROCKNIX, echo then `hostnamectl --transient` ends as
ROCKNIX; with hostnamed stopped, the echo sticks and hostnamed reads it as
static on restart.

`af9295025a`: `network-base.service` orders itself
`Before=systemd-hostnamed.service NetworkManager.service`, and the script no
longer calls hostnamectl -- the write is the whole job. `vm-qa` declares
`SSHO` (blindspot 40) and its pair-identity suite requires two names, each
equal to its setting; case m checks the ordering and the absence of the
call. The proof at boot needs an image that carries it; `878ec8863b` does
not, and the suite fails on it as it should. Related, not changed:
`avahi-set-host-name` logs "Daemon not running" on every boot, because the
responder is off (D-NET-003).
