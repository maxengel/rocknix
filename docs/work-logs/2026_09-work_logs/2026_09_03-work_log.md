
## A stamp is not a screen

The progress card closes itself when its job ends. That is correct for a
scrape and wrong for a 1.4 GiB restore, which is exactly the thing somebody
walks away from — and the maintainer did, came back to a sleeping handheld,
and had no way to tell whether it had worked. They had to ask.

The uncomfortable part: I had already been told this. The last-run stamps went
in yesterday *because* of the same complaint, and I treated them as the answer.
They are not. A row in a menu serves somebody who thinks to go and look; it
does nothing for somebody standing in front of the device when the surface
they were watching disappears. Necessary, not sufficient — and I recorded the
necessary half as though it closed the issue.

`GuiCloudTransfer` is the fix: backup and restore own the screen until
dismissed. Live line, a bar only where a real percentage exists behind it,
elapsed, then the outcome. Input refused while running (nothing to choose, and
a stray press should not dismiss a page somebody is waiting on); any button
after. Built on `GuiBackup`'s shape rather than a new one, because that is
already this codebase's answer to a long job with its own page.

The rule now has a fourth tier and a deciding column — **Ends** — because the
distinction that matters is not size or position but whether the surface
outlives the work. Duration picks between a card and a page.

### Two bugs the same session, both found by the maintainer

**BACK performed the action.** `GuiSettings::close()` runs `save()` then the
finalize hook, so a page using `onFinalize` as its "proceed" signal fires on
any exit. Pressing BACK on the system chooser started the restore. The fix
needed the proceed flag read *inside* finalize rather than after `close()`,
because close deletes the page along with the button closure currently
executing — blindspot 4, walked up to and avoided only because it is written
down.

**Content transfers never reported progress.** rclone writes periodic stats to
its log destination; with `--log-file` set and no `--progress` there is nothing
on stdout. The saves path has always passed `--progress`; the two content
scripts never did, so every content transfer since they were written was
silent to anything watching. The card showing "0 B / 0 B" while
`/var/log/cloud_sync.log` filled with "Copied (new)" is what gave it away —
the inverse of this subsystem's usual failure, which is reporting success
while doing nothing.
