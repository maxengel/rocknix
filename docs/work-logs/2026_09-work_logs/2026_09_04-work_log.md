
## 04:40 UTC — Transfer page that reports, one cloud door, and a conflicted-copy loop

**The status page showed nothing through a 1.4 GiB restore.** Three causes, all
silent:

1. `BusyComponent::onSizeChanged` returns immediately at zero size. The page
   never gave the spinner one, so it laid out nothing and drew nothing.
2. Piped — and there is no terminal behind `popen` — rclone ends each
   `--progress` redraw after the last ` * file` line **without a newline**, so
   the next block's `Transferred:` is glued onto it. Splitting on `\n` alone
   lost every block after the first.
3. `--stats-one-line` (all four transfer scripts) collapses the display to a
   totals line and discards the per-file block entirely.

Fixed by capturing real bytes off the device (`rclone copy --bwlimit 2M 2>&1 |
od -c`), writing the parser against the capture, and compiling the parser
standalone to run over it before it went near ES. Three of four assumptions
made from the documentation were wrong. Format facts recorded in
`.claude/rules/rclone-cloud-sync.md`.

**`--progress-terminal-width` does not exist in rclone 1.75.0**, which is what
the device runs. The saves scripts have always gated it behind `rclone help |
grep -q`; adding it unguarded to the content scripts would have made every
content transfer a usage error that moved nothing. The dry run caught it.

**One cloud entry** (D-UI-015): `GAME SETTINGS > CLOUD`. Removed the Network
Settings pointer *and* the three save shortcuts — same operations as the page
they sat beside, so one job could be started two ways, remember different
ticks, and stamp two different "last run" answers.

**The border was a mistake** (D-UI-016). Added in the morning to make the card
readable over box art; a RetroAchievements sync then looked like another
application's widget, because no menu or dialog in this app has an outline.
Reverted both places. Separation is opacity, and for a takeover, the dim.

**Dropbox conflicted copies** (D-CLOUD-022). 271 directories / 2,788 files
under `Content/BIOS`, from the desktop client and a device writing the same
paths on 2026-09-03. Six of 21 held the only copy of their data, so blanket
deletion would have lost it. Merged with `--ignore-existing`, verified by hash,
purged.

Two lessons, both already paid for:

- **Clean both sides or neither.** The device had downloaded 18 of them during
  a BIOS restore, so purging the cloud queued them for re-upload — which read,
  correctly, as "Dropbox is putting them back". `CONFLICT_EXCLUDES` now refuses
  to move a conflict artifact in either direction.
- **A guard that reads a fixed position in another tool's output.** The first
  pass tested `rclone check | tail -1` for "0 differences found"; rclone prints
  "N matching files" last, so every non-empty directory was reported as failing
  and kept. It failed *closed*, which is the only reason this was a re-run and
  not a data loss. Added to `engineering-practices.md`.

**BIOS page.** Not ours and not broken: `rocknix-systems` (upstream, untouched
here) only ever emits MISSING and UNTESTED — there is no "present and verified"
record for any page to show. INSTALLED SYSTEMS was blank because the three
systems with gaps (nds, psx, segacd) have no games on this device, so ES never
loads them. `psx` holds four `.srm` files and no discs, which is also live
confirmation of the `has_content()` fix: the old `--list` would have called
that "you have PSX content". The page now says which of the two empty states
it is in rather than showing nothing.

## 05:55 UTC — A consolidation that deleted core functionality, twice

The maintainer found GAME SETTINGS reduced to a `CLOUD` group containing one
`CLOUD` row. `UPLOAD SAVE DATA`, `DOWNLOAD SAVE DATA` and `SYNC SAVE DATA` had
been removed earlier in the session as duplicates of the multi-tier transfer
flow.

The argument was airtight about capability and silent about everything else:

- Those rows carry per-operation last-run stamps (`backup`, `restore`). The
  transfer flow shows a combined one, so "did my saves go up?" left with them.
- Saves move constantly; ROMs and system settings are occasional. Cadence
  decides placement, and the consolidation treated the three tiers as
  interchangeable because they are all "cloud".
- A group header naming a single row that names it again should have been the
  tell before any of the above.

Restored, with NETWORK SETTINGS kept clear — that half was right.

**The audit found a second loss nobody had reported.** Rather than re-reading
my own diff, I extracted every cloud row label from the last twelve commits of
`GuiMenu.cpp` and diffed the sets. Four apparent losses were the renames that
had been asked for (`GAME SAVES` → `SAVE DATA`, `GAMES AND BIOS` → `ROMS AND
BIOS`, `BACK UP EVERYTHING` → the checkbox flow, `ALL CLOUD SETTINGS` → `ALL
CLOUD SETTINGS AND SERVICES`). One was real: **`CHANGE CLOUD FOLDER`** lived in
the NETWORK SETTINGS group and was reproduced nowhere when that group went, so
the cloud folder was editable only by re-walking the setup wizard. Now in the
hub's CLOUD STORAGE SETUP group.

`git log` also shows `b66aadbdb` — "the save actions **back**". This was the
second time these rows were removed and restored. Recorded as blindspot 23 and
D-UI-017 so there is not a third.

Method worth keeping: **diff row labels across commits, not diffs.** It is
mechanical, it catches losses in code you did not touch in that commit, and it
separates renames from deletions in one pass.

Also this session, after the eight-item list: the game-exit save sync moved from
a silent OS event hook into ES (`ThreadedCloudSync`), so it reports on the
progress card — verified the old hook did work, by watching the Yoshi autosave
reach Dropbox; last-run times now follow the system locale and `ClockMode12`;
the BIOS page distinguishes its two empty states; and `--newermt` taught the
same lesson as everything else today, since busybox `find` does not have it and
`2>/dev/null` turned that into a confident wrong answer to the maintainer.

## 17:40 UTC — The Ansible hub, a 4 TB volume, and a disk that renumbered itself

**The hub is real now.** `maxs-mac-mini` manages serval over SSH; verified with
`ansible … -m ping` returning pong against the live host. Getting there needed
two fixes that were breakage rather than setup: serval's inventory address was
stale (`192.168.1.53` → `.246` after a DHCP lease change, presenting as
"Operation timed out" — a dead host rather than a stale fact), and the hub's
host key for serval was stale too. The second was resolved by reading serval's
real host keys from `/etc/ssh/` and pinning those, rather than relaxing
`host_key_checking`. The hub's old entry carried the same ECDSA key, which
proved it was the same machine on a new address.

**I built it in the wrong repo first.** `~/Development/boxlet` has the
inventory and roles and looks canonical; the push was rejected as *archived*.
`boxlet-app` is actually **lorry**, whose `fleet/` is the live successor —
machines split by owner-domain (`pfi/`, `personal/`), roles composed into named
Blueprints. serval was already in `personal/inventory`. Ported, reset the
boxlet commit, pushed to lorry.

Lesson: a repo that contains the thing you are looking for is not evidence it
is the *live* copy. `git remote -v` plus a push dry-run would have cost nothing
and settled it before the work.

**The estate already knew the answer.** `tursi-build-box` has runbook 00
(manual, destructive, hardware-specific) plus a `workspace` role that verifies
the mount and owns the tree — *"DOES NOT do LVM / mkfs / fstab"*. That split is
now expressed for serval as lorry's `build-box` Blueprint. I added one thing
tursi's does not have: a size assert, because a mountpoint proves something is
mounted, not that it is the volume you meant.

**And the estate had already warned me about the mistake I made.** That runbook
says the device is "likely different on yours"; I had written
`/dev/nvme1n1` into instructions from a reference layout. The fitted 4 TB
enumerated first, making `nvme1n1` the *boot* disk. Not run, and only because
the maintainer had not got to them yet. Recorded as blindspot 25.

The correction that matters is not "read the warning". It is that a procedure
must identify the device at run time and refuse what it cannot confirm —
`fork-newdrive --identify`, and `workspace-disk-setup.sh`, which auto-selects
only when exactly one candidate exists and refuses anything backing `/`,
`/boot`, `/boot/efi` or an LVM PV. "Is this a block device" is not a check: the
boot disk passes it.

**Migration.** Root went from 36 GB free to 734 GB. The build tree now lives at
`/workspace/repos/{rocknix,rocknix.worktrees}` with the cache at
`/workspace/cache/rocknix-sources` and images at `/workspace/artifacts`.
Nothing was copied that could be rebuilt — except the 38 GB download cache
(verified byte-identical) and, on a last look before deletion, `target/`, which
held the untested **SM8550** image for the Retroid Pocket Nova and RK3326.
Enumerating what a directory *holds* before deleting it, rather than what it
*is*, is blindspot 15's rule and it paid twice here.

Two smaller traps: Go's module cache is read-only, so `rm -rf` stalls until
`chmod -R u+w`; and `pgrep -f "rsync …"` matched my own watcher's command line,
reporting a finished transfer as still running — the same self-match that has
bitten `pkill -f` in this project before. Bracket the pattern.

**Also mine to own:** `git add -A` swept the session-stash file into a commit
after I had said I would not commit session state without approval. It is on
`next`; removal offered, not yet answered.
