# 2026-09-11 work log

## 05:40 UTC — #125: the walks wait on frames now

Delivered fork #125 on `feature/walk-tooling`, against guest b of
`tools/vm-pair` (build `88b82d94a7`, 640x480).

**What changed.** `tools/vm-visual-qa` has four new steps — `settle`,
`wait-for-change`, `wake`, `dismiss-dialogs` — that compare framebuffers
instead of counting seconds, and every `.steps` file is rewritten on them.
`tools/vm-qa` replays compositions from a new `tools/vm-walks/suite.txt`
and takes `--guest b`. `tools/vm-pair up` polls for SSH for 300 s instead
of trying once. `tools/cloud-round-trip` loads vm-visual-qa as a module so
KILL13's walk interpreter shares one set of thresholds.

**The thresholds are measured, not chosen.** On this guest the carousel's
clock ticking a minute moves 0.00028 of the screen and a toggled switch
moves 0.0020 — a factor of seven apart, and both under a quarter of a
percent. A band picked by eye would have sat above the switch, which is
the single case #125 names first.

**Three things this found that nobody was looking for:**

1. `wait-for-change` can be satisfied by the *tail of the previous
   transition* if the pre-press frame is captured from a screen still
   moving. An A press on ROMS AND BIOS was eaten, the row highlight from
   the `down` before it was still fading, and the step read it as landed —
   the exact failure the step exists to catch, reproduced by the step
   meant to catch it. Fixed by settling before capturing.
2. `to-change-cloud-folder.steps` had gone stale: CHECK CONNECTION joined
   CLOUD STORAGE SETUP above CHANGE CLOUD FOLDER, so six downs ran the
   connection check. Found on the first suite run, by the walk failing on
   the press that stopped landing rather than by four wrong frames.
3. The runner replayed each `.steps` file on its own from a rebooted
   guest. Nine of the thirteen are a *leg* that starts on a screen an
   earlier leg reaches, so they pressed A into the carousel and drove
   whatever game list was under the cursor — and the suite passed, because
   it counted frames.

**One wrong turn worth recording.** The transfer page's ROMS AND BIOS
switch correlated twice with the saved system selection, so I wrote that
down as the mechanism and built a precondition on it. It was coincidence:
the switches are ES settings in
`/storage/.config/system/configs/system.cfg` — *not* the
`/storage/.config/system.cfg` the rest of the harness talks about, which
is why two searches missed them. Found by touching a marker, closing the
page through the UI, and asking the guest which files were newer. Two
correlations is not a mechanism; the file listing was thirty seconds away
and would have been right the first time.
