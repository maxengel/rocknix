## 05:20 UTC — #124: the transfer lock outliving its run

**What it was.** `take_cloud_lock` does `exec 9>/var/run/cloud_sync.lock;
flock -n 9`. A shell redirection carries no close-on-exec, so fd 9 reached
every child. Watched in `/proc` on VM guest a: `rclone` holds the lock for
the whole of a transfer. An exported-function shim over `rclone` (the
`sh -c` inside it is a real exec'd child) counted **4 of 4** invocations in
`cloud_backup` and **6 of 6** in `cloud_restore` inheriting the descriptor;
the two content scripts leak it too.

**Why the acceptance loop passed anyway.** Bash waits for every child it
starts — pipelines and command substitutions included, verified locally —
so by the time the shell exits each holder is a zombie, which holds no fds.
`cloud_backup --yes --saves-only; flock -n` ran **0 failures in 100** on the
shipped scripts, and so did `--system-only`, `cloud_restore`, and the piped
form ES uses.

**The reproduction that does fail.** SIGKILL the script's shell while rclone
is copying (a `--bwlimit` and a 16 MiB save make the window): rclone carries
on with ppid 1, holding the lock, and the next `cloud_backup` exits **75**,
"Skipped: another cloud sync is already running" — with nothing running. Note
SIGTERM does *not* reproduce it: bash defers the INT/TERM trap until the
foreground rclone returns, so the script stays alive and the lock is
legitimately held.

**Fix.** The body runs with fd 9 closed — `main 9>&-` in `cloud_backup` and
`cloud_restore`, a brace group at the foot of `cloud_content_backup` /
`cloud_content_restore` and around the rest of `match_run`. Bash saves the
descriptor to one of its own, which it *does* mark close-on-exec, so the
shell still holds the lock and a concurrent run is still refused. A brace
group, not a subshell: exits, traps and variables are untouched. The refusal
also retries up to a second (belt and braces). After: 0/4 and 0/6 on the
probe, lock free the instant a killed shell dies, 0/100 on the loop, and a
concurrent run still refused (after 1011 ms instead of 5 ms).

**Lesson for the harness.** The step that met this waited ten seconds for the
lock to fall free. A wait turns a defect into a delay and reports nothing. It
is now two assertions, and the one that actually fires on the unfixed code is
the descriptor probe, not "is the lock free after a run" — that one passes on
broken code 100 times out of 100. Same shape as the "assertion that only
holds because nothing had happened yet" in `engineering-practices.md`.

Commits `65d7cf6c24`, `c2eddec7b0`. Decision `D-CLOUD-093`.
