# 2026-09-02 work log

## Device-testing round: copy, contrast, and an operation that never said how it went

Three findings from the maintainer testing the 20260902 H700 image, all fixed
and committed; none of them are in that image.

### Copy sweep

Every list on the cloud screens was missing its serial comma, and "states"
was doing duty for two different files. Fixed across ten strings, and written
down as three conventions in `.claude/rules/es-native-ui.md` so it does not
drift back:

- serial comma, always;
- a battery save is a **game save**, a machine snapshot is a **save state**,
  and bare "saves" is only acceptable where nothing contrasts with it;
- **Wi-Fi** hyphenated in user-visible text, whatever the settings key is
  called.

The sweep was mechanical once the strings were extracted from the diff against
the upstream merge base — that is the right way to find "screens we created"
without grepping the whole app and grading upstream's copy.

### The progress card blended into the game art

`AsyncNotificationComponent` drew itself at 200 of 255. Every other themed
surface — menus, dialogs, `GuiInfoPopup` past its fade-in — draws at full
opacity and lets the theme decide how solid to be, and the shipped theme's
menu background is an opaque `0x111111`. So the card was the single exception,
and at 200 roughly a fifth of the box art behind it came through: a progress
line on a smear that changed with the artwork. Now 255, via a named constant,
which is a standardisation rather than a new choice. `frame.png`'s corners
fade to nothing, so it still reads as a card.

Worth noting how the answer was found: not by picking a nicer number, but by
asking what every other surface does. There was a standard; this component was
outside it.

### "I walked away and have no idea whether it worked"

The real one. A cloud operation reports itself twice — a progress card while
it runs and a toast when it ends — and both are gone within seconds. Starting
a backup and walking away is the *normal* way to run a backup, and coming back
to a screen that has never heard of it left `/var/log/cloud_sync.log` as the
only record, at a path no player has been told.

Fix in two halves. The backends (`cloud_backup`, `cloud_restore`,
`cloud_content_backup`, `cloud_content_restore`) stamp when they finished and
with what code, on every exit path including the interrupt trap. The menus
read it back: LAST UPLOAD / LAST DOWNLOAD under CLOUD SAVES, the content pair
under CLOUD TOOLS, LAST BACKUP / LAST RESTORE on BACKUP/RESTORE SYSTEM DATA.

Two decisions inside it worth keeping:

- **The scripts stamp, not ES.** ES knows the exit code of everything *it*
  starts, which was the tempting shortcut. But sync-on-startup and
  sync-on-game-exit run the scripts directly, and those are exactly the runs
  somebody would want a record of, having never watched them. Recording from
  the caller would have produced a status line that silently ignored the
  automatic syncs.
- **`/storage/.cache`, not `/storage/.config`.** A stamp under `.config` gets
  swept into the settings backup, and restored onto a second device it would
  describe a run that device never made. Device-local state belongs with the
  other device-local state.

Exit 130 — the backends' own interrupt trap — reads as "stopped before it
finished" rather than failure. Nothing broke, and the person who stopped it
knows that already.

Also folded in: the retention sort fix found during the Dropbox cleanup, where
an undated `ROCKNIX_BACKUP.zip` sorted above every `2026_…` name (R after any
digit), held a keep-slot for ever, and got newer archives pruned around it.

### Small thing that would have cost a build

`Utils::Time::timeToString` is a hand-rolled formatter, not `strftime`: it
knows `Y y m d H I p M S` and silently drops anything else. `%d %b %Y` would
have shipped a date with a hole in it. Numeric and big-endian is the better
answer anyway — it reads the same in every locale and matches the names the
archives are written under, so a row in the menu and a file in the cloud
folder are recognisably the same run.

Syntax-checking the three changed files against the existing build tree's own
compile flags (pulled out of `compile_commands.json`, include paths repointed
at the ES worktree) caught it in seconds. Worth doing every time before a bump
— a full image build is the wrong place to discover a typo.

### Not in this round

The IA consolidation (one cloud page asking what you are backing up, replacing
the split between GAME SETTINGS > CLOUD TOOLS and NETWORK SETTINGS >
BACKUP/RESTORE) remains a separate change, as agreed. These three fixes are
committed and the ES pin is bumped, but no build has been started — the
maintainer is still testing 20260902 and more findings are likely.

## Progress card: what the gamelist update actually does, and what we took from it

Follow-up to the contrast fix. The maintainer remembered the "update
gamelists" progress as a full-width overlay and asked whether there was a
full-width pattern worth adopting.

It isn't an overlay. `ViewController::reloadAllGames` puts up `Splash`
(`es-core/src/Splash.cpp`) — the same surface as boot and game launch — which
fills the whole screen, centres a logo and text, blocks input, and draws a
progress bar at **half** the screen width. So the remembered "full width" is
full *screen*, and the progress element inside it is narrower than our card
was. Different category: a modal takeover for work that has stopped you doing
anything else, not a wider version of a non-blocking card.

The survey that came out of it, now a table in `es-native-ui.md`:

| Surface | Width | Position | Blocks |
|---|---|---|---|
| `Splash` | full screen; bar 0.5W | whole screen | yes |
| `GuiInfoPopup` | fits text, capped 0.9W | top, centred | no |
| `AsyncNotificationComponent` | was 0.62W | top-right | no |

### The thing the survey turned up

One cloud backup showed **two** surfaces: the 0.62W card top-right while it
ran, then — the instant it finished — a `GuiInfoPopup` with the outcome, a
different shape up to 0.9W, centred. It changed shape and jumped across the
screen at precisely the moment you were looking for the answer.

That mattered more than the width. Fixed by collapsing to one surface: the
card that reported the transfer now says how it went, holds it five seconds,
and fades. No second component.

### Width and placement

Maintainer's call, and the right one: past half the screen, "not quite full"
is the worst of both. Went to 0.9 — `GuiInfoPopup`'s existing cap, so it is
adopting a ceiling rather than inventing a number — and centred, which is
where the message that follows it already appeared. Appearing now fades in
place; the old slide came in off the right edge, which only reads as motion
for a card anchored there.

Consequence to watch on the device: the scraper, hasher, bluetooth pairing,
content installer and OS updater share this component and all move with it.
That is intended — one progress shape, one place — but it is five surfaces
changed by one edit, and only cloud sync has been reasoned about.

### Detail worth keeping

`ThreadedCloudSync::mInstance` is now cleared when the work ends rather than
when the object is destroyed, so the five-second hold does not tell somebody a
sync is still running or block a game launch. The clear is guarded on identity
(`mInstance == this`) because another sync can claim the static during those
five seconds — and the old code's unguarded `delete this; mInstance = nullptr;`
wrote through a freed object anyway.

## The migration split the ROMs from the saves, and nobody noticed for a week

Went to seed cloud folders on the maintainer's H700 and found its config in a state no
test covers:

```
SYNCPATH="/ROCKNIX/Saves"        <- migrated
SYNCPATH_BACKUP="/ROCKNIX/Backups"  <- migrated
CONTENTPATH="/GAMES/Content"     <- left behind
```

`cloud_migrate_layout` updates the first two and not the third. So a migrated device
keeps its ROMs in a namespace its saves have left — and once the empty `/GAMES` was
tidied up (which this session did, on 1 Sep), any content listing returns
`directory not found`. Content restore would have found nothing, on a wiped handheld,
in the exact scenario we are about to test.

The sharp part: `cloud_sync_helper` **derives** `CONTENTPATH` from `SYNCPATH`
specifically so ROMs and saves share a namespace. Its comment says a split is "worse
than either layout alone". The migration then produced precisely that split. Two pieces
of code with correct individual reasoning, and the seam between them is where the defect
lived.

Fixed in `6717e0b348`. Content moves with the rest when the pointer is one we derived;
an owner-chosen path is named and left alone; a device that already migrated is repaired
rather than told it is current, because *that state is what every early migration left
behind* — the already-migrated early return was itself part of the bug.

Six cases against a mocked remote, including the dry run leaving the config untouched.

### Two process notes

**The build script lied.** The SM8550 resume failed on `mame2015-lr`, and the harness
reported **exit code 0** — because the script's last line was a `df` whose status is
always zero. Only checking `target/` for an image caught it. *Verify the artifact, not
the report*, applied to our own tooling this time. Script now exits non-zero.

**A killed parallel build leaves poisoned objects.** `mame2015-lr` failed to link with
`undefined reference to T11` — while `obj/emu/cpu/t11/t11.o` sat right there on disk.
The first run was SIGTERMed with that package in flight, leaving archives built from an
incomplete object set; the resume compiled the missing objects but never re-archived.
H700 and RK3566 both build the same package fine, which is what ruled out the code.
Clearing that one package's build dir and stamp was the fix — the targeted version of
the libtool lesson already in `device-builds.md`.
