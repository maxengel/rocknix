# Work log — 2026-08-26

## The system-backup phase of cloud sync never restored anything

Went through the legacy `cloud_backup`/`cloud_restore` (621/664 lines) while
waiting on hardware. Started from the one invariant the rules state — that the
two scripts stay structurally in sync — and diffed their shared functions. The
helpers were identical; the drift was all in the phase-2 code, which is where
the bug was.

`cloud_restore`'s system-backup phase filtered on `/backup/*.zip` and
`backup/*.zip`, but that transfer's root is `SYNCPATH_BACKUP`, whose contents
came from `BACKUPFOLDER` — so the archive is at the root, not under `backup/`.
Neither include matched. Because using `--include` at all excludes everything
it does not match, the transfer moved no files, exited 0, and the summary
printed SUCCESS. Shipped in four images. Reachable only for users who set
`BACKUPFILE_RESTORE_OPTION="yes"`, which is off by default.

The backup side had the same mistake with no symptom: it borrowed the saves
allowlist through `RESTORE_RCLONEOPTS`, whose rules are anchored to
`BACKUPPATH` while that transfer's root is `BACKUPFOLDER`, and whose
`- /**/*.zip` matches the archive. It worked only because rclone applies
`--include` ahead of `--filter-from`. A precedence detail was the only thing
holding it up.

**Method worth repeating:** rather than reason about rclone's filter
precedence, I built a fixture tree and asked rclone. That settled four
questions in one pass and caught two excludes that had never matched anything
(`"${BACKUPFOLDER}/**"` is absolute where rclone matches relative to the
transfer root; `backups/**` names a directory that does not exist — it is
`backup`). Then I ran the real scripts end-to-end against the WebDAV test
backend by relocating `/storage` into a scratch tree, and ran the **shipped**
script alongside the fixed one: 4 saves / 0 archives before, 4 / 1 after.
A before-and-after on the real code is what turns "I think this was broken"
into evidence.

Also fixed: `--system-only` was parsed and ignored by `cloud_restore`, so it
restored game saves over local ones — the opposite of the flag. "Nothing to
transfer" returned 1 in both system phases and printed COMPLETED WITH ERRORS on
a device that had simply never made a backup. `check_internet` pinged
google.com, which fails for a self-hosted or LAN remote and passes when the
user's provider is down; it now tests the configured remote.

One claim I had to retract mid-work: I asserted in a comment that nesting
`SYNCPATH_BACKUP` inside `SYNCPATH` makes each backup delete the previous
archive. Testing it showed a full run re-uploads moments later and hides it.
The real hazard is narrower — a `--saves-only` run deletes the archives and
puts nothing back — so the comment and the new warning say that instead.

The suite never covered phase 2, which is why this lived. `cloud-round-trip`
now round-trips the archive, and `cloud-test-backend` reports `syncpath-backup`
as a sibling of `syncpath` (the driver had nested it, which the shipped
defaults do not).

## backuptool, and consolidating every branch onto next

Reviewed the hardened `backuptool` (the six commits that had been sitting on
`feature/backuptool-baseline`, merged into the test branches but never into
`next`, so `next` had been building without them). It is in good shape —
regular files only, credential stripping, an archive self-check, rotation, the
restore-finished marker. Two things left.

**The interaction only existed once both branches were together.** `backuptool`
now rotates old backups into `BACKUPFOLDER/archive/`, and its comment says that
folder dodges the cloud allowlist. True of phase 1 — but phase 2 does not use
the allowlist, it matched `*.zip`, and an unanchored rclone pattern matches at
any depth. Every rotated archive was being uploaded on every sync. Anchoring to
`/*.zip` fixes it. This is a good argument for the consolidation itself: neither
branch was wrong alone.

**Sanitize-after-the-fact still writes the secret.** `backuptool` zipped the
real `system.cfg`, `es_settings.cfg` and `retroarch.cfg`, then overwrote each
with a sanitized copy. End state clean, but the populated secret hits the
archive first and an interrupted backup leaves it there. The three files are
now held back and only sanitized copies are ever written. That also fixed a
smaller bug — the sanitized copies were added whenever the file existed, so a
user with custom `LOCATIONS` excluding one got it in their backup anyway.

I could not test Info-ZIP's replace semantics (no `zip` on this host), so I did
not claim the old approach left recoverable bytes. The ordering argument stands
on its own.

**Consolidation.** Merged `feature/backuptool-baseline`, `feature/cloud-saves`
and `test/qa-generic-x64` into `next`. All three merged clean, and none
resurrected the retired Copilot files (checked the merged trees before
committing, since two of those branches predate the retirement).
`test/qa-integration`'s remaining seven commits are all merges with no unique
content — it is now strictly behind `next`.

**This broke the upstream PR recipe, and that mattered more than the merges.**
`git rebase --onto upstream/next next pr/<name>` replays exactly
`next..pr/<name>`. Merging the features into `next` puts them in the exclusion
set, so that range is empty and the recipe yields a PR branch containing
*nothing* — silently. Confirmed: 0 commits after the merge.

Replaced it with path selection, which does not care where the commits live:
`git checkout next -- <paths>` onto a worktree at `upstream/next`. Verified it
produces one commit containing exactly the 13 rclone paths and nothing else,
and that the pre-push guard passes it. The trade — no granular history on the
PR branch — costs nothing, since upstream squash-merges and asks for one commit
anyway. Worth noting the general shape: a workflow step that derives its
correctness from where commits happen to live is fragile in a way that a step
keyed on content is not.

    projects/ROCKNIX/packages/emulators/libretro/a5200-lr/package.mk
    -PKG_TOOLCHAIN="auto"
    +PKG_TOOLCHAIN="make"

from `c1bf43ffbe` "GENERIC_X64 - emulators: fix dosbox-core-lr + a5200-lr for

(`X64_SKIP_CORES="parallel-n64-lr flycast2021-lr duckstation-lr idtech-lr"`),

I did not apply it. The recipe is global, not device-scoped, so forcing
`make` changes the build for every device, and upstream's recipe has moved
since — whether `auto` still misdetects on x86_64 is a build question I cannot
answer here. It belongs with issue #16, which already tracks per-core x86_64
fixes. Recording the exact one-line change is enough to preserve it; keeping a
5000-commit pre-rebase branch alive for one line is not.

The lesson is the ordinary one: "fully merged" was true of six branches and
false of two, and the difference was only visible by checking. A branch that is
0 commits ahead is safe; one that is 82 ahead needs its commits read.

## A guard for the worktree removal, not a note about it

The near-miss earlier today deserved a mechanical fix rather than a reminder to
be careful, because carelessness was not the problem. The problem was a loop
that treated five worktrees identically when two of them held 371 GB of build
roots. The command was the same; what sat behind it was not.

`tools/fork-worktree` now stands in front of `git worktree remove`:

- `list` says what each worktree is holding, so the difference is visible
  *before* the loop rather than after it.
- `remove` refuses outright when `build.*`, `sources/`, `target/` or `release/`
  are present, names them, and gives the two ways forward (`--preserve <dir>`
  or `--force`).
- It refuses to remove the directory you are standing in — that failure mode is
  especially nasty because the shell's cwd vanishes mid-command and every later
  step fails for an unrelated-looking reason.
- It checks whether the directory actually went away, since git can unregister
  and leave the contents; a non-zero exit inside a loop is not a report.
- `repair` encodes the recovery I had to improvise: git's own `worktree repair`
  cannot help once the admin dir under `.git/worktrees/` is pruned.

Proved it fires rather than assuming, per the lesson from the pre-push guard.
Six tests against a throwaway worktree with a stand-in build root: refuses by
default; refuses from inside the target; `--preserve` moves the build root out
and the artifact survives; a checkout-only worktree removes with no false
refusal; `--force` destroys after saying what dies; and `repair` recovers the
exact orphan state — reproduced by pruning the admin dir — where `git worktree
repair` errors out and the tool restores registration, the build artifact and
an untracked file.

Registered as blindspot 15. The general shape is worth naming: the cheap cases
in a sweep succeed first and lower your guard before the expensive one arrives,
and `--force` is the flag you add at precisely the moment you have stopped
reading.

## Detached build worktrees would have shipped an empty BUILD_BRANCH

I told the user detached HEAD was fine for building because `scripts/image`
uses `git rev-parse`. It does — on line 57. On line 161 it also runs
`git branch --show-current`, which returns empty when detached, and that value
goes into `/etc/os-release` as `BUILD_BRANCH` and is shown to the player by
`rocknix-info` as `BUILD ID: cb50b45 (test/qa-integration)`. Every image built
from those three worktrees would have carried a blank field. I had checked one
line and generalised from it.

Fixed by giving each worktree a branch named after its directory —
`build/devices`, `build/generic-x64`, `build/rclone-cleanup` — since git will
not check out `next` twice and the primary checkout holds it. Added
`fork-worktree sync` to fast-forward them, because a branch no more follows
`next` by itself than a detached HEAD does.

**Then I broke two of them while testing that.** Verifying the divergence
guard, I ran `fork-worktree sync synctest-target` with a throwaway ref. sync
walks *every* build worktree, so it fast-forwarded `build/devices` and
`build/generic-x64` onto that commit too — and I only grepped the output for
"synctest", so I never saw the two lines saying so. It surfaced later as a
nonsense "is AHEAD of next" report I nearly dismissed as a logic bug in my own
condition; instrumenting it showed the tool was right and the worktrees were
genuinely elsewhere. No harm done: the throwaway commit's tree was identical to
next's, so no file changed and no build root moved.

Two things came out of it. The footgun is gone — `sync` no longer takes a
target, because the only ref worth following is `next` and an arbitrary one
moves every worktree at once. And the testing lesson repeats an old one:
grepping a command's output for the line you expect hides the lines you did
not. Twice now the answer has been to read the whole output.

## backuptool backup has been broken since the rebase: the image has no zip

Started the VM build first, per the plan to prove backup/restore before
spending hours on device images. Two bugs surfaced before the build even
finished, and neither would have been visible on the host.

**busybox disagrees with GNU grep.** The hold-back filter I added this morning
piped `grep -vxF -f "${SECRETLIST}"` into zip. GNU grep prints every line when
the pattern file is empty; busybox prints nothing. The device runs busybox, so
a user whose custom LOCATIONS excluded all three credential files would hand
zip an empty list and the backup would fail — exactly the case the membership
check exists to serve. Found by running the construct under `busybox grep` on
this host rather than assuming the two agreed. Host busybox is a cheap and
underused proxy for device tooling; worth reaching for before a VM exists.

**Then the bigger one.** Chasing whether busybox provides `zip`, I checked the
staged 20260819 RK3566 image: there is no file named `zip` anywhere in it. Only
busybox `unzip`, `gzip`, and libzip's `ziptool`/`zipmerge`/`zipcmp`. Upstream
deleted `packages/compress/zip` in `a3d0ad0430` (Ian Leonard, Jan 2026) and our
Aug 19 rebase pulled that in — while `backuptool`, upstream's own script, still
builds its archive with `zip -9`. So `backuptool backup` has failed instantly on
every image built since, and upstream is broken the same way.

It hid for months for two reasons worth remembering. Nothing declared `zip` in
any `PKG_DEPENDS_TARGET`, so a runtime dependency on a CLI had no build-time
signal and deleting it broke no build. And *restore* kept working, because that
path uses busybox `unzip` — a feature that half works reads as a partial bug
rather than a missing dependency. It also explains a loose end from the 18th:
the restore-side symlink fix was confirmed on-device while the backup-side one
never was. The backup path could not execute.

Fixed by restoring the package (with the gcc14 patch deleted alongside it, which
a modern toolchain needs), declaring it in the rocknix package's deps so the
build now enforces it, and having backuptool say plainly that zip is missing
instead of dying on a bare "zip: not found".

**Swept the siblings** rather than assuming this was the only one: every
external command the shipped cloud_* and backuptool scripts invoke, checked
against a real image tree. 21 tools; `zip` was the only one missing.

Build notes: stopped the first run at 47/630 rather than produce an image whose
backup cannot run. The restart then hit blindspot 11 — `libtool:host` failing
with `automake: cannot open < libltdl/ltdl.mk` on a root that had a half-built
toolchain and zero stamps. Per device-builds.md the targeted libtool fix is for
one isolated bump and wrong at this scale, so the root was wiped and rebuilt
clean; libtool passed at 048/631. Also worth noting: `rm -rf` on a build root
fails on Go module caches until `chmod -R u+w`.

One self-inflicted false alarm: I reported a build failure that was my grep
matching cmake's `WILL_FAIL.rst` documentation. The build system marks real
failures `[FAIL]` in brackets. Second time today that a loose grep produced a
wrong conclusion.
