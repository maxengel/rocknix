# Work log — 2026-08-26

## The system-backup phase of cloud sync never restored anything

Went through the legacy `cloud_backup`/`cloud_restore` (621/664 lines) while
waiting on hardware. Started from the one invariant the rules state — that the
two scripts stay structurally in sync — and diffed their shared functions. The
helpers were identical; the drift was all in the phase-2 code, which is where
the bug was.

`cloud_restore`'s system-backup phase filtered on `/backup/*.zip` and
`backup/*.zip`, but that transfer's root is `SYNCPATH_BACKUP`, whose contents
came from `BACKUPFOLDER` — so the archive is at the root, not under `backup/`.
Neither include matched. Because using `--include` at all excludes everything
it does not match, the transfer moved no files, exited 0, and the summary
printed SUCCESS. Shipped in four images. Reachable only for users who set
`BACKUPFILE_RESTORE_OPTION="yes"`, which is off by default.

The backup side had the same mistake with no symptom: it borrowed the saves
allowlist through `RESTORE_RCLONEOPTS`, whose rules are anchored to
`BACKUPPATH` while that transfer's root is `BACKUPFOLDER`, and whose
`- /**/*.zip` matches the archive. It worked only because rclone applies
`--include` ahead of `--filter-from`. A precedence detail was the only thing
holding it up.

**Method worth repeating:** rather than reason about rclone's filter
precedence, I built a fixture tree and asked rclone. That settled four
questions in one pass and caught two excludes that had never matched anything
(`"${BACKUPFOLDER}/**"` is absolute where rclone matches relative to the
transfer root; `backups/**` names a directory that does not exist — it is
`backup`). Then I ran the real scripts end-to-end against the WebDAV test
backend by relocating `/storage` into a scratch tree, and ran the **shipped**
script alongside the fixed one: 4 saves / 0 archives before, 4 / 1 after.
A before-and-after on the real code is what turns "I think this was broken"
into evidence.

Also fixed: `--system-only` was parsed and ignored by `cloud_restore`, so it
restored game saves over local ones — the opposite of the flag. "Nothing to
transfer" returned 1 in both system phases and printed COMPLETED WITH ERRORS on
a device that had simply never made a backup. `check_internet` pinged
google.com, which fails for a self-hosted or LAN remote and passes when the
user's provider is down; it now tests the configured remote.

One claim I had to retract mid-work: I asserted in a comment that nesting
`SYNCPATH_BACKUP` inside `SYNCPATH` makes each backup delete the previous
archive. Testing it showed a full run re-uploads moments later and hides it.
The real hazard is narrower — a `--saves-only` run deletes the archives and
puts nothing back — so the comment and the new warning say that instead.

The suite never covered phase 2, which is why this lived. `cloud-round-trip`
now round-trips the archive, and `cloud-test-backend` reports `syncpath-backup`
as a sibling of `syncpath` (the driver had nested it, which the shipped
defaults do not).

## backuptool, and consolidating every branch onto next

Reviewed the hardened `backuptool` (the six commits that had been sitting on
`feature/backuptool-baseline`, merged into the test branches but never into
`next`, so `next` had been building without them). It is in good shape —
regular files only, credential stripping, an archive self-check, rotation, the
restore-finished marker. Two things left.

**The interaction only existed once both branches were together.** `backuptool`
now rotates old backups into `BACKUPFOLDER/archive/`, and its comment says that
folder dodges the cloud allowlist. True of phase 1 — but phase 2 does not use
the allowlist, it matched `*.zip`, and an unanchored rclone pattern matches at
any depth. Every rotated archive was being uploaded on every sync. Anchoring to
`/*.zip` fixes it. This is a good argument for the consolidation itself: neither
branch was wrong alone.

**Sanitize-after-the-fact still writes the secret.** `backuptool` zipped the
real `system.cfg`, `es_settings.cfg` and `retroarch.cfg`, then overwrote each
with a sanitized copy. End state clean, but the populated secret hits the
archive first and an interrupted backup leaves it there. The three files are
now held back and only sanitized copies are ever written. That also fixed a
smaller bug — the sanitized copies were added whenever the file existed, so a
user with custom `LOCATIONS` excluding one got it in their backup anyway.

I could not test Info-ZIP's replace semantics (no `zip` on this host), so I did
not claim the old approach left recoverable bytes. The ordering argument stands
on its own.

**Consolidation.** Merged `feature/backuptool-baseline`, `feature/cloud-saves`
and `test/qa-generic-x64` into `next`. All three merged clean, and none
resurrected the retired Copilot files (checked the merged trees before
committing, since two of those branches predate the retirement).
`test/qa-integration`'s remaining seven commits are all merges with no unique
content — it is now strictly behind `next`.

**This broke the upstream PR recipe, and that mattered more than the merges.**
`git rebase --onto upstream/next next pr/<name>` replays exactly
`next..pr/<name>`. Merging the features into `next` puts them in the exclusion
set, so that range is empty and the recipe yields a PR branch containing
*nothing* — silently. Confirmed: 0 commits after the merge.

Replaced it with path selection, which does not care where the commits live:
`git checkout next -- <paths>` onto a worktree at `upstream/next`. Verified it
produces one commit containing exactly the 13 rclone paths and nothing else,
and that the pre-push guard passes it. The trade — no granular history on the
PR branch — costs nothing, since upstream squash-merges and asks for one commit
anyway. Worth noting the general shape: a workflow step that derives its
correctness from where commits happen to live is fragile in a way that a step
keyed on content is not.

## Deleting the merged branches — and the one that was not merged

Checked every branch for containment before deleting rather than trusting the
"these are all merged now" framing. Six were fully contained. Two were not, and
one of those held work that exists nowhere else.

`feature/rclone-cleanup` had five commits whose subjects are absent from
`next`, but they were squashed into PR #3055, which merged upstream — and each
change is verifiably present (`--delete-excluded` stripped on restore,
`RSYNCRMDIR` implemented via `rclone rmdirs`, `rclonectl` gone,
`--progress-terminal-width` in both flows). Superseded, safe.

`feature/generic-x64` had two. `intel-ucode` is on `next` already. The other is
**not merged anywhere**:

    projects/ROCKNIX/packages/emulators/libretro/a5200-lr/package.mk
    -PKG_TOOLCHAIN="auto"
    +PKG_TOOLCHAIN="make"

from `c1bf43ffbe` "GENERIC_X64 - emulators: fix dosbox-core-lr + a5200-lr for
x86_64". It matters because a5200-lr is **not** in the GENERIC_X64 skip list
(`X64_SKIP_CORES="parallel-n64-lr flycast2021-lr duckstation-lr idtech-lr"`),
so it is still built for x86_64 with the toolchain that commit says is wrong.

I did not apply it. The recipe is global, not device-scoped, so forcing
`make` changes the build for every device, and upstream's recipe has moved
since — whether `auto` still misdetects on x86_64 is a build question I cannot
answer here. It belongs with issue #16, which already tracks per-core x86_64
fixes. Recording the exact one-line change is enough to preserve it; keeping a
5000-commit pre-rebase branch alive for one line is not.

The lesson is the ordinary one: "fully merged" was true of six branches and
false of two, and the difference was only visible by checking. A branch that is
0 commits ahead is safe; one that is 82 ahead needs its commits read.
