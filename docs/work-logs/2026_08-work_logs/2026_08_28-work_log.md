# 2026-08-28 work log

## 17:20 UTC — H700 unreachable over SSH: a hostname collision, and the identity gap behind it

**Symptom.** SSH to the freshly flashed official 8/1 build failed with
`EHOSTUNREACH` on both `<hostname>.local` and the IP shown in the router UI.
ES showed wifi CONNECTED and SSH enabled. **Renaming the device fixed it.**

**Why the two ES indicators were misleading.** Neither says what it looks like
it says:

- `GuiMenu.cpp:6366` renders CONNECTED from `ApiSystem::ping()`, which is
  `ping -c 1 8.8.8.8` (`ApiSystem.cpp:329`) — an *outbound internet* check. It
  proves the device has an uplink; it says nothing about whether anything can
  reach the device.
- `GuiMenu.cpp:6577` renders the SSH switch from `ssh.enabled == "1"` — the
  stored setting, sampled when the page opened, not the daemon's state.

**How the diagnosis should have gone faster.** `EHOSTUNREACH` is a layer-3/2
error; a stopped sshd on a reachable host gives *connection refused*. The
decisive check was `ip neigh` reporting **FAILED** — ARP unanswered from both
the wired and wireless interface — which rules out everything above L2 in one
command. A /24 sweep plus SSH banner grab (no OpenSSH 9.x present, and ROCKNIX
pins 9.8p1) corroborated it. Reach for `ip neigh` before scanning.

**Root cause.** The hostname is the *device family*, fixed at build time:

```
system.cfg:183        system.hostname=@DEVICENAME@
rocknix/package.mk:85 sed -i "s#@DEVICENAME@#${DEVICE}#g" .../system.cfg
```

Every H700 image boots as `H700`, reaching the router via DHCP option 12
(`network-base-setup` → `hostnamectl --transient`). Two same-family units
collide and the router's name→lease binding flips. Filed as **#50**.

**`.local` was never going to work.** `network-base-setup` calls
`avahi-set-host-name`, but `avahi/package.mk:98` has
`# enable_service avahi-daemon.service` commented out since `9f1fab30f6`.
`avahi-defaults.service` *is* enabled and creates the conf that satisfies the
daemon unit's `ConditionPathExists`, but with no `WantedBy` symlink systemd
never starts it. `nss-mdns` lets the device resolve *other* `.local` names
outbound; nothing makes it answer to its own. Whether that is deliberate
(boot time / battery) is unconfirmed — check intent before changing it.

**The larger finding.** Chasing the hostname surfaced that ROCKNIX has **no
per-unit identity at all**, and the cloud path inherits the same flaw with a
data-loss consequence:

```
backuptool:21   BACKUPFILE="${BACKUPFOLDER}/${OS_NAME}_BACKUP.zip"
cloud_backup:582 ... "${BACKUPFOLDER}/" "${REMOTENAME}${SYNCPATH_BACKUP}/"
```

`OS_NAME` is `ROCKNIX` everywhere, so two H700s upload the same filename to the
same remote path — the second overwrites the first, and restoring device A then
applies device B's config. The `archive/` rotation does not rescue it: the
upload include is root-anchored `--include=/*.zip` (correct on its own terms —
unanchored would re-upload every rotated archive every sync), so `archive/`
never reaches the cloud and there is no remote history. Filed as **#49**.

`grep -riE 'hostname|uname -n'` over `rclone/sources/` returns nothing — no
cloud script references any per-unit identity.

**Note on #10.** It covers per-core/per-chipset savestate namespacing. Two
H700s are the *same* chipset, so its scheme would not separate them. #49 is a
distinct gap, not a duplicate.

**Follow-ups.** #49 and #50 both block the two-H700 multi-device QA in #35/#26,
which the arriving RG-SP was meant to enable. Any identity scheme has to be
stable across a reflash and must not move or delete anything already in the
user's cloud folder (`upgrade-and-install.md`).

**Unblocked meanwhile.** The `CONTENTPATH` derivation test needs no SSH: read
`/storage/.config/cloud_sync.conf` from the card, drop the `.tar` into
`/storage/.update`, boot, re-read. Precondition confirmed from `upstream/next`:
`DEFAULT_SYNCPATH="/GAMES"`, no `CONTENTPATH` key, and no
`cloud_content_backup`/`cloud_content_restore` at all — those are fork
additions. Pass condition is `CONTENTPATH="/GAMES/Content"`.
