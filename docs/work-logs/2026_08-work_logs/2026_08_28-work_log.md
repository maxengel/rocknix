# 2026-08-28 work log

## 17:20 UTC — H700 unreachable over SSH: a hostname collision, and the identity gap behind it

**Symptom.** SSH to the freshly flashed official 8/1 build failed with
`EHOSTUNREACH` on both `<hostname>.local` and the IP shown in the router UI.
ES showed wifi CONNECTED and SSH enabled. **Renaming the device fixed it.**

**Why the two ES indicators were misleading.** Neither says what it looks like
it says:

- `GuiMenu.cpp:6366` renders CONNECTED from `ApiSystem::ping()`, which is
  `ping -c 1 8.8.8.8` (`ApiSystem.cpp:329`) — an *outbound internet* check. It
  proves the device has an uplink; it says nothing about whether anything can
  reach the device.
- `GuiMenu.cpp:6577` renders the SSH switch from `ssh.enabled == "1"` — the
  stored setting, sampled when the page opened, not the daemon's state.

**How the diagnosis should have gone faster.** `EHOSTUNREACH` is a layer-3/2
error; a stopped sshd on a reachable host gives *connection refused*. The
decisive check was `ip neigh` reporting **FAILED** — ARP unanswered from both
the wired and wireless interface — which rules out everything above L2 in one
command. A /24 sweep plus SSH banner grab (no OpenSSH 9.x present, and ROCKNIX
pins 9.8p1) corroborated it. Reach for `ip neigh` before scanning.

**Root cause.** The hostname is the *device family*, fixed at build time:

```
system.cfg:183        system.hostname=@DEVICENAME@
rocknix/package.mk:85 sed -i "s#@DEVICENAME@#${DEVICE}#g" .../system.cfg
```

Every H700 image boots as `H700`, reaching the router via DHCP option 12
(`network-base-setup` → `hostnamectl --transient`). Two same-family units
collide and the router's name→lease binding flips. Filed as **#50**.

**`.local` was never going to work.** `network-base-setup` calls
`avahi-set-host-name`, but `avahi/package.mk:98` has
`# enable_service avahi-daemon.service` commented out since `9f1fab30f6`.
`avahi-defaults.service` *is* enabled and creates the conf that satisfies the
daemon unit's `ConditionPathExists`, but with no `WantedBy` symlink systemd
never starts it. `nss-mdns` lets the device resolve *other* `.local` names
outbound; nothing makes it answer to its own. Whether that is deliberate
(boot time / battery) is unconfirmed — check intent before changing it.

**The larger finding.** Chasing the hostname surfaced that ROCKNIX has **no
per-unit identity at all**, and the cloud path inherits the same flaw with a
data-loss consequence:

```
backuptool:21   BACKUPFILE="${BACKUPFOLDER}/${OS_NAME}_BACKUP.zip"
cloud_backup:582 ... "${BACKUPFOLDER}/" "${REMOTENAME}${SYNCPATH_BACKUP}/"
```

`OS_NAME` is `ROCKNIX` everywhere, so two H700s upload the same filename to the
same remote path — the second overwrites the first, and restoring device A then
applies device B's config. The `archive/` rotation does not rescue it: the
upload include is root-anchored `--include=/*.zip` (correct on its own terms —
unanchored would re-upload every rotated archive every sync), so `archive/`
never reaches the cloud and there is no remote history. Filed as **#49**.

`grep -riE 'hostname|uname -n'` over `rclone/sources/` returns nothing — no
cloud script references any per-unit identity.

**Note on #10.** It covers per-core/per-chipset savestate namespacing. Two
H700s are the *same* chipset, so its scheme would not separate them. #49 is a
distinct gap, not a duplicate.

**Follow-ups.** #49 and #50 both block the two-H700 multi-device QA in #35/#26,
which the arriving RG-SP was meant to enable. Any identity scheme has to be
stable across a reflash and must not move or delete anything already in the
user's cloud folder (`upgrade-and-install.md`).

**Unblocked meanwhile.** The `CONTENTPATH` derivation test needs no SSH: read
`/storage/.config/cloud_sync.conf` from the card, drop the `.tar` into
`/storage/.update`, boot, re-read. Precondition confirmed from `upstream/next`:
`DEFAULT_SYNCPATH="/GAMES"`, no `CONTENTPATH` key, and no
`cloud_content_backup`/`cloud_content_restore` at all — those are fork
additions. Pass condition is `CONTENTPATH="/GAMES/Content"`.

## 19:15 UTC — CONTENTPATH derivation: PASS on a real official→fork upgrade

Ran the migration test that the fresh-flashed device could not: an **official**
ROCKNIX `20260801` H700 install (`OS_BUILD="official"`,
`BUILD_ID="3b9cb1f6bf48ee9ca0cf01edd9af52ca2a6b73fb"`) upgraded in place to our
`20260827`.

**Precondition** (verified on-device, not assumed):

```
BACKUPPATH="/storage/roms"   RESTOREPATH="/storage/roms"
BACKUPFOLDER="/storage/roms/backup"
SYNCPATH="/GAMES"            SYNCPATH_BACKUP="/GAMES/backup"
(no CONTENTPATH key)
absent: cloud_content_backup, cloud_content_restore, cloud_setup
```

All three fork scripts missing is what proves the base was genuinely upstream.

**Result — PASS:**

```
CONTENTPATH="/GAMES/Content"
[cloud_sync_helper] Derived CONTENTPATH from SYNCPATH /GAMES
[cloud_sync_helper] Added new configuration option: CONTENTPATH
```

`SYNCPATH` stayed `/GAMES` — the append-only merge did not rewrite the existing
layout, which was the more damaging failure mode of the two.

**Why the earlier "confirmation" was worthless.** The device had been flashed
fresh with `20260827`, which already ships `/ROCKNIX` defaults, so the
add-missing-key path never ran — and `dirname /ROCKNIX/Saves` → `/ROCKNIX` →
`/ROCKNIX/Content` is indistinguishable from the literal default anyway. Only a
pre-`/ROCKNIX` base makes the derived value observable. **A test whose pass
output is identical to the untested default proves nothing;** pick the base that
makes the two differ.

**Pre-flight worth repeating.** Before flashing, unpacked `usr/bin/cloud_sync_helper`
out of `target/SYSTEM` in the published `.tar` and read the derivation there,
and confirmed the release asset's sha256 matched the local build byte for byte
(`318ecce7…`). Per `device-builds.md`, a build that shipped without the change
would have "failed" the test for a reason unrelated to the logic. Also verified
the checksum again on-device post-transfer — the initramfs will happily apply a
truncated tar.

**Incidental: `OS_BUILD` is real and set by CI.** Official = `official`, ours =
`community`. That branch (`rocknix/package.mk:88`) flips `ssh.enabled`,
`wifi.enabled` and `samba.enabled` to 1, which is exactly why SSH was on for our
build and off on the official flash — the original symptom that started the day.
It is set by release CI, not anywhere in the tree.

**Non-interactive SSH gotcha.** `get_setting`/`set_setting` come from
`/etc/profile`, which a non-interactive `ssh host 'cmd'` does not source, so they
return empty rather than erroring usefully. Prefix with `. /etc/profile;`.

**Still open:** #46 remains unproven (its guard fires after a *restore*, not an
upgrade); #45, #47, #48 need visual confirmation on device. The nested
`SYNCPATH_BACKUP="/GAMES/backup"` warning should now fire on this device's next
backup - worth catching, since it has only ever been exercised on the host.

## 20:40 UTC — Cloud setup: the SSH flow is the wrong shape; native setup designed and started

### What the device QA actually found

Setting up a Dropbox remote through the shipped wizard failed at four points,
against a person who had written the instructions himself:

1. **rclone's prompt contradicts ours.** At `Use auto config?` rclone says
   *"Say N if running rclone on a (remote) machine without web browser
   access"* — which describes the handheld exactly. N is fatal here. rclone's
   advice is in the terminal at the decision point; ours is on another screen,
   on another device, several steps earlier. **Ours loses that contest every
   time.** Naming a conflicting instruction beats restating our own.
2. **Answering N collides on port 53682** — `rclone authorize` cannot bind it
   because the SSH tunnel holds it, then floods `channel 3: open failed`.
3. **"Failed to open browser automatically" prints on every run** (no browser
   on the device) and reads as an error at the moment the player must act.
4. **The auth link exists only in terminal scrollback.** Our step said "sign in
   via the link in your browser", implying one opens by itself.

All four are us documenting a hostile interface. Fixed the text
(`feature/cloud-setup-polish`), but the fix is the wrong altitude.

### The unlock

`rclone config create <name> <type> key=value` writes a remote
non-interactively, `--non-interactive` is documented as being *"for use by
applications that wish to configure rclone themselves"*, and every OAuth
backend accepts `token` as a plain config value. **So no upstream rclone
change is needed** — we perform the grant and hand rclone the result. Issue
#29 reframed accordingly.

Backend tiering, from `rclone config providers` on the device (69 backends):
**50 key/password** (a form is enough), **3 drivable OAuth** (dropbox via PKCE
with no redirect_uri; drive + onedrive via device flow), **16 SSH fallback**.

### We register no OAuth clients — decided, with reasons

The maintainer pushed back on ROCKNIX holding OAuth registrations. Correct on
principle, and the practice is worse than the principle:

- An unverified Google app is capped at **100 users**, and Testing status
  **invalidates refresh tokens after 7 days** — weekly re-auth for everyone.
- rclone is already retiring its shared Drive client_id ("will stop working
  during 2026"), so Drive is going bring-your-own regardless.

Player supplies their own client_id; we make everything after that painless.
50 of 69 backends are unaffected because they involve no OAuth at all.

### Non-obvious things worth keeping

- **rclone's own metadata cannot decide input masking.** `sftp.host` is
  `Sensitive=True, IsPassword=False`; so is `s3.secret_access_key`. Masking on
  `Sensitive` hides hostnames; masking on `IsPassword` exposes an AWS secret.
  Report both flags and let the UI decide (settled: mask either, reveal on
  open — which ES already does, since the row masks but the editor gets
  plaintext).
- **ES wizard pages cannot scroll.** `ComponentList` moves the camera from
  `mCursor` (ComponentList.cpp:299) and cursor movement skips unselectable
  rows (ComponentList.h:120). A page of info/prose rows has no selectable row
  at all, so content past the fold is *unreachable*, not merely off-screen.
  Text on those pages has a hard height budget.
- **`ComponentList` insets selectable rows only** — an unselectable row sits
  flush at x=0 while group headers and value rows are at 10px, so prose rows
  must pad themselves.
- `rclone` already depends on **qrencode**, so QR generation for a phone
  hand-off is available today.

### Process failure worth naming

Diagnosing "SSH times out" I asserted **wireless client isolation**, retracted
it on a sweep that looked random, then re-derived it, then had it broken again
by "wired doesn't work either" — before the real cause turned out to be stale
Orbi 970 bridge state that a router reboot cleared.

The sweep only looked random because I had not established **which hosts were
wireless**. The rule: *establish the classifying variable before asserting or
withdrawing a cause.* Also, `ip neigh` showing `FAILED` settles layer 2 in one
command and should come before any port scan; and "what makes the one working
host different?" was the question all along — I treated serval as an exception
to explain away rather than the evidence.

Filed: #51 (native remote setup), #52 (rclone.conf missing from backuptool's
held-back credentials list — currently harmless only because configuring a
remote is hard, which #51 exists to change).

Built: `cloud_remote` (97b3ee5475) — providers/fields/create/list, verified on
the H700. Refuses to modify an existing remote; verifies with `rclone lsd`
before reporting success and rolls back if that fails.
