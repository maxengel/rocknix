### The finding that made this non-optional

Upstream reworked the ES package: **archive instead of git clone**, and
`CMakeLists.txt` now declares GLES/GLES2/GLES3/GL **mutually exclusive
with a `FATAL_ERROR`**. Our `package.mk` still passes `-DGL=1` *and*
`-DGLES2=1` when both are available, which the new ES refuses to
configure. Building the new ES against the old recipe fails outright.

Reconciled recipe: upstream's file, with only the source fields changed
back to the fork's git clone (`PKG_SITE`, `PKG_URL`,
`PKG_GIT_CLONE_BRANCH`, `GET_HANDLER_SUPPORT="git"`), keeping
`-DGLES3=1`, the `${OPENGLES}` dependency and the new `makeinstall`.
Dropping `PKG_PATCH_DIRS+="${DEVICE}"` is safe - the package has no
`patches/` directory.

## The warm build roots had to go (2026-08-19)

The rebased RK3566 build failed three times, each further in, and the
chase is worth recording because the first two "fixes" were wrong in an
instructive way.

1. `libtool:host` died on `LT_LANG: unsupported language: "Objective-C"`.
   Nothing to do with Objective-C: upstream bumped libtool 2.5.4 -> 2.6.2,
   and `config/functions` exports `LIBTOOLIZE` **only when the toolchain
   already has one**. A clean tree has none (the build container ships
   neither libtool nor libtoolize - verified), so nothing overwrites the
   new macros. A warm tree finds the *old* libtoolize, which runs
   `--copy --force` and replaces libtool 2.6.2's serial-67 macros with
   2.5.4's serial-63 ones. The package sabotages its own upgrade with the
   copy of itself already installed.
2. First attempt cleared the stale macros from the sysroot. The error
   moved from `sysroot/.../libtool.m4` to `m4/libtool.m4` - which looked
   like progress and was not. Removing a *copy* does nothing about the
   process doing the copying. Removing the old libtool host install fixed
   it properly; `libtool:host` then built.
3. Next failure: `libgcrypt` wanted libgpg-error >= 1.56 and found 1.55,
   with a stamp from the previous build. Root cause is structural:
   `projects/ROCKNIX/packages/security/libgpg-error/package.mk` sources
   the generic recipe for its `PKG_VERSION`, but `calculate_stamp` hashes
   `$PKG_DIR`, which resolves to the **override** directory. The file
   holding the version is never hashed, so the bump cannot invalidate the
   stamp. **53 ROCKNIX packages use that pattern.**

At that point the right move was to stop patching and measure. Sweeping
every override's `PKG_VERSION` against what each root had built found
**35 stale packages**: openssl 3.5.1 -> 3.6.3, glib 2.85.1 -> 2.89.3,
libfmt 9.1.0 -> 12.2.0 (a major ABI break), plus curl, expat, zlib and
the X11 stack.

**The first version of that sweep was wrong**, and I quoted its worst
row before checking it. It read `PKG_VERSION` from the generic recipe
the override sources - but an override may re-set it afterwards to hold
a package back deliberately, as `gcc` (pinned 15.2.0 against a generic
16.2.0), `iwd` and `opus` all do. So it reported the compiler as stale,
and "the compiler is stale" is what I gave as the headline reason for
wiping 258 GB. One `ls build/gcc-*` would have caught it; the clean
build later showed `gcc-15.2.0`, exactly as pinned. See blindspot 12.

The decision survives on the corrected evidence - stale openssl, glib
and libfmt installs with newer consumers linking against them is a real
ABI hazard - but it was made on a claim I had not established. Wiped all four
build roots (258 GB, freed) and started clean. `sources/` is a separate
directory so nothing is re-downloaded, and the pre-rebase images were
moved to `target/prerebase-20260819/` first - the new build reuses the
same date-stamped filenames and would have overwritten the only H700
image we have.

Both upstream defects are worth a PR: the libtoolize preference, and the
stamp that misses the file carrying the version.
