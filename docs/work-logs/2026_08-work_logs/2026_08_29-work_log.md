# 2026-08-29 work log

## 01:10 UTC — Native cloud setup built, and the whole stack verified on a VM

Built P1 of #51 (native provider setup) and then verified the entire cloud
stack end to end on GENERIC_X64 against the WebDAV test backend, using a
remote **configured through the new UI** rather than by hand.

### Safety properties, demonstrated rather than reasoned about

These were all documented in `rclone-cloud-sync.md` as intent. None had been
shown to hold on a running device until now.

| Property | Evidence |
|---|---|
| ROMs/BIOS never reach the cloud | seeded `.sfc`, `.zip`, `scph1001.bin`, `gamelist.xml`, box art -> none present on the backend after backup |
| A save inside a ROM dir *is* synced | `snes/game.srm` uploaded |
| A `sync` restore does not delete the library | after restore every ROM/BIOS/artwork file still on disk - the `--delete-excluded` strip holds |
| Credentials never enter the archive | set `wifi.key="SECRET-WIFI-PASSWORD"`, then **0** occurrences in the 17 MB archive; `audio.preamp=42` preserved |
| `backuptool backup` works | archive created - the `zip` dependency fix (dead since January) confirmed |
| Both phases stay separate | `ROCKNIX/Saves/...` and `ROCKNIX/Backups/ROCKNIX_BACKUP.zip` |

Fresh-install defaults put `SYNCPATH_BACKUP="/ROCKNIX/Backups"` as a *sibling*
of `/ROCKNIX/Saves`, so our layout avoids the nesting trap upstream's `/GAMES`
default has.

Archive is **17 MB on a VM with no user data** - a concrete number for #45.

### Nine defects, and what actually found them

Only one was found by reading code. The rest needed the thing to run.

1. `GetShOutput` drops the last character of every chunk it reads, so
   multi-line output returns concatenated. The provider list became one
   bogus record - non-empty, so no error path fired; the group rendered
   empty and a search for "webdav" said "nothing matched". Added
   `GetShOutputLines` rather than changing a helper whose single-line
   callers want exactly the current behaviour.
2. TSV split used `removeEmptyEntries`, so any row with an empty column
   lost it and shifted left. Most options have no default, so nearly every
   form field vanished - the page looked finished and could do nothing.
3. Provider labels were rclone's documentation prose, truncated mid-word.
4. Options are gated on a sub-provider. koofr carries **three** separate
   options all named `password`; the form keyed by name, so it drew three
   identical rows writing to one value. s3 has 51 sub-providers and asked
   for IBM credentials regardless of vendor.
5. `local`, `memory`, `alias` and friends were offered as cloud providers.
   `local` in that list is a "backup" onto the same storage as the data.
6. Backend ids are not all shell-safe: `google cloud storage`,
   `google photos`.
7. `bool` options rendered as a text box wanting the word "true" typed in.
8. Options with a short list of suggestions rendered as free text - nobody
   guesses that generic WebDAV means the literal string `other`.
9. **The chosen list value never reached the config.** `addSaveFunc` runs
   from `GuiSettings::save()` at page close, but CREATE REMOTE builds its
   command while the page is open. The vendor was discarded *and the
   create reported success*, because WebDAV tolerates an empty vendor. On
   Sharepoint or Nextcloud that is the wrong dialect. Only reading back
   `rclone.conf` caught it - the dialog said it worked.

**The lesson worth keeping:** a passing end-to-end test certified #9 as
working. Verifying the *artifact* (what got written) rather than the
*outcome* (did it report success) is what found it. Same shape as the
`backup/*.zip` filter bug that shipped in four images: exit 0, SUCCESS
printed, nothing transferred.

### What made the loop cheap

`cloud_remote` is testable over SSH against a running VM in seconds; only
the ES half costs a build. Defects 4-8 were all found in one audit pass with
no build at all, by comparing real backend output against what the UI does
with it. Keep schema knowledge in the script and ES a renderer.

Also: enabling SSH on the VM (key over the serial console) turned a
slow screenshot-driven loop into a fast one. Do that first next time.

## 17:40 UTC — #53 fixed in an image, and the regression case proven both ways

`cloud_backup` reported a successful upload while sending nothing. On a remote
with neither modtimes nor hashes (`Precision: 3153600000000000000`,
`Hashes: []` — an ordinary WebDAV server) rclone compares by size alone, and
the archive is ~17 MB of OS-shipped assets around a few KB of config, so a
settings change routinely leaves its size identical. `preamp=7` -> `preamp=8`
is the same width.

Single device, no multi-device setup needed:

```
local md5 1905e157   size 17157375
cloud md5 6450c1cf   <- stale, and "completed successfully" printed
```

**Fix** (`3cbe680764`): decide on content, not on metadata the remote may not
have. A marker records what was last actually uploaded; a differing archive is
forced past rclone's comparison. Unconditional upload is not available -- the
game-exit hook runs a full backup on every quit -- and the marker is written
only after the remote comes back the size we sent. `cloud_restore` takes
`--ignore-times` for the mirror case, where a device holding its own same-size
archive would keep it and report a successful restore.

**The test gap mattered more than the bug.** `tools/cloud-round-trip` already
exercised this phase -- write archive, back up, restore, compare hashes -- and
passed throughout, because it **reset the remote first**. Every upload it
tested was a first upload, and a first upload always transfers. A comparison
that wrongly concludes "already there" needs something to already be there.

Proven in both directions with the same command, same fixtures, same backend,
only the image differing:

```
unfixed image:  FAIL  the changed archive never reached the cloud   1 CHECK(S) FAILED
fixed image:    PASS  the second archive replaced the first          PASSED
```

**Two of my own bugs while writing the fix**, both invisible in the outcome:
it first read `BACKUPFILE` (a `backuptool` variable, unset in `cloud_backup`),
then `OS_NAME` (also empty there -- which is why the banner prints
`=>  CLOUD BACKUP UTILITY` with a blank). Each time the cloud copy looked
correct because the archive re-uploaded unconditionally by accident; the marker
staying empty was the only sign. Four sequential fixes on one area, which is
what earned the fix-forward stop rule.

**Adopted from the scaffold estate** (forge.possibility.space/scaffold/scaffold,
41 instruction cards surveyed, 2 taken): the fix-forward stop rule and
operator-ask discipline (`a371bb77f8`), and the decision register
(`41b4071e92`). Rejected `git-safety`, whose headline advice is to stash before
destructive operations -- the one thing this environment forbids, the stash
stack being shared across worktrees.

**Dual-VM capability** landed as `generic-x64-vm --ssh-port` (`96b3d91602`),
which is what #35 wanted and how #53 surfaced. It moves the advertised port
with the forward, since the guest learns its own SSH port via fw_cfg.

Still open: #49 (cross-device overwrite) confirmed on two guests but unfixed --
per-device naming would close it and #53's cause together, pending the
retention question (D-CLOUD-006).

## 21:50 UTC — The sign-in page in two columns, and what that exposed

**The clipping was vertical, not horizontal.** The sign-in page cannot scroll:
every row on it is unselectable, so `ComponentList` never moves its camera and
anything past the fold is unreachable rather than merely off-screen. Four
numbered steps plus a square QR plus an address came to 428px of a 415px
viewport, and the address rendered cut across its baseline. The fix is the one
the maintainer named — the code in one column, its text in the other. A
`ComponentListRow` already lays elements out left to right and centres them
vertically, so the two share one row's height instead of taking two
(`5d626a13e`).

`MultiLineMenuEntry` would not do for the right-hand column: its second line is
deliberately smaller and dimmer, and an address and a code are both things
somebody reads off the screen and types. `cloudSetupTextStack` builds a
`ComponentGrid` of equal-weight lines instead.

**The layout is resolution-independent, which is worth knowing before tuning
constants against two panels.** `cloudSetupPresent` clamps the menu width to
`min(0.9 * screenWidth, screenHeight)` and the height to `0.75 * screenHeight`;
ES fonts scale with screen height. So 640x480 and 1280x800 produce the *same*
layout in font-relative units, and what the VM renders predicts the handheld.
An afternoon of arithmetic about the H700's panel was unnecessary.

**Two defects fell out of looking at it.**

The address shown was `…/?pin=7677` while the running session's PIN was 6945 —
a *previous* attempt's code on screen. `cloud_oauth`'s `write_state` merges
rather than replaces, so a finished session leaves its address and PIN behind,
and the page waited only for a URL to exist. A stale URL always exists. Anyone
typing that code in would have been refused by a listener waiting for a
different number. `serve` now resets the state as it starts, `cancel` clears it
instead of only marking it idle, and the page waits for `STATUS=waiting` rather
than for an address to appear (`54db0aef16`, `26b505d17`).

The bare address answered `403 Enter the code shown on the handheld` — a flat
refusal with no way forward, so the typed fallback only ever worked if you
typed the query string too. It now serves a four-digit prompt, which is both
usable on a phone and what lets the screen show a short address and the code
apart. Ten wrong answers end the attempt; correct ones do not count against it
(`deee4bbed5`). The QR still carries the PIN, so scanning skips the prompt —
verified by generating a QR on the device for each candidate string and
comparing bytes against the one displayed.

**Verified on the running image, not from the code**: bare address → prompt,
wrong code → "did not match", correct code → the Dropbox sign-in page, and the
displayed QR byte-identical to a QR of the PIN-carrying URL.

Follow-up: rocknix.org has nothing about the native sign-in flow at all. Per
`documentation-accuracy.md` that has to be prepared before any of this goes
upstream (#42), not before it ships to the fork's own devices.

## 22:35 UTC — First real Dropbox sign-in, and why it failed

The flow got all the way to a valid authorization code and then dropped it.
Six findings from the maintainer; the sixth was the functional one.

**Root cause, reproduced.** `rclone authorize` serves exactly one redirect and
then exits — on a failed exchange it exits *fatally*:

```
2026/08/29 18:16:43 NOTICE: Got code
Error: failed to get token: oauth2: "invalid_grant" "code doesn't exist or has expired"
```

Provider codes last about two minutes. The tester approved access, could not
find where the address was meant to go (the paste box sat below a large green
"Sign in" button that looked like the action), and by the time they found it the
code had expired. `cloud_oauth` read none of that output, reported a generic
"not accepted", and told them to walk back to the handheld and start over.

The diagnosis came from the device itself, not the report: `rclone authorize`
was **gone** while `cloud_oauth serve` was still running, and the session's
`state=` matched the redirect URL they pasted. One replay had happened and
killed it. Confirmed by driving rclone's server directly with a bogus code.

**Fixed:** the paste box is first on the page; failures quote rclone's actual
words; and a dead attempt is replaced in place — "Start a new sign-in" issues a
fresh provider link without leaving the phone. That needed the server to outlive
the attempt, and the PIN to move onto the server, because the handheld is
displaying that PIN and a QR built from it (D-CLOUD-013).

**Not fixable:** a success page at the redirect. It resolves to the *phone's*
`localhost:53682`; rclone's listener is on the handheld, and the redirect URI is
registered against rclone's provider app. Serving it would mean our own OAuth
client and a hosted callback — D-CLOUD-001 (D-CLOUD-012).

**Also:** Dropbox/Drive/OneDrive moved to the front page (they were two taps
down under MORE, from when choosing one led nowhere); the phone page is headed
with the provider's real name rather than rclone's lowercase backend id; and the
four-digit number is a **PIN** everywhere. Two things called "code" on one flow
is what made "which one am I meant to enter?" a reasonable question.

## 23:20 UTC — Second Dropbox test: the box that looked filled in

Same outcome, different cause, and a worse one because it was ours to see.

The paste field carried `placeholder="http://localhost:53682/?code=..."`. Grey
hint text reads as a value — the tester pressed the button on what looked like
a completed form, got "That did not contain a code", and stopped. A placeholder
that shows the *shape of the value* rather than *the instruction* is a trap
(D-UI-007); every one on this flow now says what to do.

Around it: the button says **Confirm** rather than Finish; an empty submit says
nothing was pasted and where to get it; **pasting submits on its own**, since
the two minutes the address lives are exactly what gets spent hunting for the
button; the note names the error the phone actually shows ("this site can't be
reached") instead of describing it; and **"Lost the address? Start over"** is
permanently on the page, so the flow has no state with no way forward.

Two structural simplifications from the same round of feedback:

- **One cloud entry.** `SET UP CLOUD REMOTE` and `CONNECT CLOUD STORAGE` named
  the same job, and the first opened the SSH wizard the second replaced. Now
  `USE A COMPUTER INSTEAD`, one level down — rclone's own config is still the
  only route to a crypt/union remote or a reconnect (D-UI-005). The
  post-restore message that named the old entry went with it, per the
  menu-moved rule in `upgrade-and-install.md`.
- **The PIN is the tail of the address.** `http://device:8080/7677`, and the QR
  encodes the same string, so the handheld shows one line and the typed path
  needs nothing extra (D-UI-006).

Checked and rejected: an out-of-band flow that would remove the dead redirect
altogether. `rclone authorize` only offers the loopback-server flow — no
provider-displayed code — so the dead page stands (D-CLOUD-012).
