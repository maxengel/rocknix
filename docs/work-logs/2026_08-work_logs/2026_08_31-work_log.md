# 2026-08-31 work log

## 04:30 UTC — An on-screen keyboard for the sign-in window, and L1/R1 scroll

Maintainer feedback on the 20260831 H700 build, four points: the QR was too
dim, A and B were swapped, the ES page still described the phone-first flow,
and nothing brought up an on-screen keyboard. Then, mid-session: some
handhelds have touchscreens, so the keyboard needs to raise itself on text
entry, and L1/R1 should scroll.

### What shipped

- **`cloud-signin-window`**: an OSK below the page (a `GtkRevealer`, so the
  page resizes around it rather than being covered), raised automatically
  when the caret lands in a text field, once per field. `shift` gives
  capitals and symbols — without it the keyboard cannot type a password.
- **L1/R1 scroll**, implemented as `window.scrollBy` in the page rather than
  `Page_Up`/`Page_Down`, which do nothing while a text field has the caret.
  That is most of a sign-in form, and exactly when the button below the fold
  is what cannot be reached.
- **A help bar**, permanently visible. Every other screen on the device has
  one; the provider's page says nothing about a handheld.
- **A cairo spinner**, because `GtkSpinner` draws from the icon theme and
  this image ships no pixbuf loader for it. It failed silently — the loading
  screen was a line of text on an empty page. This had been reported as
  "a spinner would be nice" and had in fact been implemented; it just never
  rendered.
- **ES page** now leads with `SIGN IN ON THIS SCREEN`, and the QR is drawn
  `-s 8 -m 4 --background=FFFFFF --foreground=000000` and un-tinted
  (`setColorShift(0xFFFFFFFF)`, `setOpacity(255)`) — menu rows are drawn
  muted, and a muted QR is one a phone camera struggles with.

### Two design corrections found by building it

**The keys must not take GTK focus.** The first cut grabbed focus to the
WebView on every keypress, which meant the d-pad stopped walking the keys
after the first one. Giving focus to the keys instead would have blurred the
field being typed into, and a character delivered to a blurred field goes
nowhere. The answer is that the WebView keeps focus throughout and the d-pad
is intercepted in `on_key` before the page sees it.

**Auto-raise has to be once per field, not once per poll.** Re-raising a
keyboard the player has just dismissed, every half second, is worse than
never raising it. The probe records the field signature and acts only on a
change. Verified: dismissed, then held for 12 polls with the same field
focused, and it stayed down; a Tab to the password field raised it again.

### The process failure worth recording

Two builds reported `[DONE]` and exit 0 while compiling **stale source**. The
edits were made in the `rclone-cleanup` worktree and the package was built in
the `generic-x64` worktree, whose copy was three commits behind. The one
`git merge` that would have caught it was written with `2>/dev/null` on the
end, so its failure was invisible.

What caught it was `strings <binary> | grep "L1/R1 scroll"` returning 0 — not
the build log, which was clean, and not the screenshot, which showed a
plausible-looking window. Straight into
*"verify the artifact, not the report"*: a build system asked to build
something it already has will happily tell you it succeeded.

Filed as blindspot 20.

### Verified in the VM (1 GB, GENERIC_X64)

Driven through uinput, which is the same path the gamepad bridge uses in
production, after QEMU's `sendkey` silently dropped seven of eight commands.

| Behaviour | Result |
|---|---|
| Keyboard raises on `INPUT[email]` focus | yes, page resized above it |
| Stays down after dismiss (12 polls, same field) | yes |
| Tab to password field re-raises | yes |
| D-pad walks keys, A presses, character lands | yes |
| `shift` → capitals and symbols | yes |
| R1 scrolls with the caret in a field | yes |
| L1 scrolls back | yes |
| Non-text page (`other:BODY`) does not raise it | yes |

## 19:50 UTC — Five points from the device test

1. **Provider grouping** was split by our sign-in mechanism. Merged into one
   `RECOMMENDED` list (the pre-`f0af991f9` wording) with a `COMPLETE LIST`
   behind it. D-UI-010.
2. **The flow now asks how you want to type** before anything else, so the
   on-device route no longer opens onto a page about a phone. D-UI-011.
3. **The QR was still dim, and the previous fix could never have worked.**
   `ComponentList::render` calls `setColor(Text.color)` on every element of
   every row, every frame, and `ImageComponent::setColor` *is*
   `setColorShift` — so a shift set once at construction is overwritten
   sixty times a second. The address beside it kept its brightness only
   because it lives in a `ComponentGrid`, whose `setColor` does not reach the
   labels inside; that difference is exactly what was reported. Fixed with a
   subclass that refuses the tint. Rule added to `es-native-ui.md`.
4. **Button spacing** 0.0052 → 0.022 of screen width, plus one-word labels.
   Worth stating that these are independent: `makeButtonGrid` centres each
   button in a column of `buttonWidth + PADDING`, so the gap *is* the padding
   whatever the labels say. Terser labels shrink buttons; they do not
   separate them. D-UI-012.
5. **Wording** — "SIGN IN ON THIS SCREEN" gone.

## 20:10 UTC — Mode+Start, read from the pad

Maintainer confirmed Mode+Start. Rather than write that string into the
source, `find_gamepad()` now returns the pad's key capabilities alongside the
node and `exit_hint()` answers from them — `MODE + START` when `BTN_MODE` is
present, `SELECT + START` when it is not. It reaches the sign-in window as
`--exit-hint` and the ES page as `EXIT_HINT=` from `cloud_oauth info`.

The RG351M and RG353M have no Mode button. Hard-coding the maintainer's
answer would have told those players to press one that does not exist, which
is blindspot 18 exactly: a confident instruction about hardware, sourced from
one device's behaviour.

Verified against the real pad before shipping, not after:

    pad node : /dev/input/event4
    BTN_MODE (316) present : True
    exit_hint() -> MODE + START

## 20:35 UTC — Select as a modifier, and what the second Start press hit

Maintainer described their habit: hold Select, then press Start — Select
acting as the hotkey modifier, the RetroArch pattern. Verified the bridge
implements exactly that by driving `GamepadBridge._run` with synthetic evdev
streams rather than reading the code and asserting:

| Sequence | quit | typed |
|---|---|---|
| SELECT down, autorepeat ×2, START down | yes | — |
| MODE down, START down | yes | — |
| START alone | no | — |
| SELECT pressed **and released**, then START | no | — |
| SELECT held, then A | no | `enter` |

A true modifier: the hold must still be down, autorepeat does not break it,
and the hold never types.

**What the description surfaced.** Their habit presses Start *twice* —
RetroArch confirms the exit. Our window leaves on the first, so the second
lands somewhere. Chasing that found something bigger: `InputManager.cpp`
handles `SDL_JOYBUTTONDOWN` with no focus gate, and SDL joystick events are
not focus-gated the way keyboard events are. So ES is very likely processing
every d-pad and A press the player makes *in the browser*, navigating its own
menus behind it. Keyboard is fine — the compositor delivers that to the
focused surface only, which is why typing was never a problem.

ES already has the mechanism we skipped: `ApiSystem::launchExternalWindow_
before/_after` deinits audio, volume and the window (and with it InputManager
and the Renderer). It is what a game launch uses; the sign-in window takes
over the screen just as completely and should use it.

Filed as #54, unconfirmed on hardware and labelled as such — this is from
reading the code, and the honest next step is watching it rather than fixing
from a hypothesis. Not changing the staged image mid-test.

## 21:25 UTC — #54 confirmed and half fixed

Confirmed rather than assumed: ES holds `/dev/input/event4` (the node
`find_gamepad()` returns), `main.cpp:774` dispatches every SDL event with no
focus check, and on the device a second `EVIOCGRAB` is refused while the
first is held. So ES was receiving every d-pad and A press meant for the
provider's page, and an exclusive grab does stop it.

Fixed in `cloud_oauth` alone — ES untouched. The failure mode to design
against was a grab outliving the window, which leaves a handheld whose
buttons do nothing, so the read loop became a `select()` with a timeout whose
only purpose is to check the browser is still alive. All four exit paths
tested.

The ES-side takeover stays open: it would also free the renderer while WebKit
runs (~574 MB stack on a 1 GB device), but it means blocking ES on the
browser's lifetime and does not belong in a build queued for hardware test.

## 23:15 UTC — #54 complete: ES suspends for the sign-in page

`ApiSystem::launchCloudSignIn` follows `launchKodi` exactly. Two orderings
mattered: `cloud_oauth open` returns once the window is really up (or ES
tears down its renderer and the player watches the wallpaper), and the ES
page is presented before the takeover starts (ES needs something to come back
to).

The hazard that shaped it: SDL re-opens the joystick on init, so a grab still
held at resume would leave ES with no gamepad. `cloud_oauth wait` blocks
until the window is gone *and* the pad is grabbable — testing the condition
rather than sleeping.

Full round trip verified in the VM by screenshot at every step: provider list
→ chooser → ES's window vanishing from sway's tree → the real Dropbox page
with the keyboard raised → Escape → ES restored → B still navigating. The
device-aware exit hint proved itself in the negative case: no gamepad in the
VM, and it said `SELECT + START` rather than naming a Mode button.

`comm` truncation confirmed in the wild — `ps` shows `cloud-signin-wi`.

**Not covered:** the VM has no gamepad, so the grab-release handover never
ran. Proven separately on the real pad; the ordering is hardware-only.

## 2026-09-01 01:10 UTC — A pointer, and a field that can be selected

The second real sign-in attempt could not be finished: the password box never
took focus. Cause: the provider moves from email to password without loading
a page and leaves focus on the body, so nothing holds the caret -- the
on-screen keyboard has nowhere to type and spatial navigation has no anchor
to move from. The focus poll now adopts a visible text field when the page
has abandoned focus, never when something else holds it.

And the virtual pointer, one round after filing #55 for it. Built as a
**uinput device** rather than a cursor drawn by the window: sway renders it,
WebKit gets real pointer events, and it therefore reaches the two overlays
that were covering most of a four-inch screen -- including Google's One Tap
prompt, which is a cross-origin iframe no focus traversal can enter. Dragged
from a trackpad area on the phone page, which is where the touchscreen is.

Proof it delivers: a synthesised click moved page focus from BUTTON to BODY.

Two findings from testing it:

- libinput applies pointer acceleration, so a delta of N does not move N
  pixels. Fine for a person watching the cursor; it means a script cannot
  drive the pointer by dead reckoning, which cost an hour of "the click is
  not landing" before the BUTTON->BODY transition showed that it was.
- `seat * hide_cursor 1000` is in ROCKNIX's sway config. Right for a handheld
  with no mouse, wrong while one is being dragged -- the pointer disappears a
  second after movement stops and the tap is aimed blind. Disabled for the
  window's lifetime.

Also: the phone's typing box now keeps what was typed. Clearing it after
every keystroke made a keyboard that looked broken -- you type and nothing
appears anywhere you can see. Only the difference is sent, through a promise
queue so characters cannot overtake each other and arrive scrambled.

**Unverified:** the phone-driven feel. Driven synthetically over SSH, never
by a finger on a phone against the handheld's screen.
