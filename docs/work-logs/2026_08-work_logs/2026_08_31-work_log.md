# 2026-08-31 work log

## 04:30 UTC — An on-screen keyboard for the sign-in window, and L1/R1 scroll

Maintainer feedback on the 20260831 H700 build, four points: the QR was too
dim, A and B were swapped, the ES page still described the phone-first flow,
and nothing brought up an on-screen keyboard. Then, mid-session: some
handhelds have touchscreens, so the keyboard needs to raise itself on text
entry, and L1/R1 should scroll.

### What shipped

- **`cloud-signin-window`**: an OSK below the page (a `GtkRevealer`, so the
  page resizes around it rather than being covered), raised automatically
  when the caret lands in a text field, once per field. `shift` gives
  capitals and symbols — without it the keyboard cannot type a password.
- **L1/R1 scroll**, implemented as `window.scrollBy` in the page rather than
  `Page_Up`/`Page_Down`, which do nothing while a text field has the caret.
  That is most of a sign-in form, and exactly when the button below the fold
  is what cannot be reached.
- **A help bar**, permanently visible. Every other screen on the device has
  one; the provider's page says nothing about a handheld.
- **A cairo spinner**, because `GtkSpinner` draws from the icon theme and
  this image ships no pixbuf loader for it. It failed silently — the loading
  screen was a line of text on an empty page. This had been reported as
  "a spinner would be nice" and had in fact been implemented; it just never
  rendered.
- **ES page** now leads with `SIGN IN ON THIS SCREEN`, and the QR is drawn
  `-s 8 -m 4 --background=FFFFFF --foreground=000000` and un-tinted
  (`setColorShift(0xFFFFFFFF)`, `setOpacity(255)`) — menu rows are drawn
  muted, and a muted QR is one a phone camera struggles with.

### Two design corrections found by building it

**The keys must not take GTK focus.** The first cut grabbed focus to the
WebView on every keypress, which meant the d-pad stopped walking the keys
after the first one. Giving focus to the keys instead would have blurred the
field being typed into, and a character delivered to a blurred field goes
nowhere. The answer is that the WebView keeps focus throughout and the d-pad
is intercepted in `on_key` before the page sees it.

**Auto-raise has to be once per field, not once per poll.** Re-raising a
keyboard the player has just dismissed, every half second, is worse than
never raising it. The probe records the field signature and acts only on a
change. Verified: dismissed, then held for 12 polls with the same field
focused, and it stayed down; a Tab to the password field raised it again.

### The process failure worth recording

Two builds reported `[DONE]` and exit 0 while compiling **stale source**. The
edits were made in the `rclone-cleanup` worktree and the package was built in
the `generic-x64` worktree, whose copy was three commits behind. The one
`git merge` that would have caught it was written with `2>/dev/null` on the
end, so its failure was invisible.

What caught it was `strings <binary> | grep "L1/R1 scroll"` returning 0 — not
the build log, which was clean, and not the screenshot, which showed a
plausible-looking window. Straight into
*"verify the artifact, not the report"*: a build system asked to build
something it already has will happily tell you it succeeded.

Filed as blindspot 20.

### Verified in the VM (1 GB, GENERIC_X64)

Driven through uinput, which is the same path the gamepad bridge uses in
production, after QEMU's `sendkey` silently dropped seven of eight commands.

| Behaviour | Result |
|---|---|
| Keyboard raises on `INPUT[email]` focus | yes, page resized above it |
| Stays down after dismiss (12 polls, same field) | yes |
| Tab to password field re-raises | yes |
| D-pad walks keys, A presses, character lands | yes |
| `shift` → capitals and symbols | yes |
| R1 scrolls with the caret in a field | yes |
| L1 scrolls back | yes |
| Non-text page (`other:BODY`) does not raise it | yes |
