# Work log — 2026-08-27

## First working backup/restore round-trip on a device since January

Built `ROCKNIX-GENERIC_X64.x86_64-20260826` clean (631/631, no failures, ~2h49m)
and ran the full backup/restore round-trip in QEMU. Everything passed, and this
is the first image on which `backuptool backup` could execute at all — the
missing `zip` package had made the backup path dead since upstream dropped it
in January.

**backuptool, on the guest:**

- `zip` present and running (Info-ZIP 3.0), which was the whole point of the rebuild.
- `backuptool backup` completed: 16.4M, 227 entries, `unzip -t` OK.
- Credential stripping verified *in the archive*, not just in the code:
  `wifi.key=SUPERSECRET123` absent from the archived `system.cfg`;
  `cheevos_password` blanked to `""` while `cheevos_username` was kept, exactly
  as designed for the post-restore re-entry page.
- Archive rotation worked — the previous backup moved into `backup/archive/`.
- `backuptool restore` verified the archive, restored, set
  `.restore-finish-pending`, and rebooted. After the reboot all three planted
  settings held their backed-up values (`audio.preamp=77`,
  `display.brightness=33`, `video_fullscreen="false"`), having been mutated to
  11 / 99 / "true" beforehand. One-to-one match confirmed.

**cloud, via `tools/cloud-round-trip` over SSH:** all checks passed, including
the system-backup archive reaching the cloud and coming back byte-identical —
the phase-2 fix from the 26th, which had never run on a device — plus saves
round-tripping, the allowlist keeping excluded files out, and content
backup/restore.

**A test-design correction worth keeping.** My first round-trip attempt replaced
a 225-line OS-managed `system.cfg` with a 3-line synthetic file. After restore
and reboot the file had 225 lines again and my planted `wifi.ssid` was gone, which
looked like restore being undone. It was not: boot-time seeding regenerates keys
that are missing, and I had removed 222 of them. Re-running against *existing*
keys with distinctive values gave a clean, meaningful pass. A synthetic fixture
that does not resemble the real file tests the fixture, not the feature — the
same shape as blindspot 8.

Notes for the next session: the serial debug shell shares `ttyS0` with kernel
output, so commands are sent base64-encoded and decoded guest-side, with unique
BEG/END markers — multi-line and quoted scripts arrive mangled otherwise
(`/tmp/rkvm/ser.py`). Socket paths must stay short; `/tmp/rkser.sock` is fine
where a scratch-dir path is not. A separate two-day-old "ROCKNIX QA" VM is
holding port 10022, so this one runs on 10023.

## All four images built and published — and a publish that silently did not

Device builds ran sequentially off the consolidated `next`: RK3566 34 min,
RK3326 14 min (both warm roots), H700 1h52m (cold, its stampless root having
been wiped first). Zero failures. GENERIC_X64 had taken 2h49m cold earlier.
Every image verified before publishing: `zip` present and genuinely aarch64 —
not a host binary that slipped in — plus the backuptool guard, the anchored
`cloud_restore` filter, and the `/ROCKNIX` layout.

Two process failures on my side, both worth keeping.

**I stopped watching.** The H700 build finished at 04:36 and I did not notice
for ten hours, because the background watcher had been killed and I never
re-armed it. Worse, my liveness check was `pgrep -f build-devices.sh`, which
matches its own command line and so reported "alive: yes" for a build that had
already exited. `ps -eo cmd | grep -c '[b]uild-devices.sh'` cannot match itself
and is the check to use.

**A publish that reported success while publishing nothing.** Running a
multi-gigabyte upload in the foreground let the 2-minute tool limit kill it
mid-`gh release create`, which left the release a *draft*. `fork-publish-release`
sets `--prerelease` only on the create path; its existing-release branch
re-sets title and notes and nothing else. So every later run uploaded into the
draft, edited it, and printed `Done:` with an `untagged-<hash>` URL that reads
like a real release link. The release had all six assets and was invisible to
everyone but the owner. Fixed by having the update branch re-assert
`--draft=false ${PRERELEASE_FLAG}`, and verified by re-running it against the
now-published release: real tagged URL, `draft=false`, six assets.

Registered as blindspot 17. The generalization: an update path that only writes
the delta assumes the create path finished, and a half-finished create is
exactly when that assumption is false. A success message containing a
machine-generated placeholder is a failure signal, not a link.

## Two H700 devices, and a fact I invented

The maintainer is flashing the new build to an RG35xx SP as a fresh device, with a
second H700 handheld (RG-SP) arriving this week. Briefing that flash produced one
solid finding and one self-inflicted error.

**The error first.** I told them "RG35xx SP is DDR4" and handed over the matching
checksum. That was invented. There is no model-to-RAM mapping anywhere in the
tree — not in the H700 DTS set, the device options, or the u-boot packages, whose
configs are generic (`anbernic_rg35xx_h700_lpddr3/4_defconfig`). The only
mechanism that exists is a runtime `vdd-dram` regulator read in
`bootloader/update.sh` (1200000 -> DDR3, 1100000 -> DDR4), which is useless to
someone with no OS booted yet. A wrong pick is a device that will not boot. It was
caught only because they said "we should confirm the RAM" instead of acting on it.
Registered as blindspot 18: when a question is about the physical world and the
repo cannot answer it, say unknown and give the procedure — never pick the
plausible option. Recoverable at least: `update.sh` derives `BOOT_DISK` from the
booted partition, so u-boot lands on the SD card, not internal storage.

Filed as **#44** — the release notes say "pick the one matching your board" and
then list two filenames, which is exactly the gap I fell into. Options recorded:
document the regulator check, or ship one H700 image that selects u-boot at first
boot the way `update.sh` already does (flagged that the SPL runs before DRAM init,
so the single-image route needs a spike before anyone commits to it).

**The solid finding.** Two devices on one chipset is the control case #19 never
had. Three different build families cannot separate chipset from core version when
a transfer fails; holding the chipset constant makes either outcome decisive, and
it is far cheaper than the full matrix. Recorded on #19 with the sequencing —
control first, cross-chipset after — because its result determines whether the
matrix measures what it claims to.

The pair also turns #19's third task into a live defect. `scripts/image:163` writes
`HW_DEVICE="${DEVICE}"`, the build target, so twelve distinct Anbernic handhelds
all report `H700`. Both devices will be indistinguishable in anything keyed on it —
which breaks #23 (`conflict-wizard-ia.md` specifies `device + model` per side; two
identical `H700` rows convey nothing) and #20 (a manifest recording `H700` as
provenance cannot tell them apart). The model string is right there in the device
tree, and reading it is already precedent: `ap6611s/autostart/008-ap6611s` reads
`/proc/device-tree/model`. Added as acceptance criteria on #19 rather than leaving
it in a comment, per the tracker rule that the checkbox list is the contract.
