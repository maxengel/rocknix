# 2026-07-04 Work Log

## 00:20 UTC — GENERIC_X64 VM: booted all the way to EmulationStation

Got the fresh `feature/generic-x64` VM image to boot through to a rendering
EmulationStation in QEMU (llvmpipe software GL on virtio-gpu). Four x86_64-specific
boot blockers, each with an aarch64 counterpart that hid the issue:

1. **UEFI shell** (earlier): mkimage didn't flag partition 1 as ESP on gpt/syslinux, so
   strict UEFI wouldn't auto-run `\EFI\BOOT\BOOTX64.EFI`. Fixed with `set 1 esp on`.
2. **`/init` panic (error -2)**: x86_64 glibc's loader is `/lib64/ld-linux-x86-64.so.2`,
   but the base initramfs only made `/lib,/bin,/sbin`. Added an x86_64 initramfs overlay
   conf (`initramfs.x86_64.conf`) creating `/lib64 -> usr/lib`. aarch64's loader is
   `/lib/...` so it was unaffected.
3. **Post-resize "Can't lookup blockdev" → power-down**: first-boot `fs-resize` runs
   `tune2fs -U random`, regenerating the storage ext4 UUID. aarch64 survives because
   u-boot re-reads the UUID at boot (`fsuuid` in `a_boot.ini`); syslinux/grub bake it
   statically. Switched the x86_64 boot entries to `boot=LABEL`/`disk=LABEL` (labels
   `ROCKNIX`/`STORAGE` survive resize) — matches the ROCKNIX grub generator.
4. **ES crash "wayland not available"** — actually sway dying first: `111-sway-init`
   derives the DRM card number from the first connector matching `DP|HDMI|DSI`.
   virtio-gpu exposes the panel as `card0-Virtual-1`, so `card_no` was empty →
   `WLR_DRM_DEVICES=/dev/dri/card` (no number) → "Found 0 GPUs" → no Wayland → SDL abort.
   Added `Virtual` to the connector match. Real panels still match DP/HDMI/DSI first.

**Why it matters:** this is the whole point of GENERIC_X64 (issue #16) — devs can now QA
ES/features in a VM instead of flashing. The remaining concessions (llvmpipe vs hw GL,
skipped cores) are tracked for the eventual bare-metal x64 build (issue #17).

### Debugging/QA method notes (durable)
- Local QA: `qemu-system-x86_64` + OVMF split firmware (writable `OVMF_VARS` copy) +
  `-vga virtio`. TCG (`-cpu max`) works but is too slow for two boots + ES; KVM is needed
  for a timely full boot.
- KVM access: `setfacl -m u:max:rw /dev/kvm` is **reset by logind** between sessions. The
  durable fix is `usermod -aG kvm max` + launching QEMU via `sg kvm -c` (picks up the group
  without re-login).
- ES/other logs land on tmpfs `/var/log` (lost on shutdown). Read them **live over SSH**
  (root/rocknix, hostfwd + `SSH_ASKPASS`) or **offline** with `debugfs -R "cat …"` on the
  `dd`-extracted ext4 partition 2. Headless UI check: QEMU monitor `screendump`.
- The ES crash looked like a GL/ES bug but the real cause was one layer down (sway had no
  GPU). Reading `sway.log` before chasing ES saved a lot of time — verify the layer below
  before blaming the app (see engineering-practices).
