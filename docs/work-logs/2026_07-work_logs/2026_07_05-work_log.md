# 2026-07-05 Work Log

## 20:55 UTC — GENERIC_X64 boots to ES in KVM, but UTM drops to UEFI shell → root cause: 4K sectors

Landed the last boot blockers (sway virtio-gpu connector + a self-inflicted missing shebang in
`start_es.sh`) and verified a **clean image auto-boots to EmulationStation** in KVM. Published
qcow2 + raw to the fork release.

Then @maxengel reported the image still drops to the **UEFI interactive shell in UTM** on Mac
(both raw and native-qcow2). Spent the session pinning it down:

- The image is **correct**: it boots in Ubuntu OVMF, upstream EDK2 (retrage), and **qemu's own
  `edk2-x86_64-code.fd` (the exact firmware UTM bundles)**, across **virtio and SATA** buses.
- Verified the ESP is a valid EFI System partition and `BOOTX64.EFI` is a valid x86-64 PE.
- GPT primary + backup headers intact; container format (raw vs qcow2) is irrelevant (identical
  bytes; both fail in UTM).
- **Reproduced the failure** by forcing 4K sectors with UTM's firmware:
  `-device virtio-blk-pci,logical_block_size=4096,physical_block_size=4096` →
  `BdsDxe: failed to load Boot0001 "UEFI Misc Device" ... Not Found` → PXE → shell. Exactly the
  user's "`map` shows only `BLK0`/`BLK1`, no `FS0:`".

**Root cause:** OVMF/UTM firmware can't UEFI-boot a disk exposed with **4096-byte logical
sectors** when the GPT/FAT are laid out for 512 bytes (misreads GPT → only protective MBR → no
ESP). Confirmed by UTM docs + tianocore bug 957. Fix is **VM-side (present 512b sectors)**, not
the image — which validated the user's instinct that the *machine config* must travel with the
artifact.

### Decisions / follow-ups
- Deliver a **1-click `.utm` bundle** (config + disk in one file) with a **512b VirtIO** boot
  disk baked in — the user's stated goal and the actual fix. (`x64-vm-image` todo.)
- On "shareable dev image" formats: VDI is *least* universal (VirtualBox-only); qcow2 covers
  UTM+QEMU; VMDK is the broadest bare disk; but a bare disk still needs correct VM setup — the
  real shareable unit is an **appliance** (`.utm` / OVA) that carries the config.
- Immediate user fix to try: switch the UTM boot drive to a 512b interface (VirtIO/SATA), not a
  4K/NVMe-4K disk.
- Captured as a Copilot memory + a new section in `generic-x64-vm-testing.instructions.md`
  ("Won't boot in UTM / a VM → check the disk logical sector size").

### Method note
Matching the *exact* firmware the user runs (pulled qemu's `edk2-x86_64-code.fd`, the file UTM
ships) + sweeping one variable at a time (firmware → bus → sector size) is what turned an
un-reproducible "works for me" into a deterministic local repro. Container format was a red
herring; the disk **sector size** was the variable.
