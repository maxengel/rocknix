# 2026-07-27 Work Log

## Cloud setup asks for its password once, not twice

- Grounded the "drop our auth layer?" question in rclone's own rc server
  (fs/rc/rcserver/rcserver.go): --rc-user/--rc-pass IS the only credential —
  the web GUI's login form just replays it as HTTP basic auth, and the
  login_token is base64(user:pass). Dropping it does not remove a prompt, it
  removes the wall: unauthenticated rc allows inline remote definitions and
  backend init that can execute commands. rclone itself logs "It is
  recommended to use web gui with auth", and omitting the flags makes rclone
  invent a 128-character random password (worse to type).
- Decision: keep the single credential, kill the duplicate prompt. cloud_setup
  now embeds the credentials in the QR URL (what rclone does when it opens the
  GUI itself), so the browser is pre-authenticated and the page's login form
  is satisfied by the token. The printed address stays credential-free for
  manual typing.

## UTM bundles can advertise a reachable host address

- Problem: behind a port forward the guest cannot discover the address a phone
  must scan, and no launcher runs on macOS to inject it (fw_cfg injection was
  Linux-launcher-only).
- Solution: the generated .utm bundle now ships the fw_cfg argument
  pre-written with a deliberately invalid placeholder
  (EDIT-ME-http://your-host-ip:15572). The tester edits it once in UTM's
  QEMU > Additional Arguments; until then the guest rejects it and falls back
  to its own address. Bridged bundles omit the argument (guest is on the LAN).
- 095-cloud-url quirk restructured so any invalid/placeholder value also
  clears a stale override, not just a missing fw_cfg key.
- fw_cfg key and host port moved into profile.json (source of truth) and
  shared by both the Linux launcher and the UTM bundle; profile bumped to v4.
- Verified by rendering both outputs: launcher emits the live host IP, bundle
  emits the placeholder, port forwards and Emulated VLAN mode unchanged.
