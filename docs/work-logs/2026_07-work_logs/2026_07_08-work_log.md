# 2026-07-08 work log

## 21:30 UTC — GENERIC_X64 "menu has no dim/blur": root cause was disk size, not graphics

**Finding.** The long-hunted GENERIC_X64 ES bug (main menu opens/navigates but has no
dimmed/blurred background, wrong fonts, missing help-button glyphs) is **not** a
graphics/compositor/GL bug. It is caused by an **undersized VM disk**:

- The raw `.img` is ~4GB (`SYSTEM_SIZE=4096` + a tiny `STORAGE` tail). `STORAGE` resizes to
  fill its disk on first boot, but on a ~4GB disk it stays ~33MB and hits **100% full**.
- First-boot `rsync /usr/config → /storage/.config` then fails with **ENOSPC**
  (`rsync: write failed on .../resources/DroidSansFallbackFull.ttf: No space left on device`)
  and copies **0 of 144** ES resource files.
- ES therefore can't resolve its `:/` resources — including `:/shaders/blur.glsl` (menu
  dim/blur), `:/ubuntu_condensed.ttf`, and `:/help/*.svg`. `postProcessShader`'s shaderBatch
  is null → no dim. Real hardware never hits this (storage resizes to fill the whole SD card
  *before* the rsync).

**Red herrings ruled out:** weston vs sway (ES makes its own Mesa GL context regardless of
compositor), `glBlitFramebuffer`/`postProcessShader`, GL 3.0 core context. All downstream of
the missing embedded shader.

**How it was found.** SSH into the VM kept resetting and headless `screendump` was black, so I
added a **serial debug console** to GENERIC_X64 (`serial-debug-shell.service`: autologin root
`/bin/sh` on `ttyS0`, systemd debug-shell pattern since ROCKNIX strips all getty units). With a
real shell, `df -h /storage` (100%) + `journalctl | grep "no space"` made the cause obvious.
Also learned: headless `screendump` needs `-vnc :N` (a bare `-display none` captures black).

**Fix (verified).** Boot on a 16GB disk → storage resizes to 11.9GB → rsync completes (144
files, `blur.glsl` + fonts present, 0 ENOSPC) → main menu renders with a proper dimmed
background + fonts + help icons (screenshot-confirmed).

- Feature branch `feature/generic-x64`: committed the serial console (`a83efbd71d`); `mkimage`
  now also emits a **sparse 16GB `.qcow2`** gated on a new `VM_IMAGE_SIZE` option so a 1-click
  boot has adequate storage.
- Personal (`next`): updated `generic-x64-vm-testing.instructions.md` with the disk-size
  section + the serial-console technique + the `-vnc` screendump note.

**Follow-ups.** Public rocknix.org docs for GENERIC_X64 don't exist yet (target isn't upstream),
so no public-docs change today. Consider whether `SYSTEM_SIZE=4096` is larger than needed for
the ~1.9GB squashfs (would give more `STORAGE` headroom on small disks) — deferred, low value
since the qcow2 fix covers the VM case.
