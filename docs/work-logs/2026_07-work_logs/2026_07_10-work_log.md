# 2026-07-10 work log

## 23:30 UTC — Reopened GENERIC_X64 artifact work around environment parity

The 16 GiB qcow2 fixed storage sizing, but it did **not** satisfy the original developer-QA
goal: a disk image carries disk bytes only, not CPU, RAM, firmware, machine type, disk bus and
sector geometry, GPU, network, audio, input, or serial configuration. Closing the VM-image
task after publishing qcow2 was a scope error.

**Decision:** standardize on QEMU's guest-visible machine model, not VirtualBox. VirtualBox on
Apple silicon only runs Arm guests and cannot run this x86_64 image. UTM can run x86_64 via
QEMU TCG on the M5 Mac; Linux uses QEMU/KVM. Host acceleration necessarily differs, but both
must consume one versioned canonical profile.

Baseline profile:

- Q35 + UEFI
- Haswell-v4 (oldest fixed model satisfying ROCKNIX's `x86-64-v3` build), 4 vCPUs, 8 GiB RAM
- 16 GiB VirtIO disk with explicit 512-byte logical/physical sectors
- `virtio-gpu-gl-pci`, `virtio-net-pci`, Intel HDA, USB 3, and serial console

Implemented `projects/ROCKNIX/devices/GENERIC_X64/vm/profile.json` and a single generator that
runs Linux/QEMU and builds a current UTM configuration-v4 `.utm.zip` from that profile. The
Linux path full-booted with KVM to the serial debug shell. The UTM plist and bundle structure
were validated against UTM's current Codable schema; actual launch on macOS/UTM remains the
cross-host acceptance check.

`tools/fork-publish-release` now generates and uploads qcow2 and `.utm.zip` from the same
profile and updates existing release notes, preventing the two host environments from
silently drifting.
