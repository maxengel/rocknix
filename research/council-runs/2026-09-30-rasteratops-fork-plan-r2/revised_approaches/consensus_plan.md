## Winning plan as base

This is `claude-revised_plan.md` restated as an executable plan. Argument with reviewers is removed; the positions that argument produced are kept. Every element added or changed by this integration is marked in place as `[+seat: what]`. Anything unmarked is the base unchanged.

### 0. House rules

1. **External knowledge is labelled.** Anything about the LibreELEC build family, GitHub, `rclone`, or Docker that was not read in the corpus or the primary tree is marked *(family/platform knowledge — verify)*.
2. **Corpus numbers are inputs, not measurements.** Build times, line counts, root sizes, asset limits, and prior intervention counts are single samples until re-measured in P0.
3. **Labour, elapsed time, and owner yeses are three different quantities.** They are **recorded separately after each phase**, never planned as numbers. `[brief rule: the base's day-figures are struck; the controlling variables — cold-build time per target, whether `vm-qa` and builds can be isolated, owner latency — remain named as measurements to take]` `[+gpt via kimi ballot: owner time per yes and per flash is recorded; that record is the input to the 0.0.x cadence decision, not a budget set in advance]`
4. **Re-gate.** No identity-changing commit under `distributions/`, no updater re-point, and no tag until the P0 and P1 exits pass. Reads, backups, register writing, and throwaway-branch experiments are not gated. `[+kimi §2.8 "Phase E re-gate" / muse §F "half-executed gate, re-gate the remainder"; gpt §1 "block behavioural cutovers, not inspection, backup, or throwaway-branch experiments"]`
5. **Receipts.** Every exit check records the manifest digest it ran against and, where a negative fixture is defined, is shown to fail on it. `[+gpt §4 "each check must produce a revision-pinned receipt and fail when its negative fixture is introduced" — generalised from the base's brand-sweep negative control to all checks]`

### 1. Rules that shape 0.0.1

**1.1 ES: no refactor of upstream-owned files before the first measured upstream ES merge.** If step 0 of #336 needs a hook into ES, it lands as a narrow adapter: one new fork-owned source file plus the minimum call sites in existing files. D-WORKFLOW-080(a) (the `GuiMenu.cpp` split) is an unblocked backlog item whose trigger is a measured merge. Any future reconsideration: one bucket split on a branch, trial merge of `upstream/next`, decision from the conflict report.

**1.2 Rename: retained while tracking, with a forward rule and a trigger.** (a) Upstream-owned paths and package names are retained while the fork tracks upstream. (b) **Forward Rule:** every new fork-owned package, script, unit, or config takes the `rasteratops` prefix from creation. `[gemini §2.1 names this "The Forward Rule"; same rule as the base's 1.2(b), adopted as the contributor-facing name]` (c) The code-level rename is reconsidered only on a trial-merge cost report and is automatically reconsidered when the pin-vs-track trigger (§2.4) fires. This refines D-WORKFLOW-085; it does not reverse it.

**1.3 Identity implementation default: display-only, in place.** `[+kimi §2.5 "keep distributions/ROCKNIX/ with DISTRONAME=rasteratops set inside"; gemini §2.2 "Identity strings are updated strictly via DISTRONAME"; claude ballot "display-only should be the default; the split should be the opt-in throwaway experiment"]` For 0.0.1: keep `DISTRO=ROCKNIX` and the `distributions/ROCKNIX/` directory; set the display name via `DISTRONAME` inside it; change only consumers the P0 read classifies as display text (1.5). The `DISTRO=rasteratops PROJECT=ROCKNIX` split is run as a **throwaway-branch experiment only when the P0 read supplies a reason** (a player-visible string or recipe derives from `DISTRO` rather than `DISTRONAME`; or Branch B (§2.2) makes asset names free and the owner wants the new prefix from 0.0.1). Its exit is a completed build **and boot**, not variable expansion `[+gpt §3 / muse §C]`; at most one small reviewable coupling fix is attempted, then the experiment is closed for 0.0.1 `[+gpt §3 "Do not turn a naming release into a build-system refactor"]`.

**1.4 Persisted contracts keep their RC2 values in 0.0.1.** `[+gpt §2 "Default rule: preserve RC2's persisted paths, labels, and machine contracts"; kimi §2.4; muse §B; gemini §2.2]` `DISTRO_BOOTLABEL`, `DISTRO_DISKLABEL`, `/storage/.config/<name>/`, hostname, SMB share name, mount points, unit names, and the machine-readable fields of `/etc/os-release` stay as RC2 wrote them. The base's per-target "keep / dual / migrate" record survives, with **keep as the default**; any `dual` or `migrate` for 0.0.1 needs a cited read and an owner yes and is expected to be zero. Relabeling belongs to a later clean-install-only release whose init accepts both labels. No label-search shim is written before the boot path is read.

**1.5 Four-class classification of every identity consumer.** `[+gpt §2 "Classify each use as: 1. Display text. 2. Machine-readable identity. 3. Persisted path or network name. 4. Boot/storage contract."; gemini ballot Dissent 1]` The P0 sweep assigns every hit to one class; class 1 may change in 0.0.1, classes 2–4 default to keep (1.4).

**1.6 Backup and recovery are a P1 prerequisite.** Minimal mechanism: (a) an encrypted second copy of the secret layout (`~/.config/gh`, signing key, mail credentials, `rclone.conf`, runner registration) off `serval`; (b) `[+gpt ballot Dissent 2 / kimi §2.1 "a blueprint is not a backup… restic job"; muse §C "restic/rsync snapshot"]` an **off-host snapshot of non-reconstructible state** — unpushed work, local-only configuration, release records, retained candidates, archived source tarballs — with a recorded snapshot ID; reproducible caches and rebuildable worktrees are out of scope `[gpt ballot: "Reproducible caches need not all become mandatory backup scope"]`; (c) a `serval-blueprint.sh` that reproduces toolchain and worktrees on a clean host **without any secret**; (d) a restore drill: run the blueprint on a clean host, restore a representative file from the snapshot, confirm a warm build starts `[+gpt ballot: "verify a representative restore"]`. The blueprint is **role-specific**: a build or QA host never receives control-account credentials. Provisioning the second Tiny *is* the drill. `[+gpt §2 loss targets, recorded as the drill's pass condition: no loss of published release inputs; loss of active work bounded to what the snapshot cadence leaves unsnapshotted]`

**1.7 Isolation tests never print a secret, and isolation is configured, not assumed.** Replace any `sudo -u <runner> cat <token>` with `sudo -u <runner> test -r <path>; echo $?` expecting `1`; a synthetic canary at each secret location with an alert on read; an effective-privilege audit (`id`, `groups`, `sudo -l`, `docker` membership, `/var/run/docker.sock` readability, reachable `setuid` binaries). `[+gemini Phase 0.1: stated as configuration steps — remove the runner user from `docker`, revoke `sudo`, remove read access to `~/.ssh`, `~/.config/gh`, and cloud tokens]` A container with the Docker socket is not a secret boundary. `[+gpt §2: if these boundaries cannot yet be enforced, the Actions runner stays disabled]`

**1.8 Repositories: three transfers, one fork, all pinned.** `EmulationStation-fcamod` and the two other owned repositories transfer; `rocknix-splash` is upstream-owned and is **forked** into the org and pinned. `[+kimi §1 / claude ballot: the ES transfer precedes the P2 image build because the two player-visible strings are ES source; splash is a fourth repository on the same critical path]` Grants are scoped: the bot's fine-grained token names only the repositories it needs; team scope is not unlimited future access `[gpt, retained from base §2.3]`.

**1.9 Emergency exception to the plumbing freeze.** Credential revocation and security changes are never blocked by a WIP limit; the exception is recorded, not silently taken.

**1.10 Brand suite: a gated sweep with an allowlist.** (a) `NAMING.md` carries a versioned allowlist of permitted old-name occurrences with a reason each (attribution, licence notices, compatibility paths, history, translations, preserved compat IDs). (b) `strings` over `os-release`, the ES binary, theme XML, unit files, and the `/storage` skeleton, filtered against the allowlist, returns zero *unclassified* hits. (c) Template matching over QA frames with stated thresholds **and a bounding box** `[+muse §D P2 "logo template match with tolerance/bounding-box not '0 diff'"]`, plus a negative control: a frame with the old logo injected must fail. Sampled frames are a sample, not proof of absence in every frame; the report says so `[+gpt §4]`. (d) The same walk carries the **secret sweep** (test accounts, `rclone` remotes, dev material in `/etc` or the skeleton) and the leak classes (hostname, SMB share, mount points, unit names); discovered secrets are counted, never printed to logs `[+gpt §4]`. (e) **Localization reconciliation:** the two ES source-string changes are reconciled against every `.po`/`.xml` entry; orphaned entries are updated or the English fallback is verified and recorded `[gemini, retained from base P2; gpt §4 "Localization"]`. One image walk, four classifications: brand-visible, brand-internal, secret, allowed.

**1.11 `BUILD_ID` is defined before anything gates on it.** P0 quotes its derivation. The manifest binds each image to its own `BUILD_ID` and hash; cross-image consistency is asserted on the *inputs* (distro commit, ES commit, splash commit, container digest, source archive index), not on `BUILD_ID` equality.

**1.12 Background Tier 1 does not review code being rewritten.** During the step-0 spike, Tier 1 covers only files step 0 will not touch; the launch/control slice is reviewed after the spike stabilises, before step 1. **Known findings of security, state-preservation, or launch-path class block 0.1 regardless of tier.** Permission to explore on a branch is not permission to release.

**1.13 Divergence is a review signal.** The upstream-merge tool reports upstream-owned diff size and patch-refresh effort per merge; both feed the pin-or-track review (§2.4). `[+gpt §6: distribution and ES conflict/repair records are kept separately; imported workflows, build scripts, and patches are diffed and reviewed before execution — muse §B names the merge as an injection surface]` `patches/` is fork-maintained; a patch needing manual refresh three merges running becomes an upstreaming or override candidate at cadence review.

**1.14 Immutable candidate first, lock second, from the first build.** `vm-qa` reads a hashed copy in a candidate store, never the build's output path; a lock (`flock` around build and `vm-qa` `[+muse §D P1]`) is the secondary control against resource starvation. Two failure mechanisms, two controls. `[+gpt §3: per-package concurrency stays conservative until measured; a global job count is not a memory budget]`

**1.15 Boot-chain read and runtime-reference sweep, with decision branches.** Read `scripts/image`, the initramfs, fstab generation, the installer, and every consumer of `DISTRO`/`DISTRONAME`/`ID`/`LABEL`; record keep/dual/migrate per target (default keep, 1.4). Starting sweep (not a complete audit) `[+gpt §2 / muse §B / kimi §2.4: variable set; lowercase variants per kimi]`:

```sh
rg -n 'DISTRO(NAME)?\b|DISTRO_BOOTLABEL|DISTRO_DISKLABEL|HOSTNAME|DISTRO_SRC|distroname|rocknix' \
  packages projects scripts config distributions
```

Follow derived values into generated files and runtime consumers. `[+claude ballot "shared across all four": the first line of the sweep report answers whether `DISTRO=rasteratops` implies a new directory and whether image and asset filenames derive from `DISTRO`, `DISTRONAME`, or something else — this decides whether the RC2 asset match survives]`

**1.16 Release-channel discipline.** No CI image is ever a Release asset; CI images travel as Actions artifacts or through the candidate store. Releases start as drafts; the rehearsal vehicle is chosen so that fielded RC2 devices cannot be offered the candidate (a pre-release only if the P0 read shows fielded clients ignore pre-releases; otherwise drafts or an authenticated staging path); full release only at publish. Each asset's size is checked against the per-asset limit read in P0 *(platform limit — verify at P0)*.

**1.17 Trust assumption stated, not hidden.** A `.sha256` fetched beside its payload detects corruption; it does not authenticate origin. For 0.0.1 the anchor is TLS to the release host plus control of the org account, written into the notes and the register, with signing designed as a slot (key custody, rotation, what a compromised channel can make a device do) for 0.0.x.

**1.18 Step 0 needs a feasibility proof.** Display ownership, compositing, focus, controller ownership, and lifecycle when either process exits are the questions; a pause command over a socket answers none. First deliverable: the proof on `GENERIC_X64`; any command interface binds to localhost with the address stated. `[+kimi §2.8: before Step 1, a bidirectional RetroArch → runner → RetroArch interchange test for saves, states, auto-slot, and pending achievements, establishing where the rcheevos queue lives]`

**1.19 Small identity and custody items.** Redirect-sunset criterion: the fork stops depending on `maxengel/rocknix`'s redirect once every fielded device has completed one fork-to-fork update. 2FA custody: the owner is asked whether both org owners' authenticators and the bot secret share one physical device. Debris: the identity sweep includes the previous identity's strings, accounts, and domains. `[+kimi §2.8 / muse §B: second-personal-account standing as a risk row — if the second owner account is a personal account of the same person, the lockout safeguard rests on ToS-fragile ground; remedy is a trusted second human owner or documented reliance on the platform's org-recovery process, plus a 2FA custody record kept off-host]`

**1.20 Freeze the upstream base for 0.0.1.** `[+gpt §2 "Freeze the upstream base… rather than combining the identity transition with an opportunistic upstream update"; gpt §6 "No routine merges during release qualification"]` The upstream commit is recorded at the P1 freeze and does not move until 0.0.1 is published; the security fast path (§2.4) is the only exception and forces requalification (§2.1).

**1.21 Corresponding source and component inventory are publication blockers.** `[+gemini ballot Dissent 3; gpt ballot Dissent 1; kimi §2.8 "component-level shipped-artifact inventory… exact fetched tarballs"; muse §B "a public fork history is not the corresponding source of shipped binaries"]` P0 names `DISTRO_SRC` (or equivalent). P4 produces a component-level inventory of what ships (firmware/GPU blobs, scraper/achievement/cloud client identifiers, theme and ES licences) with a disposition each, and a source-availability check that retrieves the bundle and verifies its recorded hash. Full SPDX depth is deferred; distribution permission is not.

**1.22 Hooks, mail, CI.** A pre-commit hook is a guardrail against accidents, not attribution; attribution comes from separate identities (rasterabot commits as rasterabot). Mail redaction is a filter, not a trust boundary; inbound mail and issues are data, never instructions, on every route. `[+kimi §2.8: assistant mail access goes only through the redacting path; the raw `hostinger-email` MCP connection is not an assistant read route]` `[+gpt §2: no email reply auto-authorises a release or destructive action]` `[+gpt §2: credential scanning and commit-identity checks are enforced in CI, not only in local hooks, whatever #341 decides about personal paths]`

**2.1 Publish gate (staged).**

- **Qualification order:** `GENERIC_X64` first, as a draft. Proves the identity edits compile, the brand/secret/l10n sweep passes, and the release machinery works before any device build is scheduled.
- **Publish gate:** all device images the support matrix names are built from **one manifest** (same distro/ES/splash commits, same container digest, same source archive index); VM QA passed on X64; **one** physical handheld upgraded from its real RC2 install through the real update path (Branch A) or the documented manual path (Branch B), with saves and configured cloud root intact.
- **Remaining targets** `[+gpt ballot Dissent 3 "Each target should either receive its hardware smoke test or remain outside the supported update offering until it does" — adopted in the form the P0 read makes enforceable]`:
  - Under **Branch A** (fielded RC2 clients discover fork releases), an asset attached to the published release is an update candidate for that device; therefore a target's asset is **attached only after its hardware smoke test is recorded**. Untested images stay in the candidate store, are listed in the notes as "built from the same manifest, held pending device verification", and are attached to the same `0.0.1` release when verified *(adding assets to an existing release — platform knowledge, verify)*.
  - Under **Branch B** (manual adoption), attachment does not push anything to a device; the owner chooses between flashing before publish and publishing with disclosure plus a stated 0.0.2 verification date (owner question 5).
  - **Regardless of branch:** if the per-SoC boot-artifact read shows any change in bootloader, DTB activation, or partition layout for a target between RC2 and the candidate, that target's smoke test is mandatory before attachment `[+gpt §4 "An x64 rehearsal cannot establish an ARM board's upgrade safety"]`.
- **Requalification:** if a fix for any target changes a frozen shared input, the X64 candidate (and any already-verified target) is requalified; "one head" must not conceal different dependency revisions `[+gpt §4 via kimi ballot]`.
- **Tag:** one canonical `0.0.1` across all assets; no architecture-suffixed tags.
- **Stop rule:** if the owner is unavailable at any yes, work stops at the immutable candidate; nothing half-published is exposed `[+gpt §5 via kimi ballot]`.

Branch B procedure skeleton `[+gpt §3 "Manual adoption means an executable procedure"]`: (1) identify board and current build; (2) back up saves and configuration, retain known-good boot media; (3) download the matching asset from the fork release; (4) verify digest and any supported signature mechanism; (5) use RC2's source-confirmed manual route (`/storage/.update` only if the P0 read confirms it), sync, reboot; (6) verify build, save/config continuity, update-menu behaviour; (7) tested recovery if adoption fails. If in-place tar is unsafe, the procedure is clean install to separate media plus restore, not an improvised migration.

**2.3 Three enforceable roles on one box.** **Build** (runner user; no persistent credentials; restricted triggers), **bot** (rasterabot identity; fine-grained token scoped to needed repositories), **owner** (signing key, org admin, 2FA, publication yes). No five-role table, no formal threat model; the attack path is named once: unsolicited PR code on a persistent machine with publishing credentials → credential theft → malicious publish.

**2.4 Pin vs track: track, with a budgeted exit.** Hard-pinning removes the merge tax and the rename constraint but stops kernel/Mesa/bootloader/security fixes and makes new devices impossible. Recommendation: track. Divergence and patch-refresh numbers (1.13) are reviewed at every cadence against a pre-declared budget; if merge cost exceeds budget two cadences running, or the fork skips two consecutive cadences, or decides to pin, the pin-vs-track decision **and the code-level rename** are re-opened together. Cadence interval is owner-set; a security fast path runs outside the interval `[+gpt §6]`.

**2.5 Second Tiny.** Backup-first gates provisioning, not purchasing. Provisioning is the restore drill (1.6). Not a 0.0.1 dependency in either direction.

## Step 5 handoff content

**Context.** #338 ships the first release of rasteratops, an identity release of a ROCKNIX RC2 fork, from one build host (`serval`) for the device set the support matrix names, to a fleet the owner holds. Everything the release renames — distribution name, version scheme, asset names, hosting — is a migration input to an already-installed updater and boot chain, so the plan reads before it edits, preserves every persisted RC2 contract, publishes only bytes that were qualified against an immutable candidate, and keeps the ROCKNIX-to-rasteratops hop on one real device as the gate that matters. Time is recorded after each phase, never planned. The owner's yeses are counted and placed; their minutes are recorded.

### Register rows (the sentence each row carries)

1. **D-WORKFLOW-085 (refine):** Upstream-owned paths and package names are retained while the fork tracks upstream; every new fork-owned artifact takes the `rasteratops` prefix from creation; the code-level rename is reconsidered only on a trial-merge cost report and is re-opened automatically whenever the pin-vs-track trigger fires.
2. **D-WORKFLOW-083 (refine):** The RetroArch-under-ES Step 0 spike may proceed on a branch before Tier 1 closes; merging it and releasing 0.1 require closure of Tier 1 punch items for the launch/control/state slice and of any known security, state-preservation, or launch-path finding regardless of tier; Tiers 2–3 close before 0.2/0.3, except the Tier 3 launch-path slice, which gates #336 Step 1; this row takes effect only on explicit owner approval, otherwise the prior gate stands as written.
3. **Merge cadence and pin/track (new):** Upstream is reviewed at the owner-set interval with a security fast path and no merges during release qualification; every merge records upstream-owned diff size, patch-refresh effort, and ES conflict/repair cost separately, and imported workflows, scripts, and patches are diffed before execution; when merge cost exceeds the pre-declared budget on two consecutive cadences, or two cadences are skipped, or a pin is decided, the pin-vs-track decision and the code-level rename are re-opened together.
4. **Cloud namespace contract (new):** 0.0.1 does not rename, merge, dual-read, or delete cloud roots; the configured root wins on upgrade; the RC2 clean-install default ships unchanged; any future change to the default is preceded by the mixed-installation test (one account, upgraded device plus fresh install, both roots present, provider errors distinguished from absence, one write authority) and a non-destructive conflict rule.
5. **Update-channel trust assumption (new):** For 0.0.1 the update channel is authenticated by TLS to the release host plus owner control of the publishing organisation; the `.sha256` beside each asset detects corruption and does not authenticate origin; image signing is a designed slot (key custody, rotation, behaviour under channel compromise) for 0.0.x and is not implemented in 0.0.1.
6. **Runner trust boundary (new):** Self-hosted runners execute only `push` on protected refs and `workflow_dispatch`, never `pull_request`, `pull_request_target`, or `workflow_run` checkouts of untrusted code; the runner user holds no persistent publishing credentials, no `sudo`, no Docker-socket access, and cannot read bot, mail, or signing stores; build, bot, and owner are the only credential-holding roles; if any boundary cannot be enforced the runner stays disabled; credential revocation and security changes are exempt from any WIP freeze and are recorded when taken.
7. **Release publication discipline (new):** No CI image is ever attached to a Release; candidates live in the immutable candidate store keyed by digest and QA reads only from it; releases begin as drafts, use a pre-release for rehearsal only when the P0 read shows fielded clients ignore pre-releases, and become full releases only at the owner's per-release publication yes; under Branch A a device asset is attached only after that device's hardware smoke test is recorded; if the owner is unavailable the release stops at the immutable candidate.
8. **D-WORKFLOW-088 / Choice 2 (resolve):** D-WORKFLOW-088 is restored from the primary record or struck, and Choice 2 is labelled, before any dependent decision is finalised; until then dependent conclusions are marked conditional.
9. **Corresponding source and component inventory (new):** Every published release carries a component-level inventory of shipped works with licence and disposition (firmware and GPU blobs, scraper/achievement/cloud client identifiers, theme and ES licences) and preserves in fork-owned, backed-up storage the exact fetched source tarballs, patches, and build scripts for every component whose licence requires corresponding source; public repository visibility alone does not close the obligation; full SPDX depth is deferred.
10. **Organisation recovery and 2FA custody (new):** Organisation recovery must not depend on a second personal account of the same person or on authenticators that share one physical device with the bot secret; the remedy is a trusted second human owner or a documented reliance on the platform's org-recovery process, with a 2FA custody record kept off-host.
11. **Redirect sunset (new):** The fork stops depending on the old-name repository redirect once every fielded device has completed one fork-to-fork update; until then each release records the redirect dependency; `ghcr.io` namespaces and third-party embeds are not covered by the redirect and are re-pointed in P1.
12. **Identity default (new):** In 0.0.1 every persisted path, partition label, hostname, share name, mount point, unit name, and machine-readable identifier keeps its RC2 value; only consumers the P0 sweep classifies as display text change; `DISTRO=ROCKNIX` and `distributions/ROCKNIX/` are retained; relabeling belongs to a later clean-install-only release whose init accepts both labels.
13. **Support matrix (new):** The support matrix distinguishes build target, physical board, and QA guest and records per target the clean-install result, upgrade result, boot medium and boot-chain deltas, recovery method, and attachment status; a target with any boot-chain delta from RC2 receives its hardware smoke test before its asset is attached, regardless of adoption branch.
14. **Backup scope and recovery drill (new):** Non-reconstructible state (unpushed work, local-only configuration, release records, retained candidates, archived source tarballs) is snapshotted off-host with a recorded snapshot ID and a verified representative restore; credential recovery material is separately encrypted under owner control; the secret-free, role-specific blueprint reproduces toolchain and worktrees on a clean host, no build or QA host receives control-account credentials, and provisioning the second host is the restore drill.
