# #133 QA cloud matrix on the VM: self-hosted backends first, hosted providers that are not Dropbox second [OPEN]

**Maintainer, 2026-09-11:** "we should always ask the question: 'Can this be done on the VM?' Only if the answer is no should we move elsewhere. We can create a QA Dropbox account, but I actually don't know why that would matter. Why wouldn't we just use our web dev or something else? If anything, this gives us a chance to try other storage backends for our clone. We shouldn't optimize solely for Dropbox just because I use it. We'd be better off choosing a different clone cloud backend that isn't Dropbox and being able to test across more clouds."

Decision D-QA-017. Supersedes the Dropbox-account half of the proposal on #131.

## The matrix

**Self-hosted on the build host, reachable from the VM pair at 10.0.2.2 (no accounts, no personal data):**
- WebDAV -- today's `tools/cloud-test-backend` (port 9010, dead port 9011 for failures).
- S3 -- MinIO; `cloud-test-backend` already has a `BACKEND=s3` branch. Covers the S3 form (#123), multipart, ETag-as-hash.
- SFTP -- an OpenSSH instance with a QA key. Covers the SFTP form and a hash-less remote.
- SMB -- Samba. Covers the WINDOWS SHARE tier.
- FTP -- for the implicit/explicit TLS rows.

**Hosted, free tier, QA-only accounts that hold nothing of anyone's -- one or two, none of them Dropbox:** candidates Google Drive (OAuth, its own hash, shared-drive semantics), Box or pCloud (OAuth, different lock/rename behaviour), Mega (user/password, client-side crypto). Signed in on a VM guest through the wizard's own flow; the session never holds a password.

The Dropbox-specific bugs (#53's size-only comparison, #107's lock contention) stay Dropbox's to find; the matrix trades that for coverage of everything else, which is the maintainer's call.

## Acceptance criteria

- [ ] `tools/cloud-test-backend up --backend <name>` brings up each self-hosted backend and `rclone-conf` describes it; `tools/cloud-round-trip` passes against every one of them on the VM.
- [ ] `tools/vm-qa` can run the round-trip against a chosen backend (`--backend`), default WebDAV.
- [ ] At least one hosted non-Dropbox provider is signed in on a VM guest and the round-trip passes against it; the account holds only QA data.
- [ ] The device-testing policy's first question -- can the VM do it? -- is answered in writing in every issue that proposes a device run.
