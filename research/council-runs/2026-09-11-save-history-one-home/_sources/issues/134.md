# #134 Save history: one home for replaced and discarded saves, inside Saves, hidden, with a manifest [OPEN]


Maintainer, 2026-09-11: *"So, saves replaced something that is permanent. It doesn't
make sense, even with our existing naming scheme, which is discarded saves. Is this
meant to be a permanent part of our structure? If so, we should think about whether
this is even the right way of handling it. ... having two different homes for two
different events is confusing. I'd recommend that we house these within the saves
folder if possible and include readmes, but they need to be named clearly. We could
even consider whether these should be hidden directories so users are not tempted to
touch them. We want to keep this all as simple as possible for the end user."*

## 1. What exists and what is planned

The analysis, the options and the recommendation: `docs/save-history-gap-analysis.md` (published on `next`). Short form: the #11 plan as written institutionalises two sibling folders -- `Saves-replaced/` (rclone's `--backup-dir`, no metadata, one run deep) and the planned `Saves-discarded/` (#22 R9, `record.json`, per-save count) -- for what a player experiences as one thing. Recommendation: **one hidden store `Saves/.history/<unit>/<seq>/`, written only by the reconciler (retain-before-publish, the ordering rule #25 already states), `record.json` with a `reason`, a README at its root, one restore tool (#25) labelling by reason, `--backup-dir` retired.**

## What #11 does not cover (the gaps, regardless of this design)

- a replacement nobody decided: a crash-truncated save, a stale device that then played, a save state replaced on every exit -- today one run of protection (#132);
- no validity check before a publish (zero-length or all-zero save) -- no issue held it until now;
- save states churning any count-bounded store;
- self-hosted providers keep no versions of their own (#133);
- the layout was never on the public page.
