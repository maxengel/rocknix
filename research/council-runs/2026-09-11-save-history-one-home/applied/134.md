## The design, on one screen

**Home.** `<SAVES_REMOTE>/.history/<unit>/<seq>/`, dot-prefixed, excluded from every transfer by the allowlist's first rules. `<SAVES_REMOTE>/README.md` and `<SAVES_REMOTE>/.history/README.md` say what the folder is, how much it keeps, and that the handheld's menu is where a version comes back (in V1: that the versions are kept and the menu is coming, D-CLOUD-033). `--backup-dir` is retired at the #22 R1 cutover; until then the shipped scripts are unchanged (D-CLOUD-097).

**The invariant: retain only.** *Nothing leaves the cloud's current save unless that version is already a complete entry in the store.* Every version that is about to be overwritten or deleted is placed in `.history/` first, verified, and only then replaced (`replaced`, `discarded`, `deleted`, `suspect`, `legacy`). The other half of the council's store-first rule -- that every publication also places its own new version in the store before the head is written -- is **dropped** (D-CLOUD-102): with one console at a time there is no race for a pre-published copy to protect against, and the accidental overwrite is covered by the retain. There is no `published` entry and no reason by that name. This generalises D-CLOUD-014 (a backup never deletes by default) and D-CLOUD-078 (one last-known-good at rest) to every writer of the saves tree, and it is why the retain-on-decision store of #22 R9 is superseded rather than moved.

**Retain from the stage.** The console about to publish is the console that restored the cloud's current version, so its capture stage already holds those bytes (D-CLOUD-078; #21's stage keeps the last agreed version of every save until a newer one is agreed). The displaced version is uploaded **from the stage** into `.history/<unit>/<seq>/`, and then the new version is published: two uploads of the save's size on every backend alike, no download, no server-side copy on the common path. Where the stage cannot supply the displaced version there are exactly two cases, and neither is silent: a console about to overwrite a version it never restored is the classifier's **both-changed** unit and goes to the wizard (#23); a **legacy head** at the cutover, which no stage ever held, is retained by one cloud-to-cloud copy (server-side where the backend can, else one download and one upload) marked `legacy` -- a one-time cost per save at cutover, never a per-exit cost.

**The transaction.** (1) member bytes, stored under their own sha256 as the file name; (2) `record.json`, written last -- a valid record is the commit point; (3) the head. A directory without a valid record is an orphan: invisible to the reader and to the pruner's protections, swept only by the device whose id is in its `<seq>`, on a full pass, when its run id is not current and no local pending record names it. Copy, never move, from the head (a move opens the absence window D-CLOUD-037 turns into a question). A `replaced` entry is skipped when the newest complete entry of that save file already holds the same version and is protected, so a repeated retain is harmless; `discarded`, `deleted` and `suspect` entries are never deduplicated. Own-manifest witness (#22 R7) before any store write. Every store mutation writes its audit line before it acts (D-CLOUD-027).

**Where it runs.**

| Where | What | Player waits? |
| --- | --- | --- |
| **Launch path** | Nothing. A launch cancels an automatic pass in any phase (D-CLOUD-076); the only addition is quiescing a *dead* lock-owner's children, inside D-CLOUD-076's two-second budget. | No |
| **Exit sync** (cancellable) | Head evidence + own-manifest witness -> retain the displaced version from the stage (members, then `record.json` last) -> verify -> head write -> correspondence -> agreement. **Bounds and their priority (D-CLOUD-096, refined by P-2).** Protections first: **P1** head-equal, or named by this device's own pending record; **P2** the newest complete entry of a save whose head is absent *without explanation* (agreement on record, newest reason not `deleted`), and a device's own newest complete entry of any headless file; **P3** the newest `discarded` entry per save file (D-CLOUD-032's one step back survives routine churn). Then caps, on full passes only: **C1** count per save file (a state and its PNG are one entry; auto-state churn never evicts a manual slot's versions -- what makes D-CLOUD-099 true), default 3, range 1-9 (D-CLOUD-036); **C2** 90 days, only when both the entry's time and the pruner's clock are trusted; **C3** 256 MiB over every stored byte -- members, PNGs, records, imports, descriptors, orphans -- oldest first over this device's own unprotected entries. **A device deletes only entries its id owns**: free under serial use, and it makes a mistaken concurrent run harmless. Overshoot is logged and disclosed, never resolved by deleting protected material.

**One setting for the fleet.** The own manifest carries `history_keep {on, count, rev}` (additive, D-CLOUD-045). A pass reads every manifest and adopts the highest `rev`; ties: ON beats OFF, the larger count wins; an edit writes `rev = max_seen + 1`. Under serial use an edit is never concurrent with another, so last-edit-wins is trivially safe. OFF stops every new entry from the next pass, purges nothing, and the switch's dialog says what that gives up (P-1, the maintainer's word).

**Suspect (D-CLOUD-100).** Zero length, or all one byte, where the agreed version was neither. Heal from the capture stage by temp-and-rename; the suspect version kept as an exact descriptor (`size`, `byte`) -- a version, shown by #25 as SET ASIDE AS DAMAGED; nothing published for the unit; the recovery reported on the card after the install succeeds. Stage missing -> one bounded fetch of that unit; fetch fails -> `suspect-unhealed`, healed at the next full pass. Both sides suspect, no verified good counterpart, a both-changed pair with one suspect side, a suspect cloud head over a good local copy, and the second suspect capture of one save after a heal are **questions** (D-CLOUD-037's surface), never heals.

**No lock, and what serial play gives the wizard (D-CLOUD-102/103/104).** No lock, marker or hidden file tells another console that a game is in play: a console that dies mid-game or drops off Wi-Fi would leave one behind for somebody to clear. The realistic failure is a commute session with no network -- the commute console exits without publishing, the same game is played and published at home, and the commute console comes online changed while the cloud changed too. That is the classifier's both-changed unit and it goes to the wizard, with no prevention rule added. What D-CLOUD-103 gives the wizard is an assumption it may use: the two versions were made in sequence by one person. So the compare page keeps the source's columns -- the cloud's version left, this console's right (D-CLOUD-041) -- carries one line under each saying which console played it (the name the player gave it, D-NET-001) and whether that session was the later or the earlier one, ordered by publish sequence and never by clock, and opens with the cursor on the newer version (D-CLOUD-104). Nothing is kept without that press (D-CLOUD-032), the loser is retained, and KEEP BOTH stays first-class: both versions are real progress.

**Save states.** All of them, auto-states included (D-CLOUD-099), made true by the per-file count bucket above.

## Time to play as a gate (D-CLOUD-098, #135)

Interface to first frame: unchanged by design; E12 confirms it against the baseline. Exit to the next first frame: unchanged in the worst case (the cancellation budget holds); the exit sync itself grows by **one retain of the changed save -- one more spawn and one more upload of its size, on every backend alike, with no download** (the current R5 budget of 3-4 spawns on hashed backends becomes 4-5; the hashless path gains no re-fetch for the retained copy, because its bytes are the stage's and their hash is known). Those figures are arithmetic on the existing budget, not a measurement: E12 supplies the real ones, and reports latency distributions *and* completion rates. The number for "one changed battery save, hashed backend" becomes the budget row (P-13) and a run over it fails the suite. Nothing in this epic lands before that row exists.
