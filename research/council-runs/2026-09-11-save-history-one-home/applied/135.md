**Maintainer, 2026-09-11:** "we need to think about a key metric being the time to play, meaning how long does it take for someone to go from being in the UI to starting a game, or from exiting a game to starting another game. Things that could slow this down, for example, are: startup; game save sync when the console starts syncing after exiting a game, when you're then unable (or should be unable) to start a new game until the saves are written to the cloud, etc. We need to balance our goal of having a rigorous backup and sync engine with a player's goal of wanting to actually enjoy playing a game as quickly as possible."

Decision D-CLOUD-098. What already holds: a launch cancels an automatic sync in any phase (D-CLOUD-076); a sync that can touch saves gates a launch (D-CLOUD-038), which is the tension to measure rather than assume.

## The metric

- **UI to game**: from the press on a game to the emulator's first frame, on a device with cloud sync on, at boot (startup sync running) and at rest.
- **Game to game**: from the exit hotkey to the next game's first frame, with the exit sync in flight.
- Budgets to propose after a first measurement; the exit sync of one changed save should not add more than the network round trip it needs, and never a wait the player can see without a card saying why.

Can this be done on the VM? **Yes** -- `tools/vm-qa` gets a `time-to-play` cell: boot the pair, time carousel to RetroArch first frame (the exit test already detects the process; a frame is the screendump changing), and exit to relaunch with the exit sync running against the QA endpoint, with and without a bandwidth cap. Reported in the runner's table on every image.

## The cell, as #134 needs it (E12)

The cell runs **two arms** on WebDAV and SFTP, bandwidth-capped and not:

1. **no history** -- the exit sync as it is today, the baseline;
2. **retain-from-stage** -- the design (#134, #22 R5): the displaced version is uploaded from the capture stage into `<SAVES_REMOTE>/.history/` and verified, then the new version is published.

and measures the **one-time `legacy` retain** once beside them -- the cloud-to-cloud copy a full pass makes for a head no stage can supply at the cutover -- because it is a cutover cost per save, not a per-exit cost, and the two must not be confused in the budget row.

For each arm it reports: the **launch-path** time; the exit-sync **latency distribution**; the exit-sync **completion rate** (the share of exit syncs that finish before a launch cancels them, D-CLOUD-076); and the **startup-sync** duration.

## Acceptance criteria

- [ ] The runner reports both times for every image, and `docs/vm-qa-log.md` carries them. *(VM pair)*
- [ ] A budget for each is a register row, and a run over budget fails the suite. *(VM pair)*
- [ ] The design of #134's history store and #22's reconciler is checked against the budget before it lands (the retain is one extra small transfer; it must not be on the launch path). *(VM pair)*
- [ ] Settings that trade rigour for speed (startup sync, exit sync) say what they cost in seconds where the player turns them on. *(frames from `tools/vm-visual-qa`)*
- [ ] The launch-path number under retain-from-stage equals the no-history baseline within noise. *(VM pair, WebDAV + SFTP)*
- [ ] The exit-sync number for **one changed battery save on a hashed backend** is proposed as a register row (P-13 of D-CLOUD-101) from the measurement, never chosen; once recorded, a run over it fails the suite. *(VM pair, WebDAV)*
- [ ] No store operation happens on the launch path, and the exit sync adds only the retained entry and its record, checked against that row before #22 lands. *(VM pair, WebDAV + SFTP)*
